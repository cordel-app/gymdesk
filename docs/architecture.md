# Gymdesk Architecture

## TL;DR (read this first, skip the rest for small tasks)

**Stack**: Express API (`api/`) · Next.js admin app (`apps/admin/`, port 8081) · Next.js member PWA (`apps/member/`, port 8082) · MySQL 8 (HeatWave in prod, schema `fitness`) · Clerk auth.

**Tenant isolation**: every domain table has `gym_id`. Every query filters by it. The `x-gym-id` request header carries the active gym; `tenantContext` middleware resolves it and attaches `req.tenantCtx`.

**Auth**: `requireAuth()` verifies the Clerk Bearer token → `userId` on `req.auth`. `tenantContext` then resolves the gym role from `gym_memberships`. Use `requireModuleAccess(module)` / `requireModuleWrite(module)` to gate at the router-mount and write-route level respectively. Use `requireRole('admin')` only for explicit last-admin guards or superadmin operations. Never use `getAuth()` — use `req.auth`.

**Roles**: `guest` (public) · `member` · `nutritionist` · `accountant` · `front_desk` · `trainer_performance` · `trainer_perf_nutrition` · `admin` (gym-scoped) · `superadmin` (platform, Clerk metadata).

**DB conventions**: auto-increment `INT UNSIGNED` PKs, `CHAR(36)` UUID for `gyms`, `UTC_TIMESTAMP()` not `NOW()`, `VARCHAR` not `TEXT` for indexed columns, soft-delete via `deleted_at DATETIME`, named CHECK constraints for statuses, no `RETURNING` (insert then SELECT by `insertId`), `db.transaction()` for multi-statement writes.

**Frontend**: all requests go through `apiFetch()` → `/api/proxy/` (Next.js proxy, Node runtime) → backend. Admin app uses `useGym()` / `GymContext`; member app uses `useApp()` / `AppContext`. Sidebar is config-driven via `config/navigationGroups.ts` — add nav items there, not in JSX.

**Reference implementations**: Members (staff-level CRUD + soft-delete) · Plans (`api/src/api/membership-plans.ts`, admin-only CRUD). Copy one of these for new features.

**Architectural decisions**: see `docs/decisions.md` for the settled choices (MySQL, Clerk, no ORM, etc.) — don't re-litigate them.

---

## Overview

Multi-tenant Gym Management SaaS. One Express backend, two Next.js frontends (admin + member), one MySQL 8 database (Oracle HeatWave in deployed environments; schema `fitness`). Authentication via Clerk. Tenant isolation via `gym_id` on every domain table and the `x-gym-id` request header.

The domain now spans membership plans & billing, classes & scheduling, class packages/credits, promotions, workouts & training plans, team management, per-gym theming, and an audit log. See `docs/roadmap.md` for phase status.

## Authentication & Authorization

### Auth (Clerk)
- `requireAuth()` in `index.ts` verifies the Clerk Bearer token on every protected route.
- Decoded `userId` is attached as `req.auth.userId`.
- **Required Clerk instance setting: Restricted mode.** Every user in this app — Members and Team roles alike — is meant to arrive via an invitation, never public self-registration. In the Clerk Dashboard, this is `Configure → Protect → Restrictions → Enable restricted mode`, and it must be **on** for every instance (dev + production). This is a dashboard-only toggle, not exposed via the Backend API (`GET`/`PATCH /instance` and `/instance/restrictions` only cover allowlist/blocklist and other flags — no sign-up-mode field), so it can't be enforced from code and isn't covered by CI. With it off, anyone can self-serve sign up with any email at `/sign-up`, independent of invitation state — see the Team invite flow note below for why that matters.

### Tenant context (`infra/tenantContext.ts`)
- Reads the `x-gym-id` header, looks up `gym_memberships` to get the user's `role` in that gym.
- Attaches `req.tenantCtx = { userId, gymId, role, gymMembershipId, isSuperadmin, actorName }`. `actorName` is derived from the Clerk user object already fetched in this middleware and stored for use by `recordAudit` (no extra query).
- Helper `getTenantContext(req)` retrieves it safely inside route handlers.
- Superadmins (Clerk metadata) are granted a synthetic `admin` role for any gym without a membership row.

### Roles

`AppRole` (the DB-backed role type, from `api/src/infra/permissions.ts`) is `admin | trainer_performance | trainer_perf_nutrition | front_desk | accountant | nutritionist | member`. `superadmin` is a **platform** role stored in Clerk, not a `gym_memberships` value. `guest` is anonymous (public routes only). Migration 075 renamed `coach → trainer_performance` and `staff → front_desk` and added 3 new roles.

### User Impersonation (#135, extended by #189)
Superadmins can impersonate any active gym user for support and debugging without a password change.

**How it works (separation of authentication and authorization):**
- The authenticated identity never changes. Only the *effective* identity used for authorization changes.
- The frontend stores an impersonation session in `sessionStorage` (survives refresh, cleared on tab close).
- `apiFetch()` appends `x-impersonate-as: <value>` to every request while impersonating. The value is `member:<id>` when impersonating a member (using `members.id`), or the Clerk user ID when impersonating a staff user.
- `tenantContext` detects this header and, after confirming the caller is a superadmin, resolves the effective identity. For `member:<id>` prefixed values it queries `members` directly (no `gym_memberships` join needed, so members without Clerk accounts are eligible). For Clerk user IDs it falls back to the existing `gym_memberships` lookup. Sets `effectiveType: 'member' | 'staff' | null` on the context.
- `TenantContext` carries `effectiveUserId` and `effectiveType`. For member impersonation `effectiveUserId` is the `members.id` as a string; for staff or normal usage it is the Clerk user ID. All `/me/*` handlers use the `resolveMemberId(gymId, ctx)` helper which routes to `WHERE members.id = ?` or `WHERE clerk_user_id = ?` depending on `effectiveType`.
- `centerContext` (runs after `tenantContext` on `/me/*`) follows the same rule when resolving a `member` role's assigned centers: it matches `member_centers` on `members.id = effectiveUserId` under member impersonation, or `members.clerk_user_id = userId` otherwise — never the impersonating superadmin's raw `userId` against `clerk_user_id`, which would resolve to zero centers and 403 every `x-center-id`-scoped request (#362).
- `recordAudit` encodes both identities in `actor_name` (e.g. `"Alice Johnson (impersonating John Smith)"`) so every business audit row remains traceable.
- **Gotcha — `centerContext` runs after `tenantContext` and must key off `effectiveUserId`, not `userId`.** `centerContext` (`api/src/infra/centerContext.ts`) resolves a `member`-role caller's `allowedCenterIds` via `member_centers`. Under member impersonation `userId` is still the impersonating superadmin's own Clerk ID — only `effectiveUserId`/`effectiveType` carry the impersonated member's identity — so any lookup keyed on `userId` (e.g. `clerk_user_id = ?`) silently resolves to zero centers instead of the impersonated member's. When `effectiveType === 'member'`, match `member_centers.member_id = effectiveUserId` directly instead of joining through `clerk_user_id`. `/me/*` handlers that scope by center (e.g. `GET /me/schedule` filtering `class_sessions.center_id`) must call `getCenterContext(req)` themselves — `centerContext` only populates `req.centerCtx`, it does not filter automatically like `tenantContext`'s `gym_id` scoping.
- **Gotcha — an empty `member_centers` result is not always "assigned to zero centers."** Many gyms have only one center and never populate `member_centers` at all. `centerContext` treats a `member` role's empty lookup as a single-center-gym fallback: if the gym has exactly one **active** center, `allowedCenterIds` resolves to that sole center rather than `[]`, mirroring `resolveCenterId()`'s existing single-center fallback for writes. Only a gym with 2+ active centers and a member genuinely unassigned in `member_centers` resolves to `[]` (sees nothing).
- **Sole-center defaulting counts active centers only.** Every "no center given → use the gym's only center" fallback (`resolveCenterId()`, `resolveMemberCenters()`, `resolveStaffCenters()`, the `centerContext` member fallback) goes through `soleActiveCenterId()` in `infra/centerContext.ts`. An inactive center never makes a gym multi-center; staff-side explicit center choices still accept inactive centers, because the admin pickers list them. Website registration no longer involves centers at all (#757).
- **Gotcha — `calendar_events.center_id` can be NULL and must stay visible regardless of center scoping (#478).** `materializeScheduleRule` (`domain/scheduleEngine.ts`) sets a materialized occurrence's `center_id` from its Activity Type's `default_center_id`, which is nullable and commonly unset. A strict `ce.center_id = ?` / `ce.center_id IN (...)` filter excludes every such row for every member (NULL never matches), which is what made schedule-rule-generated sessions vanish from the Member Calendar while the (center-unfiltered) Admin Calendar kept showing them. `GET /me/schedule`, `GET /me/bookings`, `GET /me/upcoming`, and `GET /me/activity-history` (`api/src/api/me.ts`) all wrap their center filter as `(ce.center_id IS NULL OR ce.center_id = ?)` / `(ce.center_id IS NULL OR ce.center_id IN (...))` — a NULL `center_id` means the occurrence isn't tied to any one center, so it must stay visible under every center context rather than being silently dropped. Any new center-scoped query against `calendar_events` should follow the same pattern.

**API surface** (`api/src/api/impersonation.ts`, mounted at `/platform/impersonation`, no `tenantContext` middleware — uses `requireSuperadmin` only):
- `GET /platform/impersonation/targets?q=&gym_id=&type=` — returns active staff (non-member roles in `gym_memberships`, name LIKE) + **all active members** (`members.deleted_at IS NULL`, no Clerk requirement); excludes the caller. Returns `[{ id, name, email, type, role, status?, gymId }]` where member `id` is `"member:<members.id>"` and staff `id` is the Clerk user ID. `type` (`staff` | `member`) is an optional filter — omitted, the endpoint returns both (original behavior, used internally); the Admin app's `ImpersonationDialog` always passes `type=staff` and the Member app's dialog conceptually wants `type=member` (#504 — the Admin dialog previously received Members mixed into its results because this filter didn't exist). A staff row with neither `name` nor `email` set falls back to its raw Clerk `user_id` as `name` for matching purposes — the Admin dialog detects this (`name === id`) and shows a translated placeholder instead of the technical ID. **#592:** staff targets are `gym_memberships` `LEFT JOIN staff ON staff.gym_membership_id = gm.id`, so `name` prefers the Staff record's `first_name last_name` and the response carries `profile`/`staffId`; the Admin dialog shows the profile as the secondary label. A login with no Staff record (the gym owner's admin membership created at gym creation) is still listed under its membership name; a Staff record with no login is not — there is no identity to impersonate. A **pending invitation** (`status = 'invited'`, `invited_<ts>` placeholder) is listed but greyed out as "Invitation pending", and `POST /:targetId` refuses it with 400: `tenantContext` resolves the target in Clerk on every request, so a session on a placeholder would fail on its first call (this reverses the POST half of #358; invited staff still appear, per #342).
- `POST /platform/impersonation/stop` — accepts `{ impersonated_user_id, impersonated_user_name?, impersonated_role?, duration_seconds? }`, returns 204. Must be declared before `/:targetId` in the router to avoid being swallowed by the dynamic segment.
- `POST /platform/impersonation/:targetId` — body `{ targetType: 'member' | 'staff' }`. For members: queries `members` by `id`; returns `{ id: 'member:<N>', name, role: 'member', gym_id, gymIds }`. For staff: `gym_memberships` check only (not yourself); returns `{ id: <clerkUserId>, name, role, gym_id, gymIds }`. `gymIds` restricts the gym selector in the frontend.
- **Staff discovery/validation is fully database-driven (#364)** — `impersonation.ts` makes no Clerk lookups at all (`createClerkClient` was removed from this router). Staff targets and validation come exclusively from `gym_memberships`; a staff member missing from Clerk still appears and can be impersonated. Superadmins are excluded implicitly because they carry no `gym_memberships` row (see `TenantContext.gymMembershipId`'s doc comment) — impersonating a superadmin's Clerk user ID simply fails the `gym_memberships` lookup with "no membership in this gym", the same as any other non-member user ID. This is a deliberate simplification (confirmed on the ticket): no `superadmins` DB table was introduced, since superadmin status remains Clerk-only and out of scope for this router. `requireSuperadmin` (the gate on *calling* these endpoints) is unaffected and still reads Clerk's `publicMetadata.platform_role`.

## Multi-tenancy Pattern

Every domain table has `gym_id CHAR(36) REFERENCES gyms`. Every query filters by it:

```sql
SELECT * FROM members WHERE gym_id = ? AND deleted_at IS NULL
```

The frontend sends `x-gym-id` on every request via `apiFetch()`, which reads it from `GymContext.activeGymId`. Global lookup tables (`benefit_types`, `charge_types`, `action_types`, `result_types`) are the deliberate exception — they have no `gym_id` and are seeded in their migrations. `payment_providers` (#636, migration 175) is the same exception with CRUD on top: platform-level configuration administered from Cordel, pointed at from the tenant side by `gyms.payment_provider_id` (NOT NULL). It is deliberately *not* the nullable-`gym_id` hybrid `themes` and `nutrition_library_items` use — a gym can own a theme, but never a payment provider — and the joined row is served only on the superadmin `/platform/gyms` reads, never on the member-readable `GET /gyms`, since a provider's status and default flag are platform state. The nutrition-library junction tables (`nutrition_library_item_categories`, `nutrition_library_item_qualities`, `nutrition_library_item_translations`) are the same exception one level down: they hang off `nutrition_library_items` by FK with `ON DELETE CASCADE`, so tenant isolation holds transitively and a `gym_id` of their own would only be able to disagree with the item's. `nutrition_library_items` is a hybrid: `gym_id` is nullable — `NULL` marks a Cordel-owned system item (global, read-only to gyms), a set value marks a gym-owned item that gym can edit (#350).

## Request Locale (`infra/locale.ts`, #643)

Translated **UI labels** live in each app's `locales/base/{en,es,ca}.json` and never reach the API. Translated **data** — content stored in the database — has to be resolved server-side, so the API needs to know the caller's language.

`getRequestLocale(req)` resolves it from, in order: the `x-locale` header (both apps send it from next-intl's `useLocale()`; both `/api/proxy` routes allowlist it), then `Accept-Language` (q-value ordered, with `es-ES` falling back to `es`), then the base locale. It never throws and never returns a value outside the allowlist.

- `SUPPORTED_LOCALES` (env, default `en,es,ca`) is the allowlist; entries that aren't well-formed BCP-47 tags are dropped at boot, and an allowlist that parses to nothing throws.
- `DEFAULT_LOCALE` (env, default `en`) is the base locale: the language base columns are written in, and the fallback whenever a locale has no translation row. Untranslated never renders blank.

**Translating a column.** Add a junction table keyed `(entity_id, locale)` holding the translated value — the same catalogue+junction shape used for categories and qualities — and leave the base column on the entity as the fallback and the uniqueness key. Resolve reads through a `COALESCE` subquery (`localizedNameSql` in `domain/nutritionLibrary.ts` is the reference), which collapses to a plain column reference for the base locale so English pays nothing. The locale is interpolated into that SQL rather than parameterised, so the helper embeds **the matching `SUPPORTED_LOCALES` entry**, not the locale it was handed — the argument is compared against the allowlist and otherwise unused, and anything with no match resolves to the base column. Request bytes therefore never reach the query text, regardless of what upstream validation did.

Expose the localized value as a **separate field** (`display_name`) rather than overwriting the base one: edit forms submit the base value back, so a form prefilled from a translation would overwrite the original on save.

## Database Conventions

- **Migrations**: Knex JS files in `infra/migrations/`. Numbered sequentially (`001_` … `071_`). Run with `npm run db:migrate`. ⚠️ MySQL DDL is **non-transactional** — a failed migration leaves partial state, so keep migrations small and re-runnable (guard `ALTER`s with `hasColumn`/information_schema checks — see `030_gym_theme.js`).
- **Primary keys**: auto-increment `INT UNSIGNED` for domain tables, `CHAR(36)` UUID for `gyms` (tenant root, `DEFAULT (UUID())`).
- **Timestamps**: `DATETIME`, always UTC (the mysql2 pool uses `timezone: 'Z'`; use `UTC_TIMESTAMP()` in SQL, never `NOW()`).
- **Indexed text columns**: `VARCHAR(n)`, not `TEXT` (MySQL cannot index TEXT without a prefix length).
- **Soft deletes**: Add `deleted_at DATETIME` and filter `WHERE deleted_at IS NULL`. Used for members, workout templates (which also set `status='deleted'`), and exercises (`status='deleted'` + `deleted_at`; the `(gym_id, name)` unique index was dropped so a deleted name can be reused — uniqueness among non-deleted rows is enforced in the router). Consider for other user-facing entities.
- **Cascade**: FK `ON DELETE CASCADE` when the child has no meaning without the parent. Use `ON DELETE SET NULL` when the reference is optional.
- **Duplicates**: unique-key violations surface as `err.code === 'ER_DUP_ENTRY'` (errno 1062) → return 409.
- **Statuses**: `VARCHAR` + a **named** CHECK constraint (so the allowed set can evolve without an `ALTER TYPE` dance).
- **No partial/filtered indexes** in MySQL: for "unique among non-deleted/active rows" use a generated column + unique index.
- **Inserts**: no `RETURNING` in MySQL — insert, then `SELECT` by `insertId` (returned by the `db.query` helper). Upserts use `INSERT ... AS new ON DUPLICATE KEY UPDATE col = new.col`; "insert if absent" uses `INSERT IGNORE`.
- **Transactions**: multi-statement writes use `db.transaction(async (tx) => { … })` — never `BEGIN`/`COMMIT` through `db.query` (pooled connections).

### `gym_memberships` (the "users in a gym" table)

Beyond `user_id`, `gym_id`, `role`, this table now carries invitation state (migrations 031–034):
- `status` — `active | invited` (named CHECK).
- `email` — set for invited rows before a Clerk user exists; cleared to `NULL` on link.
- `name` — display name (editable for invited rows).
- `invitation_id` — the Clerk invitation id, used to revoke on removal.

Invited rows use a placeholder `user_id` of the form `invited_<timestamp>` until the invitee signs in and `/staff/link` (or the Clerk `user.created` webhook) materializes the real Clerk `user_id`. Since #592 every non-member row is expected to be owned by a Staff record via `staff.gym_membership_id` (FK `ON DELETE SET NULL`); the exception is the gym owner's admin row inserted at gym creation.

### `members` (portal-invite tracking, migration 051)

`members.invitation_id` (nullable, migration 051) mirrors `gym_memberships.invitation_id` — the pending Clerk invitation id, used to revoke on removal or explicit un-invite. Unlike `gym_memberships`, there's no `status` column: a member row is always "real" (it's the billing/plan record) independent of portal access, so portal state is derived as `clerk_user_id IS NULL AND invitation_id IS NOT NULL` (invited) vs `clerk_user_id` set (linked) vs neither (never invited). See "Member invite + auto-link flow" below.

### `user_memberships` — billing columns (migration 111)

Two nullable columns added for recurring MIT billing:
- `next_billing_date DATE NULL` — set by the payment webhook on the first successful charge (DATE_ADD(starts_at, INTERVAL bp.recurring_billing_interval bp.recurring_billing_unit)); advanced by the billing run after each subsequent charge.
- `last_billed_at DATETIME NULL` — stamped by the billing run on success.

### `billing_run_log` (migration 111)

System-wide singleton (single row, id=1, CHECK id=1). Not a per-tenant table — intentional exception to the `gym_id` convention. Tracks `last_run_at DATETIME NULL` for the 23-hour rate limit on `POST /billing/run`.

`billing_events.event_type` CHECK extended with `recurring_payment` and `failed_billing`. `payment_requests.source` CHECK extended with `billing_run`. Migration 185 (#635 stage 11) adds `waived_billing` — a cycle the assignment's Free Period, Bonus Duration or an applied Promotion's free month covered, recorded at amount 0 with no Payment Transaction behind it, so `deriveBillingEventStatus` reads it as `recorded` (informational, never payment-actionable). A new event type goes in **two** places: the CHECK and whatever writes it; `billing.ts` is the only writer of this one.

### `recurring_booking_run_log` (#647 stage 4, migration 170)

The same singleton shape as `billing_run_log` (single row, id=1, CHECK id=1, `last_run_at DATETIME NULL`), for the 23-hour guard on `POST /recurring-bookings/run`. Also not per-tenant — the second deliberate exception to the `gym_id` convention, and for the same reason: it is a lock on a platform-wide job, not tenant data. Stamped when a run *starts* (not on success, unlike billing) so a run that dies half way still holds the lock rather than inviting a retry storm; re-running is harmless because the job is idempotent by construction.

Migration 170 also rewrites `chk_member_notifications_type` (migration 087) to add `recurring_booking_skipped`, and — while the constraint is being re-added anyway — `shared_training_approved` / `shared_training_rejected`, which `infra/notifications.ts` has emitted since #575 without ever being added to the CHECK, so those inserts were failing invisibly (`sendNotification()` is fire-and-forget and only `console.error`s). **Adding a notification type now means editing that CHECK**, not just the `NotificationType` union.

### Billing Event payment actions (#640, migration 165)

A **Billing Event** (`billing_events`) is the charge; a **Payment Transaction** (`payment_requests` pointing at it through `billing_event_id`) is an attempt to settle it. An event carries 0..N transactions, and its **status is the status of the latest one** — `domain/billingEventStatus.ts` (pure, unit-tested) maps `completed`→`paid`, `failed`/`expired`→`failed`, `pending`→`pending`, and falls back to the `event_type` mapping (`recurring_payment`/`payment_recorded`→`paid`, `failed_billing`→`failed`, everything else→`recorded`) for an event with no transaction at all. Both the list endpoint and the Details endpoint derive from that one module, never inline.

Migration 165 adds `modified_at` + `modified_by_user_id` to `billing_events` and `payment_requests`, and `failure_code` / `failure_message` / `notes` / `attempt` to `payment_requests`; `chk_payment_requests_source` widens to `admin|customer|billing_run|retry|manual`. The actor columns are Clerk user ids (matching `billing_events.actor_user_id`, not the `modified_by_membership_id` FK the newer catalog tables use), resolved for display through `gym_memberships.name` — the same lookup the audit registry's `gym_user` entity uses.

Three routes on `paymentsRouter`, all under the existing PAYMENTS gates:
- `GET /payments/billing-events/:id` — read-only Details (§2 of the issue): id, member, plan, amount, currency, derived status, event/charge type, source, Created At/By, Modified At/By, Next Payment, failure reason (transaction-level wins over the ledger row's `notes`), receipt number, and the `can_retry` / `can_record_manual_payment` flags the UI keys its context menu on.
- `POST /payments/billing-events/:id/retry` — Retry Payment. Creates a **new transaction against the same event** (never a second ledger row), fires `executeRecurring`, and on rejection fires once more. Two rejections pause the assigned plan via `recordStatusChange`, so the pause is explicable from the ledger like any other transition.
- `POST /payments/billing-events/:id/manual-payment` — the front-desk settlement the issue first called "Flag as Paid". Records a completed transaction (`source='manual'`, `provider='manual'`), no provider call.

Invariants both actions share (`domain/billingEventPayments.ts`): the event must be `failed`, must hang off a membership (`payment_requests.user_membership_id` is NOT NULL) and must have a positive amount; an event that already has a **completed** transaction returns 409, which is also what stops one charge advancing the schedule twice. A settled charge advances `next_billing_date`/`last_billed_at` exactly as the nightly run does, and only while the membership is still waiting on that charge (`next_billing_date <= today`). `audit_logs` carries the manual intervention — actions `retry_payment` and `manual_payment` with previous/new status and the per-attempt results.

`GET /members` derives `payment_status` from the latest transaction of **any** membership covering the member (joined through `user_membership_members`), not only from transactions raised against them personally: a two-person or family Membership bills once, against its owner, so every covered member has to follow that charge's outcome.

### Assigned Plans — expanded detail + Billing Events (#511 stage 3, migration 150)

`GET /user-memberships/:id` is now the "expanded card" endpoint for an Assigned Plan (mirrors `enrichPlan()`'s pattern in `membership-plans.ts` — everything the Details modal needs in one call, rather than several separate per-section requests). Beyond the plain `user_memberships` row + audit metadata (stage 2), it also embeds:
- `members` — every covered Member (owner + additional, #374), via the existing `MEMBERS_SELECT`.
- `billing_policy` — the plan's `billing_policies` row (the Billing frequency `recurring_billing_*` + auto-renew; the initial/service interval pairs were retired by migration 189, #635 stage 13).
- `promotions` — applied promotions with their stage-2 snapshot overlay, via the same `fetchAppliedPromotions()` also used by `GET /:id/promotions`.
- `additional_services` — the Additional Periodic Services attached to the assignment (#631, below).
- `billing_events` — the Billing Events view (below).

`GET /user-memberships/:id/billing-events` exposes that last section on its own (a lighter, single-section fetch), computed by the same `computeBillingEventsView()` the `:id` response embeds it from.

**Billing Events range rule** (per the #511 issue thread's Q2 answer, implemented in `domain/assignedPlanBillingEvents.ts` — pure, unit-tested, no DB dependency): show all billing events affected by a promotion applied to the plan, plus the events covering the following two calendar months after the last one; with no applicable promotion, the next two calendar months from the plan's `starts_at`. Clamped to `ends_at` when the plan ends first.
- **`draft`** plans never write to `billing_events` — the view is a non-persisted projection from the plan's recurring billing cadence (`billing_policies`) and its currently-applied promotions' Membership Fee benefits, capped at 36 months out as a safety net for an indefinite (no `duration_months`, never-revoked) promotion, which would otherwise push the range forward forever.
- Every other status queries the real, persisted `billing_events` ledger and only ever tags (`promotion_affected: true/false`) and filters it — amounts are never recomputed, preserving historical values.
- The response's top-level `projected: true/false` (and per-event on the draft path) lets the frontend distinguish a draft's preview from a submitted plan's persisted events.

`user_membership_promotions.revoked_at` (nullable `DATETIME`, migration 150) is stamped when a promotion is revoked (`DELETE /user-memberships/:id/promotions/:promotionId`) — together with `applied_at`, it defines the `[applied_at, revoked_at]` window used to tag whether a given billing event (or projected cycle) was affected by that promotion, independent of the row's `status`. Migration 150 also adds a `billing_events (user_membership_id, created_at)` composite index, since the range calculation reads every ledger row for one membership ordered by `created_at`.

The Close action's unused-value check warns on a pending `next_billing_date`. #511 stage 3 also warned about a `session_count` allowance with sessions left in its window; #635 stage 4 (part 2) retired Included Services, so that half is gone — a Plan's Session Benefits are billed up front rather than consumed per booking, so closing forfeits nothing.

### Additional Periodic Services (#631, migration 164)

`user_membership_services` attaches recurring Sellable Items (`gym_charges`) directly to an Assigned Plan (`user_memberships`) — independent of the Membership Plan's included benefits and of Promotion benefits (#631 §7), which keep their own tables. The Sellable Item stays the source of truth for the name, price and `billing_frequency` (read live on every request, never copied onto the attachment), so the table stores only the assignment-specific facts: `gym_charge_id`, `quantity`, `starts_at` and `ends_at`. `gym_charge_id` has no `ON DELETE CASCADE` (the same reasoning migration 130 used for the charge-benefit snapshot, retired in stage 4): items are only ever soft-deleted, and an attached service must survive one being retired — a service whose item was later retired keeps billing and is flagged `sellable_item_retired` on read. A `VIRTUAL` generated column (`open_service_key`, non-NULL only while `ends_at IS NULL`) carries a unique key, so two concurrent POSTs can't both slip past the overlap check and leave the same item attached twice.

Routes (mounted at `/user-memberships/:id/services` in `app.ts` — three path segments, so `userMembershipsRouter`'s own `/:id` never matches — behind the same `PAYMENTS` gate and `payments.transactions` flag as the rest of Assigned Plans):
- `GET /user-memberships/:id/services` — the attached services, oldest window first. Also embedded in `GET /user-memberships/:id` as `additional_services`.
- `POST /user-memberships/:id/services` — attaches one. Only items `classifySellableItem()` (#550) classifies as `periodical` are accepted, and only while the plan still bills (`draft`/`awaiting_payment`/`active`/`paused`); `starts_at` defaults to today, or to the plan's start date when the plan hasn't started yet, and can never precede it. Attaching an item that already has an open window on the same plan is a 409 — quantity is what expresses "two of them".
- `DELETE /user-memberships/:id/services/:serviceId` — **future-only removal** (#631 §3): it stamps `ends_at = today` instead of deleting, so charges the service already produced stand and only future ones stop. A service whose billing has not started yet (`starts_at` in the future) is deleted outright — an `ends_at` before `starts_at` would violate `chk_ums_ends_at`.

The Billing Simulation projects each attached service as its own stream (below). The admin frontend renders `ADDITIONAL PERIODIC SERVICES` as inline row CRUD with no modal (`[locale]/financials/assigned-plans/AdditionalPeriodicServices.tsx`), in the Assigned Plan expanded row and in the Member page's current plan card — where an add/remove also remounts the Billing Simulation, so it recalculates immediately (#631 §6).

### Assigned Plan snapshot (#635 stages 2–3 + 6–13, migrations 174, 183, 184, 185, 186 and 189)

An Assigned Plan owns the commercial configuration it was assigned with, so a later edit to the Membership Plan, a Promotion or a Sellable Item can never move an assignment that already exists (#635 §11–§17). What is captured, all inside the assignment's own transaction:

- **On `user_memberships`** — `free_months` / `paid_months` / `bonus_months` / `pay_beforehand_months` (the Plan's Billing & Duration, migrations 173 and 189), `recurring_billing_interval` / `recurring_billing_unit` (the Plan's `billing_policies` cadence) and `membership_fee_price` (the *regular*, pre-Promotion fee: the price window covering the start date). A Plan with no price window leaves it `NULL`. Since #635 stage 15 it is also where a **negotiated** fee lives — `final_price`, the separate "agreed price after promotions and discounts" column, is gone (migration 191), so an assignment stores one price and every cycle is resolved from it.
- **`user_membership_session` / `_oneoff` / `_periodical`** — the assignment's copy of the Plan's three benefit sections, each row carrying `quantity` plus the item's `item_name`, `item_type`, `item_billing_frequency`, `unit_price` and `currency` as they were. `gym_charge_id` has **no** `ON DELETE CASCADE` (unlike the Plan-side tables of migration 173): the row is the historical record, so it outlives a retired item — same reasoning as migrations 130 and 164.
- **`user_membership_promotion_{session,oneoff,periodical}_snapshot`** — created empty by migration 156 and finally written here, when a Promotion is applied (`snapshotPromotionGrants()` in `membership-promotions.ts`). Migration 174 adds the pricing columns they lacked; a name and a quantity cannot reproduce a charge.
- **`user_membership_services`** — Additional Periodic Services gain the same five snapshot columns, captured at attach time. `NULL` marks an attachment made before migration 174.

`api/src/api/assigned-plan-snapshot.ts` owns the write (`snapshotAssignedPlan()`, called from all three assignment entry points: `POST /user-memberships`, `POST /user-memberships/:id/assign-new-plan`, `POST /membership-plans/:id/assign`) and the read (`loadAssignedPlanSnapshot()`, embedded in `GET /user-memberships/:id` as `snapshot`). `snapshot_captured: false` marks an assignment that predates the migration and has nothing to read back.

**Editing the snapshot (stage 6, no migration).** §9/§10/§15: the Assigned Plan exposes the Membership Plan's own structure and each section is saved on its own, against *this* assignment:

- `PUT /user-memberships/:id/billing-duration` — the six `user_memberships` snapshot columns. Only the keys present in the body are written (so one section's editor can leave the others alone), a blank clears back to `NULL` ("not configured", distinct from `0`), and the cadence is validated as a pair: half of one would let `ASSIGNMENT_CADENCE`'s per-column `COALESCE` mix the assignment's interval with the Plan's unit.
- `PUT /user-memberships/:id/fee-benefit` (#772) — the **Personal Membership Fee Benefit**, `{action, value}` replace-all. See its own section below; it is edited here but it is *not* part of the snapshot, so it is the one section editor that does **not** materialise.
- `GET`/`PUT /user-memberships/:id/{session,oneoff,periodical}-benefits` — the same replace-all `{items:[{gym_charge_id,quantity}]}` contract as the Plan and Promotion sections (the admin editors are shared), writing the assignment's own rows via `writeAssignedPlanBenefitSection()`. A line already in the section keeps the commercial facts it was captured with and only changes quantity — a *newly* added line freezes the Sellable Item as it is now, so editing one line never silently reprices its neighbours (§17); re-pricing a kept line is a deliberate remove-then-add. Only a new line is held to the catalogue (gym-owned, non-deleted, `active`, and of the section's category), so a line whose item was since retired stays saveable.

All three are `requireModuleWrite('PAYMENTS')` and refuse a `cancelled`/`expired` assignment — a terminal row bills nothing further, so rewriting what it was agreed at would only falsify the record. The first two call `materialiseAssignedPlanSnapshot()`: for an assignment with `snapshot_captured: false` the live values it resolves today are written down before the edit applies, because stage 3's fallback is all-or-nothing — the first edit would otherwise make the assignment "captured" and blank the sections it never mentioned. Since stage 3 these rows *are* what the assignment bills, so a saved section moves its Billing Simulation immediately; the Plan, its other assignments and the Sellable Items are untouched. Admin UI: `[locale]/financials/assigned-plans/AssignedPlanConfiguration.tsx` renders `BILLING & DURATION` above `ONE-OFF`, `SESSION` and `PERIOD BENEFITS` inside the expanded row, each with its own Edit/Save/Cancel and no modal (#627's section-at-a-time editing), reusing the shared `components/SellableItemBenefits.tsx` editor. Its read-only view shows each line's *frozen* unit price rather than the catalogue's, which is the difference from the Plan's own sections.

### Personal Membership Fee Benefit (#772, migration 192)

Everything else that changes what the Membership Fee costs is bounded in time: a Promotion's Membership Fee Benefit lives inside that Promotion's own Free/Paid/Bonus timeline and ends with it (#635 stage 12), and the Plan's Free / Pre-paid / Bonus durations are counted from `starts_at` and run out. This one is bounded by nothing — it belongs to the Assigned Plan, lasts its whole lifetime, and only an explicit edit changes or removes it.

- **Stored** as `user_memberships.personal_fee_benefit_action` (`VARCHAR(30) NOT NULL DEFAULT 'no_benefit'`) + `personal_fee_benefit_value` (`DECIMAL(10,2) NULL`). The action vocabulary is shared with the Promotion benefits so `applyPeriodBenefit()` stays the one place a pair becomes an amount, but `domain/personalFeeBenefit.ts` restricts *this* surface to the ticket's two options — `no_benefit` and `percentage_discount` — and `toPersonalFeeBenefit()` clamps whatever it reads to 0..100, because `user_memberships` carries no CHECK (migrations 174 and 189 declined one on that table: `ADD CONSTRAINT` rebuilds it under `ALGORITHM=COPY`).
- **Not part of the snapshot.** It is agreed with the member rather than captured from the catalogue, it has no live counterpart to fall back to, and its columns are NOT NULL with a default — so it is deliberately absent from the `has_billing_snapshot` expression and from `snapshot_captured`, and `PUT /:id/fee-benefit` does **not** call `materialiseAssignedPlanSnapshot()`. Folding it in would answer "captured" for every row in the table and freeze the duration fallback for assignments that never captured anything.
- **Not a negotiated price.** `membership_fee_price` is still the regular fee this contract discounts *from*, and `discount_reason` still marks a negotiated one. The two are separate decisions, so a percentage keeps following the fee if the fee is later renegotiated.
- **Read on every cycle** by `resolveMembershipFee()`, as the last step and via a required `personalFeeBenefit` on `MembershipFeeContext` — required so a new pricing path cannot silently forget it. Every fee surface therefore carries it: the Assigned Plans list and card, the Billing Simulation, the Billing Events projection, `GET /me/membership` and the nightly run.
- **Not carried across a plan change.** `POST /user-memberships/:id/assign-new-plan` leaves the successor at the column default: it is a different Assigned Plan, at a price renegotiated in the same request, so a percentage agreed against the old Plan's fee would apply a discount nobody agreed to the new number.
- Admin UI: a `MEMBERSHIP FEE BENEFIT` section in `AssignedPlanConfiguration.tsx`, between Billing & Duration and the three Sellable-Item sections, with the same Edit/Save/Cancel shape as its neighbours.

**The applied Promotions (stage 7, no migration).** §16: an applied Promotion is part of the agreement, so both what the card *shows* and what the assignment *charges* come from the application rather than from the Promotion's current definition.

- `fetchAppliedPromotions()` (`membership-promotions.ts`, shared by `GET /user-memberships/:id/promotions`, the expanded card's `GET /user-memberships/:id` and the Member configuration read) returns, per application: `applied_by_name` (resolved from `gym_memberships.user_id = ump.applied_by` as a subquery, so a staff member since removed still leaves the record readable), `display_status`, and `session_grants` / `oneoff_grants` / `periodical_grants` — the frozen Sellable Items, loaded through the same `loadPromotionGrantSnapshots()` the Billing Simulation uses, so the two can never disagree about what was granted. An application with no grant rows at all predates the snapshot flow and falls back to the Promotion's live benefits.
- `display_status` is decided by `domain/promotionApplicationStatus.ts` (pure, unit-tested): `inactive` once the application is no longer standing, `expired` while applied but past the end of its **agreed** window (the snapshot's `ends_at`, not the Promotion's current one), `active` otherwise. The issue thread also names "incompatible"; nothing can persist in that state, because a Promotion that does not stack with one already applied is refused at apply time.
- The fee resolution reads each applied Promotion's Membership Fee Benefit out of its own snapshot (`membershipFeeBenefitsFromSnapshot()`) instead of joining `promotion_membership_fee_benefits` live. That join was the last path by which editing a Promotion could still move an existing assignment's price: the fee is re-resolved on every read, so a Promotion repriced in between used to reprice everything already applied (§13). The `duration_months` gate stays in SQL (`applied_at + INTERVAL n MONTH > NOW()`, one round trip for the whole set) so month arithmetic still clamps the way it always did. Only a snapshot-less application still reads the Promotion's current definition — it has nothing else to read.
- Admin UI: `[locale]/financials/assigned-plans/AssignedPlanPromotions.tsx` renders one expandable card per application — checkbox, name, applied at, applied by, `StatusBadge` — which opens onto the agreed window, Billing & Duration, the Membership Fee Benefit and the three grant tables at their frozen prices. A revoked application reads as `inactive`: its checkbox is cleared and its card does not expand. Clearing a standing one's checkbox revokes it (`DELETE /user-memberships/:id/promotions/:promotionId`, behind a confirmation), which recomputes the price and moves the Billing Events section with it. Ticking a spent one back applies the Promotion again — see stage 9 below.

**Billing & Duration bills (stage 8, no migration).** §7 asks the Plan's Free Period / Paid Duration / Bonus Duration to use "the same semantics as the Promotion configuration"; stages 1 and 2 stored them and nothing read them, so a Plan sold with a free first month billed its full fee on day one. `api/src/domain/planDuration.ts` (pure, unit-tested) classifies a date as `free_plan` / `pay_plan` / `bonus_plan` / `pay_regular`, and the Billing Simulation waives the Membership Fee in the first and third, reporting it as a `source: 'membership_plan'` benefit line carrying the period. Three rules worth knowing:

- **The Promotion wins any overlap** — the thread's Q2 answer, *"in case of conflict, prioritize the promotion"*. Where an applied Promotion governs the date (inside its own timeline, or applying its Membership Fee Benefit) it decides the fee alone; the Plan's own period applies only where no Promotion does, including after one is revoked. Stacking them would also let a Promotion's *paid* month be overridden by the Plan's free one, which inverts the answer.
- **The periods are counted from the assignment's `starts_at`**, not from the first of its month the way `computePromotionTimeline` anchors a Promotion's illustrative preview — a plan starting on the 31st must not be free for 30 days it was never given. Every boundary is measured from that anchor in a single `advanceBillingDate` step, so its end-of-month clamping (31 Jan + 1 month = 3 Mar) cannot accumulate and put a later boundary before an earlier one.
- **Only the Membership Fee is waived.** The Plan's Period Benefits are still charged inside a free month, exactly as they are inside a Promotion's. The Paid Duration charges the regular price and produces no benefit line — it *is* the regular charge, so the horizon stops there unless a Bonus Duration behind it still has to be shown.

The durations are read from the assignment's own columns, with the Plan's live ones as the fallback for an assignment that captured no snapshot at all — the same all-or-nothing rule as the benefit loader, and for a sharper reason: the columns are nullable, so a per-column `COALESCE` would let a Free Period *added to the Plan later* start waiving an existing assignment's fee (§13). Nothing else changes: the nightly run charges `final_price` on its own cadence, as it does for a Promotion's free months too.

**A Promotion can be deselected and selected again (stage 9, migration 183).** The thread's Q2 answer asks for Promotions that are *"selectable and deselectable adjusting automatically the simulation"*. Stage 7 only revoked: `ump_unique_pair` (migration 022) reserved `(user_membership_id, promotion_id)` across every status, so a revoked application held the pair for good and a second apply answered 409. Migration 183 narrows the uniqueness to the applications that are still **standing** — a `standing_promotion_key` VIRTUAL generated column, non-NULL only while `status = 'applied'`, under a UNIQUE KEY (`ump_one_standing_per_promotion`), the same shape migration 164 gives Additional Periodic Services. The plain index `ump_membership_promotion_index` is created *before* the old unique key is dropped, because that key was also the index MySQL used for the `user_membership_id` foreign key.

- **`applied_at` and `revoked_at` share one clock.** Migration 022 defaulted `applied_at` to `CURRENT_TIMESTAMP` (the server's session time zone) while the revoke path stamps `revoked_at = UTC_TIMESTAMP()`. The two bound the same window, and since stage 9 a replacement application's `applied_at` is compared against the `revoked_at` of the one it replaced, so migration 183 moves the default to `UTC_TIMESTAMP()` — a non-UTC server would otherwise mis-tag which persisted charges a Promotion affected.
- **A re-apply is a new application, not a resurrection.** The row owns the snapshot of the Promotion it was agreed with (§16) and its `[applied_at, revoked_at]` window is what tags the Billing Events ledger (#511 stage 3), so reusing it would rewrite what the member was already billed under. The spent application therefore stays on the list as history, and the new one snapshots the Promotion **as it stands today** — a new agreement, made now, the same rule stage 6 applies to a newly added benefit line. A Promotion repriced between the revoke and the re-apply moves the new application only (§13 keeps it off the spent one).
- **Every eligibility rule stays on the apply path**, which is unchanged: the Promotion must be `active` and inside its own window, must target the Plan, must satisfy stacking, and must honour `only_applicable_for_new_members`. The one addition is an explicit "a standing application already holds this pair" check, so the database's unique key surfaces as a 409 with a message rather than as a duplicate-key error.
- **`can_reapply`** (per application, from `GET /user-memberships/:id/promotions` and the expanded card) is what the checkbox reads, decided by `canReapplyPromotion()` in `domain/promotionApplicationStatus.ts` (pure, unit-tested): the application must be `inactive`, no other application of the same Promotion may be standing, and the Promotion itself must be active and inside its window today. It is deliberately narrower than the apply path — stacking, plan targeting and new-member eligibility are not re-run on a read, and surface as the server's message if the apply is refused. Admin UI: ticking a spent card's checkbox confirms, then `POST`s to the apply endpoint; the confirmation says the Promotion is agreed as it stands today.

**The Member sees the snapshot too (stage 10, migration 184).** `GET /me/membership` — the Member app's My Membership page — was the last surface still reading an assignment's commercial configuration live. Its `BENEFITS` list came from `membership_plan_benefits` (migration 006's plan-keyed benefit vocabulary, joined to `benefit_types`), a table no code has written since it was created and which is keyed to the *Plan*, not to the assignment; its billing cadence came straight from `billing_policies`, so a Plan re-cadenced after enrollment moved the dates the member was shown. Both now resolve the assignment's own rows: the cadence through `ASSIGNMENT_CADENCE` (as every other billing query does) and the benefits through `loadPlanBenefitsForSimulation()`, so the Member reads exactly what the Billing Simulation and the nightly run bill — the Sellable Items the assignment carries, at the quantity, frequency and price frozen with them, with the Plan's live sections as the fallback only for an assignment that captured no snapshot at all. Migration 184 drops `membership_plan_benefits` (its last reader is gone); `benefit_types` stays, as a global vocabulary with its own read-only router. The member app renders the lines grouped one-off → session → period (`membership.benefit_group.*`) with each line's frozen price and frequency (`membership.frequency.*`), replacing the fixed `membership.benefit.<code>` label set. Nothing about what is *charged* moved at that stage: `upcoming_payments` still projected the stored agreed price, which is what the nightly run charged, only now on the assignment's own cadence.

**The nightly run stops charging a waived cycle (stage 11, migration 185).** Stage 8 made the Billing Simulation bill from the assignment's own Billing & Duration and stage 10 put the same numbers in front of the Member — but `POST /billing/run` still charged `user_memberships.final_price` flat, so a Plan sold with a free first month was shown €0 and charged for it that night. The run now resolves, for the date it is billing (`next_billing_date`, not "today" — a run missed for two days must still price the cycle it is settling), whether the fee is waived, through `priceDueMembershipFee()` in `api/src/api/billing-run-pricing.ts`. That function calls `resolveMembershipFee()` — the Billing Simulation's own resolver, exported for the purpose — so the run cannot disagree with what the member was shown, precedence rule included: where an applied Promotion governs the date it decides alone, and the Plan's Free Period applies only where none does. A waived cycle calls no payment provider and writes no `payment_requests` row; it records a **`waived_billing`** billing event (amount 0, `source = 'system'`, its `notes` naming the period: `free_plan`, `bonus_plan`, `free_promotion`, `bonus_promotion`) and advances `next_billing_date` exactly as a charged cycle would. `last_billed_at` deliberately does not move — nothing was billed. `POST /billing/run` answers with a fourth counter, `waived`.

Two things stage 11 left alone (stage 12 below closes the first). A cycle that is *not* waived was charged `final_price` — that column carries no date, so a Promotion's Membership Fee Benefit which had run out kept discounting later cycles. An assignment that captured no snapshot reads its **Plan's live** Billing & Duration, all-or-nothing, the same rule the benefit loader and the simulation apply (§13). And a €0 `final_price` is now treated as waived rather than sent to the provider as a zero-amount MIT charge. Supporting change: `advanceBillingDate` moved into its own leaf module, `api/src/domain/billingDate.ts`, because the run importing the engine would otherwise have closed an `api/billing → domain/billingSimulation → domain/planDuration → api/billing` import cycle; `api/src/api/billing.ts` re-exports it, so every existing importer is unchanged.

**One date-aware Membership Fee rule, everywhere (stage 12, migration 186).** The thread's stage 12 answer (a) — *a Promotion's own Free/Paid/Bonus months determine when its Membership Fee Benefit ends* — settles §16's last gap. Three code paths priced a fee and they disagreed: `final_price` (what the run charged) and `computeMembershipFeePriceAt()` (the Billing Events projection) applied the benefit for as long as the application stood, gated only by its own `duration_months`, while the Billing Simulation and My Membership stopped it at the end of the Promotion's timeline. For the same cycle the Member was *shown* one price and *charged* another, in both directions.

`resolveMembershipFee()` is now the only implementation of the rule, and everything asks it:

- `computeMembershipFeePriceAt()` delegates to it, and takes the assignment's own Billing & Duration, so a Free Period shows €0 in the Billing Events projection too. Its `promotionAffected` still means "an applied *Promotion* changed this charge" — the range rule (#511 Q2) extends from those events, and a cycle the Plan's own Free Period waives is the contract's regular shape, not a Promotion's doing.
- Applying or revoking a Promotion (`membership-promotions.ts`) resolves the cycle `next_billing_date` names — never a date already past, never before `starts_at` — instead of discounting a date-less number.
- `GET /me/membership` prices each of its two `upcoming_payments` on its own date (`computeUpcomingPayments`'s `priceOn` callback) rather than repeating one stored number, so the second can legitimately cost more than the first.
- `POST /billing/run` charges what the resolver returns for the cycle, not a stored price flat.

To make that possible without duplicating the rule, `MembershipFeeBenefit`, `AppliedPromotionForBilling` and `promotionCoversDate` moved into a new leaf module, `api/src/domain/promotionApplication.ts` (and `AppliedPromotionForBilling` now carries the Promotion's Free/Paid/Bonus months, because every caller needs them to bound the benefit). `domain/billingSimulation.ts` imports that instead of `domain/assignedPlanBillingEvents.ts`, which inverts the edge that had kept the two rules apart; both old modules re-export what they used to declare, so no importer changed. `regularMembershipFee()` likewise moved to `api/user-memberships.ts`, so the number every path discounts *from* has one chain as well: the assignment's frozen `membership_fee_price` → its Plan's `membership_plan_prices` window at `starts_at` → a non-zero `base_price`.

**It shipped switchable and off, and stage 15 removed the switch.** The correction *raises* the charge of a member whose promotional months already elapsed, which the thread asked not to let happen silently — so stage 12 gated the two writers that move money on a `billing.date_aware_membership_fee` feature flag seeded **disabled** (migration 186), and stage 14 gave the impact report a page of its own (**Payments → Membership Fee Drift**, its own `payments.membership_fee_drift` key, migration 190) so a gym admin could review what switching it on would change. Every read-only surface resolved dates through the rule regardless — showing the agreed timeline correctly charges nobody.

The thread's answer to that review was to stop switching it: *"please remove the billing.date_aware_membership_fee feature flag entirely, as well as the stored final_price approach. Date-aware Membership Fee pricing should be standard system behaviour, with pricing calculated dynamically in the Assigned Membership Plan simulation."*

**Date-aware pricing is standard, and nothing stores a price (stage 15, migration 191).** Both flag rows and `user_memberships.final_price` are dropped, the drift report and its page are deleted (empty by construction once nothing is stored to drift from), and the run's `drift` counter is gone with them. There is no second rule left to disagree with, and nothing to keep in sync at apply/revoke time — which is the point: `final_price` was a number with no date in it, recomputed only on mutation, so a Promotion whose months had elapsed kept discounting until someone happened to touch the assignment again.

What replaces it is one shared module, **`api/src/api/membership-fee-pricing.ts`** (the former `billing-run-pricing.ts`, renamed because it is no longer the run's private helper):

| Export | What it answers |
|---|---|
| `priceMembershipFeeOn(row, date)` | The fee owed on one date: `{ amount, waived, periodStatus }`, resolved through `resolveMembershipFee()` over the assignment's own regular fee, Billing & Duration and standing applications. |
| `priceMembershipFeesFor(rows, dateFor)` | The same over many assignments and dates, with one query for every row's applications — what a list page needs instead of N round trips. |
| `currentCycleDate(row)` | The date "what does this member pay **now**" means: `max(next_billing_date, today)`, never before `starts_at` and never a cycle already past. |
| `currentMembershipFee(gymId, umId)` / `currentMembershipFees(gymId, ids)` | That cycle's fee, for one assignment or a list. |
| `FEE_ASSIGNMENT_COLUMNS` / `FEE_ASSIGNMENT_FROM` / `loadFeeAssignment(s)` | The columns and joins any of the above needs, so no caller re-derives the snapshot/fallback SQL. |

Every surface that used to read the column now reports a computed **`membership_fee`** instead: `GET /user-memberships` and `/:id` (beside `snapshot.membership_fee_price`, the *regular* fee an edit writes), the create / renew / lifecycle responses, `POST /user-memberships/:id/promotions` and its DELETE, `GET /members/:id/membership-configuration`, `GET /me/membership`, and the Payments dashboard's projected rows — which are now priced **per projected date**, so a Free Period reads €0 and the cycle after a Promotion's timeline ends reads the regular price. A **payment request** (staff-raised, `POST /payment-requests`, or member-raised) asks for that same resolved number and is refused with 400 when the cycle owes nothing, rather than asking a member to pay for a cycle the run would waive.

Two knock-on changes worth knowing:

- **A negotiated fee lives in `membership_fee_price`.** There is no second column for it, so `POST /user-memberships` and `POST /:id/assign-new-plan` take `membership_fee_price` (with `discount_reason`, as before) in place of `final_price`, and freeze it through `snapshotAssignedPlan()`. `PUT /:id` no longer takes a price at all — editing one is a snapshot edit, which goes through `PUT /:id/billing-duration` so the snapshot is materialised first. `discount_reason` still marks an assignment as negotiated, which is what keeps `POST /membership-plans/:id/pricing/apply-to-assigned-plans` off it; a past `discount_expires_at` is the one case that reads the Plan's price window instead of the frozen number (`regularMembershipFee`'s `ignoreFrozenFee`). Migration 191 therefore runs **two** backfills before the `DROP COLUMN`, not one: the narrow *last-resort* pass (the fee is written from `final_price` only where the old chain would have returned `final_price` anyway, materialising an uncaptured candidate in full first), and a *negotiated-price* pass (#777) for an assignment created with a price override **before stage 15**, whose Plan had a price window covering `starts_at`: the override went to `final_price` while `membership_fee_price` took the **catalogue** price (from `snapshotAssignedPlan()`, or from migration 174's backfill for an older row), so without the second pass the member would be charged the catalogue fee from the first nightly run after the deploy. The pass keys on a non-empty `discount_reason`, a frozen fee that disagrees with `final_price` and a non-terminal status, and it deliberately **skips an assignment that ever had a Promotion applied, in any status**: a standing one has the discount baked into `final_price`, and a revoked one had `final_price` recomputed from scratch at the revoke (pre-stage-15 apply/revoke never started from the previous value — under the legacy rule it started from `base_price`, a constant 0), so the agreed number is in neither column and a `status = 'applied'` filter would have frozen a `0.00` as a 100 % override. Those rows keep the catalogue fee; the migration logs how many it left behind and `docs/go-to-production.md` lists them for a staff re-negotiation.
- **Pushing a Plan's price onto its assignments now writes `membership_fee_price`.** `apply-to-assigned-plans` wrote `base_price`/`plan_price_id`/`final_price`, none of which the resolver reads first — so under date-aware pricing it would have changed nothing an assignment bills. It materialises each affected assignment's snapshot (the write makes the row "captured", and the all-or-nothing rule would otherwise blank its benefit sections) and then moves the frozen fee.

The migration's backfill is deliberately narrow: `membership_fee_price` is written from `final_price` only where `regularMembershipFee()`'s chain would have returned `final_price` anyway — no frozen fee, no Plan price window covering `starts_at`, no positive `base_price`. Copying it more widely would freeze a *promotional* discount into the contract as its regular fee, which is the bug stage 12 existed to fix.

It cannot write that fee on its own, though, and that is the subtle part. `membership_fee_price IS NOT NULL` is one of the seven disjuncts that *define* `has_billing_snapshot`, and the fallback it turns off is all-or-nothing: setting it alone would flip an uncaptured assignment to captured, and its Free Period, Pre-paid and Bonus Durations, cadence and three Plan benefit sections would then read back as *nothing* instead of falling through to the Plan — a member inside a free month would start being charged for it. The two row sets overlap by construction rather than by accident: the rows migration 174's backfill left uncaptured are exactly those whose Plan had no durations, no billing policy *and* no price window covering `starts_at`, and that last condition is the one this backfill keys on. So 191 materialises an uncaptured candidate in full first — the same values `materialiseAssignedPlanSnapshot()` and 174 write, benefit rows included, with the candidate id set frozen in a scratch table because inserting those rows is itself a capture — and writes the fee on top. `api/src/test/billing-run-membership-fee.test.ts` pins the rule, so a future path that writes the fee alone fails there rather than in a billing run. Two operational consequences: `up()` is guarded on `hasColumn('final_price')`, because the `DROP COLUMN` commits implicitly and a retry must skip the statements that read it; and the materialisation is one-way — `down()` restores the column but those rows stay captured, which changes nothing they bill (the values are what they already resolved to live) but means the pair is not a round trip.

**Billing reads the snapshot (stage 3).** Everything that prices or schedules an existing assignment resolves its own row first and only falls back to the live catalogue when it has none: the Billing Simulation (regular fee, cadence, the Plan's three benefit sections, each applied Promotion's grants, each attached service's price), the nightly run in `billing.ts`, the Billing Events projection, the Billing Events page's scheduled rows, the Payments dashboard, the schedule advance after a settled payment and the webhook that stamps the first `next_billing_date`. The cadence half is one shared SQL fragment, `ASSIGNMENT_CADENCE` in `assigned-plan-snapshot.ts` (`COALESCE(um.recurring_billing_*, bp.recurring_billing_*)`) — every one of those queries therefore LEFT JOINs `billing_policies`, so a Plan whose policy is deleted no longer strands its assignments. The Plan-side benefit loader falls back to the live sections only for an assignment with no snapshot at all (`hasBillingSnapshot` false *and* no benefit rows), so a Plan that gained benefits after an assignment was made cannot reach it. **Stage 4 (part 1)** then retired Charge Benefits outright — `plan_charge_benefits` and `user_membership_charge_benefits` are dropped by migration 176, their endpoints and both payload fields are gone, and the #485 Plan Billing Forecast carries no benefit lines any more. Nothing billed off either table after stage 3, so no assignment changed what it charges. **Stage 4 (part 2)** retired Included Services: migration 177 drops `plan_allowances`, and the `allowances` / `activity_allowances` fields, the four `/membership-plans/:id/allowances` endpoints and the `INCLUDED SERVICES` section go with it. It was never commercial configuration — it was booking access — and the issue answered where that belongs: *"Activity type should flag [which] membership plans are enabled to attend [a] certain activity type"*. That relation already existed as `activity_type_eligible_plans` (#481, migration 139), so `activity-eligibility.ts` is now the only plan-based booking gate, and the check is configured from one side instead of two. Two things moved rather than disappeared: the plan **center coverage** check that shared the retired hook's file now lives in `plan-center-access.ts`, and the **class-package claim** (a member without a covering plan paying out of prepaid sessions) is made by the eligibility gate itself via `tryClaimPackageCredit()`. What genuinely goes away is the per-window `session_count` cap, which eligibility has no equivalent for and §1 forbade relocating. Existing assignments were backfilled from the live catalogue by migration 174 rather than deleted (the #635 Q3 answer permitted deleting them): the values captured are the ones those rows already resolved to, so nothing they bill changed. Benefit rows are copied only for assignments that still bill — a `cancelled`/`expired` one would otherwise be stamped with today's catalogue under the heading "what was agreed". Every copy of a Sellable Item's name and type resolves `COALESCE(gc.name, ct.name, …)` / `COALESCE(gc.type, 'other')`, because a *system* charge carries neither of its own (both `gym_charges` columns are nullable) and the snapshot columns are `NOT NULL`.

### Promotion eligibility — "Only applicable for new members" (#634 §3 — no migration)

`promotions.only_applicable_for_new_members` (`NOT NULL DEFAULT 1`, stored since #633/migration 163) is enforced from #634's follow-up on. The #634 thread defines "new" as *a member that books his/her first membership plan in 12 months* — a Member who left more than 12 months ago and comes back counts as new again.

- `api/src/domain/newMemberEligibility.ts` — pure, unit-tested, no DB. An Assigned Plan disqualifies its Member when it is **live** (`draft`/`awaiting_payment`/`active`/`paused` — the same list the configuration read and the simulation use), when it **started** on or after the cutoff, or when it **ended** (`ends_at`) or was **closed** (`closed_at`) on or after it. A row superseded by Assign New Plan carries neither end date (the supersede stamps only `status = 'expired'`), so it is dated by the assignment that replaced it — otherwise a membership renewed through that action for years would read as "new".
- `api/src/api/new-member-eligibility.ts` — reads the Member's own assignments (`user_memberships.member_id`; being *covered* by somebody else's family plan is not booking one) and applies the rule.

The assignment the Promotion is being applied to **never counts against its own Member**: a Plan is assigned first and its Promotions applied right after, so without that exclusion a brand-new Member would be disqualified by the very plan being configured. Enforcement points, all excluding it: `POST /user-memberships/:id/promotions`, `applyPromotionToMembership()` (assign-new-plan, `POST /membership-plans/:id/assign`'s best-effort auto-apply, `POST /payments/apply-promotion`) and #628's up-front `validatePromotionSelection()`, which takes the `member_id` and excludes nothing, because the assignment it validates for does not exist yet.

`GET /user-memberships/member/:memberId/configuration` reports the answer per Assigned Plan as `new_member_eligible`, which is what the `PROMOTIONS` picker disables an ineligible option on (a UX affordance — the API is the enforcement point). Since the column defaults to 1, every Promotion created before this carries the flag: test fixtures that are not about the rule set it to `0` explicitly.

### Billing Simulation (#629 stage 1 — no migration)

`GET /user-memberships/member/:memberId/billing-simulation` returns a read-only, **never persisted** forecast of what a Member will actually be charged: the concrete dates, the regular price, the Promotion/Benefit that changed it, and the resulting amount. It creates no `billing_events`, invoices, charges or payment records, and is recomputed on every request, so it always reflects the current configuration.

It is **Member-level and consolidated**, not per Assigned Plan (the #629 thread's Q4 answer): every simulated assignment of that Member contributes to one chronological simulation, which is the shape #634 asks for. The route is mounted separately in `app.ts` (three path segments, so `userMembershipsRouter` never matches it) behind the same `PAYMENTS` module gate and `payments.transactions` feature flag as the rest of Assigned Plans.

Split in two, the same way the Billing Events view is:
- `api/src/domain/promotionApplication.ts` — pure, no DB, no imports but `promotionBenefits`: what one **application** of a Promotion is (`AppliedPromotionForBilling` — its window, its Free/Paid/Bonus months, its Membership Fee Benefits) and `promotionCoversDate`. A leaf module so the fee rule and the Billing Events projection can share one definition (#635 stage 12); re-exported from `domain/assignedPlanBillingEvents.ts`.
- `api/src/domain/billingSimulation.ts` — pure, unit-tested, no DB. Resolves *regular price → promotion → benefit → actual charge* per event and groups events into sections (`one_off`, `year`, `month`, `four_weeks`, `week`, `session`, `other` — the first four in the order #629 §3 fixes; the rest exist because `gym_charges.billing_frequency` and `billing_policies` can produce them).
- `api/src/api/billing-simulation.ts` — the reads, plus the router. `loadPromotionApplications` (exported from `user-memberships.ts`, shared with the Billing Events range calculation) supplies each applied Promotion's window, duration and Membership Fee benefits.

Rules the engine implements:
- **Inputs** (#629 thread Q1): the membership price, one-off prices, periodic benefits, session benefits, the applied Promotions and (#631) the Additional Periodic Services attached to each assignment. Plan Charge Benefits are not an input: they were decommissioned entirely by #635 stage 4 (migration 176). Since #635 stage 3 every one of those is read from the assignment's snapshot, with the live catalogue as the fallback for a row that captured none.
- **Membership Plan benefits** (#635 stage 3): the Plan's One-off / Session / Period Benefits, frozen onto the assignment, are *charged* items — the Plan grants the member a locker, not a free locker. A Period Benefit is a stream at the item's own frequency, priced `unit_price × quantity`; the other two are a single line on the start date. A Sellable Item carried by both the Plan and an applied Promotion produces **one** merged stream (keyed on `gym_charge_id`), the Promotion covering periods or units of it — two streams would bill the same locker twice. A one-off/session grant covers up to the quantity the Plan bills and the remainder is charged (10 sessions with 4 granted = 6 charged); an item only a Promotion carries is covered in full, exactly as before.
- **Additional Periodic Services** (#631): one stream each, billed at the Sellable Item's own `billing_frequency` and price × quantity, from the later of the assignment's start and the service's `starts_at` to the earlier of the assignment's end and its `ends_at`. They are not Promotion benefits, so no benefit ever resolves against them — every occurrence charges the regular price, including inside a promotional period.
- **Regular Membership Fee**: `user_memberships.membership_fee_price`, frozen at assignment time (#635 stage 3); for an assignment without it, the Plan's `membership_plan_prices` window covering `starts_at`. There is no further fallback since #635 stage 15 — an assignment neither of those can price has no fee anyone agreed. `user_memberships.base_price` is *not* usable — `effectivePrice()` has snapshotted a constant `0` into it since `membership_plans.base_price` was dropped in migration 058.
- **Promotion periods** (#629 §5): each projected charge is classified through `computePromotionTimeline` (the same projection the Promotion screen renders) — Free and Bonus periods waive the fee, Pay/Prepaid periods apply the Membership Fee (Period) Benefit, and nothing applies outside the Promotion's own timeline — since #635 stage 12 that is the rule *everywhere*, `computeMembershipFeePriceAt` and the nightly run included, so a Promotion configured with no Free/Paid/Bonus months changes no cycle at all (its timeline is one open-ended Pay (regular) period, and #625 caps the benefit at free + paid + bonus = 0). `resolveMembershipFee()` is that single implementation.
- **The assignment's own Billing & Duration** (#635 stage 8, stage 13): its Free Period, **Pre-paid Duration** and Bonus Duration charge no Membership Fee (`source: 'membership_plan'`, `period_status: 'free_plan'` / `'prepaid_plan'` / `'bonus_plan'`), counted from `starts_at` by `domain/planDuration.ts` — a pre-paid month is one of the Paid Duration's months that was already paid up front (`pay_beforehand_months`, the Promotion's own column since migration 141), so it is labelled pre-paid rather than waived. A Promotion governing the same date decides the fee alone (§7 + the #635 thread's Q2 answer) — see "Assigned Plan snapshot" above.
- **The assignment's own Personal Membership Fee Benefit** (#772): a `percentage_discount` applied to the Membership Fee **last and on every cycle** (`source: 'personal'`, `period_status: null`). It stacks with everything above rather than competing with it — a Promotion that halves the fee and a personal 10% together charge 45% of the regular price — and it never expires, so the cycle after the Promotion's timeline ends still carries it. It deliberately does not mark a charge `promotional`: a benefit with no end would otherwise push the horizon below to its 36-month cap for every discounted assignment, and a cycle whose only benefit is the personal one *is* this contract's regular charge. See "Personal Membership Fee Benefit" above.
- **Granted Sellable Items**: `promotion_periodical` grants are projected at the item's own `billing_frequency` (4-week means 28 days, never a month), free for the granted number of periods and at the regular price afterwards; `promotion_oneoff` and `promotion_session` grants are a single line on the assignment's start date covering the granted quantity. Read from the `user_membership_promotion_*_snapshot` rows written when the Promotion was applied (#635 stage 3), keyed on `user_membership_promotions.id`; an application with no snapshot rows at all falls back to the live `promotion_session`/`_oneoff`/`_periodical` definitions, so editing or deleting a Promotion cannot move an assignment that has one (§16).
- **Horizon** (#629 §6 / thread Q3): every item is projected until it has been charged once at its *regular* price, and the whole simulation then runs to the latest of those dates — a yearly item pulls the monthly ones out with it. "Regular" means no Promotion governs the charge *and* none is still ahead of it: a paid promotional period with no benefit charges the regular price but is still inside the Promotion, and a charge that predates a Promotion applied mid-assignment comes before it. Since #635 stage 8 the assignment's own Billing & Duration counts the same way — a free or bonus month is never the regular charge, and a Paid Duration month is one only when no Bonus Duration follows it. Capped at 36 months, which sets `truncated: true` for a benefit with no end date. Charges a year or more after the item started carry `price_may_change: true`, flagging a possible annual price revision.
- **Statuses**: `draft`, `awaiting_payment`, `active` and `paused` assignments are simulated; `cancelled`/`expired` bill nothing further.

The admin frontend renders it as its own `BILLING SIMULATION` section of the Member expanded row (`[locale]/members/MemberBillingSimulation.tsx`) — never inside a Membership Plan card (#634 §13) — and remounts it whenever the Member's plans change.

### Member invite + auto-link flow (`members` + `me`)

Unlike Team, a `members` row is the record of truth (name, contact, plan, billing) whether or not the member ever gets portal access — invite is a separate, optional action layered on top, not part of creating the member. Portal state is derived from two columns, never a `status` enum: `clerk_user_id` (set once linked) and `invitation_id` (the pending Clerk invitation, if any).

1. Staff calls `POST /members/:id/invite` (also `admin`,`staff`) → Clerk sends an invitation email with redirect to the member app (`CORDEL_FITNESS_MEMBERS_URL`), and the returned invitation id is stored in `members.invitation_id`. 409s if the member already has a linked `clerk_user_id`.
2. `POST /members/:id/reinvite` resends it (only valid while `clerk_user_id IS NULL AND invitation_id IS NOT NULL`) and **overwrites** `invitation_id` with the new one — this matters because the old id is no longer revocable once superseded (see the Team reinvite note below for the bug this avoids).
3. `POST /members/:id/revoke-invite` cancels a pending invitation without touching the member record — for when staff invited someone by mistake or changed their mind, but the member stays on the roster.
4. Member signs in via Clerk in `apps/member`.
5. On first sign-in the app calls `POST /me/link` (no `gym_memberships` row yet) — backend matches by email + gym_id (requiring `clerk_user_id IS NULL AND deleted_at IS NULL`), sets `members.clerk_user_id`, clears `invitation_id`, and inserts `gym_memberships(role='member')`.
6. Subsequent requests use `/me/*` routes with `tenantContext` resolving the member role.

**Orphaned Clerk accounts (#709).** A Clerk login is *linked* to Gymdesk when it is a superadmin (`publicMetadata.platform_role`), has a staff `gym_memberships` row (any role but `member`), or has an **active** `members` row (`clerk_user_id`, `deleted_at IS NULL`); a member-role `gym_memberships` row on its own does not count. That single definition lives in `infra/clerk-account-links.ts` (`loadAccountLinks`, pure `classifyAccount`, `unlinkClerkAccount`) and is used by all three places that could otherwise leave an account linked to nothing:
- **`DELETE /members/:id`**: when the member's login has no other link, the Clerk user is deleted **first** (502 and no DB change if Clerk fails, mirroring staff `revokeAccess({ deleteClerkUser: true })`), then this gym's member-role `gym_memberships` row is removed and `members.clerk_user_id` nulled; the same unlink happens when Clerk no longer has the account. A login still linked elsewhere (staff in another gym, superadmin) is kept **and the member stays linked to it**, so a Recycle Bin restore (`POST /recycle-bin/member/:id/recover`) reconnects them as before; a member whose login was deleted is restored unlinked and invited again.
- **Clerk `user.deleted` webhook** → `unlinkClerkAccount(userId)`: every `gym_memberships` row for the user is deleted and `members.clerk_user_id` nulled (rows kept). Idempotent, so the echo of our own deletes is a no-op. Audited with `gym_id` NULL, source `system`. The event must be enabled on the Clerk webhook endpoint.
- **`/platform/orphaned-accounts`** (superadmin, *Cordel → Orphaned accounts* in the admin): `GET` pages through every Clerk user (`getUserList`, 500 per call) and returns the unlinked ones with a reason (`member_deleted`, `signup_incomplete`, `signup_in_progress`, `no_links`) and the gyms they used to belong to; `DELETE /:userId` re-classifies (409 if linked, or a sign-up younger than 24 h), deletes in Clerk first, then `unlinkClerkAccount`, audited as `clerk_account` via `recordPlatformAudit` (`infra/audit.ts`, the gym-less audit writer).

Every FK to `gym_memberships.id` is `ON DELETE SET NULL` or `CASCADE` (checked for #709), so removing member-role rows never fails on a reference.

**Removing a member with a pending, not-yet-accepted invitation revokes it.** `DELETE /members/:id` (soft-delete) checks `clerk_user_id IS NULL AND invitation_id IS NOT NULL` before setting `deleted_at`, and best-effort calls `clerkClient.invitations.revokeInvitation()` first (a revoke failure doesn't block the soft-delete) — same race this closes as the Team flow: `/me/link` already refuses to link into a soft-deleted (`deleted_at IS NOT NULL`) row, so without the revoke the only leftover risk was an orphaned, still-valid Clerk invitation email and a wasted invitation slot, not an actual access breach. Revoking it is cleanup, not a security fix, in this case — the DB-level `deleted_at` guard was already sufficient. This still depends on the Clerk instance being in **Restricted mode** (see "Auth (Clerk)" above) to stop a fresh, uninvited self-registration with the same email.

### Website self-registration (`public-registrations.ts` + `website-integration.ts` + `me`) — #599, #645

The one **write** route under `/public`: `POST /public/gyms/:gymRef/registrations` lets a gym's own website (WordPress — setup in `docs/wordpress-integration.md`) register a person by `{ name, email, locale? }` — to the **gym** only: no center (#757; a `center_id` sent by an older site is dropped by the schema, not rejected). It has no Clerk session; it is authenticated by a **per-gym API key** in `x-api-key` and is meant to be called server-to-server, so the key never reaches a browser and the API needs no CORS.

- **Key storage.** `gyms.website_api_key_hash` (salted scrypt, stored as `scrypt$<salt>$<digest>`), `website_api_key_prefix` (first 12 chars — shown in the UI) and `website_api_key_created_at` (migration 159). `infra/website-api-key.ts` generates/hashes/verifies (`timingSafeEqual`). scrypt is slow by design and this runs on an unauthenticated route, so `verifyWebsiteApiKey` compares the stored prefix **first**: a caller without the key never reaches the digest, and junk traffic cannot burn CPU. (A fast hash would be cryptographically sufficient for a 256-bit random key; scrypt is what CodeQL's `js/insufficient-password-hash` accepts, and the pre-filter makes it free.) Managed by an admin at **System → Website Integration** via `GET /system/website-integration`, `POST …/key` (generate or rotate — returns the plaintext key **once**) and `DELETE …/key`; SYSTEM module, feature flag `system.website_integration`, audited as `website_api_key`. Gym rows are read with `SELECT g.*` in `gyms.ts`, so `stripGymSecrets` there drops the hash from every response and audit payload — **any new secret column on `gyms` must be added to it.**
- **No `members` row at request time.** The handler only creates a Clerk invitation carrying `publicMetadata.gym_signup = { gym_id, name }` (plus `lang` for `ca`/`en`, #701) and the usual `…/<locale>/link?gym_id=` redirect. Clerk copies that metadata onto the new user, and `POST /me/link` — when no unlinked `members` row matches and `gym_signup.gym_id` equals `x-gym-id` — creates the `members` row (with **no** `member_centers` row — #757; a `center_id` left in older invitations' metadata is ignored) and `gym_memberships(role='member')` in one transaction, returns 201, then clears the metadata. The metadata is server-set, so it is the proof that our backend invited that email to that gym. A fake request therefore costs one unused invitation and never reaches the roster. If staff had already added the person (unlinked, never invited row), the endpoint behaves like the staff **Invite** button instead: no metadata, `members.invitation_id` stored.
- **Gym reference (#645).** `:gymRef` is `{gymId}-{gym-name}`: `parseGymRef` takes the leading `CHAR(36)` UUID and resolves the gym **by id**, so two gyms with the same name can never share an endpoint and a rename never breaks a configured website (the name half is never matched against anything). A reference that doesn't start with a gym id falls back to `gyms.slug`, the pre-#645 format, so WordPress installs configured before the change keep registering; the only way the two forms could overlap is a slug shaped like a UUID followed by a hyphen, which slugified gym names don't produce. `website-integration.ts` builds the advertised URL in one place (`gym_ref` / `endpoint_path` / `endpoint_url`), URL-encoding the name half because a slug set by hand is not guaranteed to be URL-safe.
- **Health check (#645).** Exactly `{ name: 'test', email: '' }` is a connectivity probe, not a registration: after the key check and gym resolution it answers `200 { ok: true, health_check: true }` and returns before validation — no member, no invitation, no email, nothing written. It is recognised by `isHealthCheckBody` (trimmed, case-insensitive name; empty email), which cannot collide with a real registration because the schema requires a non-empty email — the name `test` with a real address is a normal `202`. A probe skips the per-gym daily limiter (it writes nothing, so it must not spend a gym's registration quota) but not the per-IP one.
- **No enumeration.** Once the key and body are valid the answer is always `202 { ok: true }` — for a new email, a staff login (#594 guard, `isStaffLoginEmail`), an already linked/invited/soft-deleted member, an email on another gym's member record (`members.email` is unique platform-wide), or a Clerk `422` (invitation pending / account exists). Swallowing the `422` is also the per-email throttle: a repeat request sends no second email. Unknown gym reference and wrong key share one `401`. `400` is reserved for caller mistakes (invalid body), `502` for a Clerk outage.
- **Flood protection.** A per-IP limiter runs before any DB work (`PUBLIC_REGISTRATION_IP_LIMIT_PER_HOUR`, default 60) and a per-gym limiter runs **after** the key check (`PUBLIC_REGISTRATION_GYM_LIMIT_PER_DAY`, default 200) so only authenticated calls spend a gym's quota. CAPTCHA belongs on the website's form, not in the API — a platform-wide Turnstile secret would have to enumerate every gym's domain, and the key already proves the caller is the gym's server.
- **`trust proxy`.** The API runs behind nginx, so `app.ts` sets `trust proxy` to `TRUST_PROXY_HOPS` (default `1`). Without it `req.ip` is the proxy's address for every request and every per-IP limiter — including the global 500/15 min one — collapses into a single bucket shared by all clients.
- **Known limits (v1).** An email that already has a Clerk account gets no email (Clerk refuses to invite existing users — same as the staff Invite button), and the website cannot trigger a resend while an invitation is pending.

### Staff app access (`staff.ts` + `infra/staff-access.ts`) — #592

The **Staff** page is the only place an admin manages who can sign in to the admin app. The old Team page (`gym-users.ts`, `/team`, `/link-team`) was dropped from navigation in #77 and removed entirely in #592; its invite/grant/revoke mechanics moved, behavior intact, into `api/src/infra/staff-access.ts` (`grantAccess`, `resendInvitation`, `revokeAccess`, `linkGymInvite`).

Every Staff record owns at most one `gym_memberships` row in its gym via `staff.gym_membership_id`. The RBAC role is **derived from the HR `profile`** through `PROFILE_ROLE_MAP` in `infra/permissions.ts` (Gym Manager→`admin`, Personal Trainer→`trainer_performance`, Personal Trainer & Nutritionist→`trainer_perf_nutrition`, Front Desk→`front_desk`, Accountant→`accountant`, Nutritionist→`nutritionist`); an unknown profile is a 400. There is no separate role picker — changing a profile changes what the person can access.

- `POST /staff` (active employee) → `grantAccess`: if Clerk already knows the email, insert/update the membership row (status `active`, `name` = first + last, `COALESCE(?, name)` on update — #504); otherwise create a Clerk invitation carrying `publicMetadata.gym_invite = { gym_id, role }` and insert an `invited_<ts>` placeholder row. The link is stored immediately in both cases. A Clerk failure does **not** roll back the staff row — the 201 carries `access: { status: 'error', error }` and the admin retries from the row. An employee created `inactive` gets no login (`access.status = 'not_enrolled'`).
- `PUT /staff/:id` → the login follows the record: profile change syncs `gm.role` (self-edit and last-admin guards → 400, same as the old Team role edit), name change syncs `gm.name`, and a changed email on a still-pending invite revokes the old invitation and issues a new one. **Save also keeps login and status in step:** an `active` record with no login gets one exactly as on create (records that predate #592 heal on their next save; re-activating restores the login), and saving a record as `inactive` removes its login like `PATCH /deactivate`. The response carries `access` whenever a login was granted or removed; the form warns before saving that an invitation email may be sent.
- `PATCH /staff/:id/deactivate` → `revokeAccess({ deleteClerkUser: false })`: pending invite revoked (best-effort) / membership row deleted, Clerk account kept; `gym_membership_id` cleared. Re-activation just needs *Send invitation* again.
- `DELETE /staff/:id` → `revokeAccess({ deleteClerkUser: true })`: as above, plus the Clerk user is deleted when this was their last gym membership anywhere — that delete must succeed first (502 otherwise), so a failure never orphans the account.
- `POST /staff/:id/access` → idempotent retry/resend: not enrolled → grant/invite (201); pending → resend and **overwrite** `invitation_id` (the superseded id is no longer revocable, so a later revoke must target the live one); active → `{ status: 'already_granted' }`.
- `DELETE /staff/:id/access` → revoke only, staff row untouched (204).
- `POST /staff/link` (mounted before `tenantContext`, like `/me/link`) → `linkGymInvite(userId)`: on the invitee's first sign-in the admin app's `GymContext` self-heal calls it; it flips the placeholder row to the real Clerk `user_id` (the Staff link keeps pointing at the same row) and clears the metadata. The Clerk `user.created` webhook calls the same function so activation happens whichever fires first.

**One email is never both member and staff of the same gym (#594).** A staff member signs in with their work account; if the same person is also a member, that membership lives on a separate personal account. Because `gym_memberships` holds a single role per `(user_id, gym_id)`, letting both flows write it would silently flip the role and break whichever app lost (every `/me/*` route is `requireRole('member')`; `/me/link` can't recreate a deleted member row because `clerk_user_id` is already set). So both sides refuse with **409** instead: `assertNotMemberEmail` (staff side — active `members` row on that email in the gym, or the Clerk account already holding a `member` row there) runs in `POST /staff` **before** the insert, on `PUT /staff/:id` when the email changes, and inside `grantAccess`; `isStaffLoginEmail` (member side — a Staff record with a linked login, or a pending staff-invite placeholder on that email) guards `POST /members` and `POST /members/:id/invite`; and `POST /me/link` refuses when the signing-in account already holds a non-member row in the gym (this also covers logins with no Staff record, e.g. the gym owner). Messages: `MEMBER_EMAIL_CONFLICT` / `STAFF_EMAIL_CONFLICT` in `staff-access.ts`.

`GET /staff/:id/clerk-status` is unchanged and drives the row's **App access** section (`not_enrolled` / `invited` / `active` / `suspended` / `error`). All access mutations are audited under the existing `gym_user` entity (the audit registry entry stays for historical rows).

**Removing an invited (not-yet-accepted) user is a revoke, not a delete.** This closes a race: an admin invites someone, then removes them before they click the email link — without revocation, the `gym_memberships` row would be gone from the app but the Clerk invitation would still be live, so accepting it later would silently recreate access. `revokeAccess` therefore calls `clerkClient.invitations.revokeInvitation(invitation_id)` before deleting a pending row (best-effort — a revoke failure doesn't block the row deletion).

Revoking the invitation closes the race for the *link itself* (Clerk shows "The invitation was revoked" if they click it), but does **not** by itself stop that email from just self-registering fresh at `/sign-up` — that's a separate, instance-wide Clerk setting, not something this endpoint can control. See "Required Clerk instance setting: Restricted mode" above; with it enabled, sign-up requires a currently-valid invitation, so a revoked one is rejected outright instead of letting a brand-new, gym-less account through.

## Audit Logging (`infra/audit.ts` + `audit_logs`)

`recordAudit(req, { action, entityType, entityId?, entityName?, previous?, next? })` is a **fire-and-forget** writer: it never fails the calling request (a rejected INSERT just logs to `console.error`). Each row is a self-contained historical snapshot:

- **`actor_name`** — display name captured from the Clerk user object already fetched in `tenantContext` (zero extra queries). Populated on every write; survives later Clerk user renames.
- **`entity_name`** — resolved by `infra/audit-registry.ts` at write time. Named entities (those with a `name` column) use a registry lookup; M-N/link entities (e.g. `user_membership`) get a composed label from their FK parents. Callers may pass `entityName` directly to skip the lookup. The UI shows "Unknown" (translated) when the field is null.
- **FK enrichment** — `previous_values`/`new_values` are enriched before storage: `foo_id: value` becomes `foo: { id, name }` using the FK map in `audit-registry.ts`.

The registry (`AUDIT_ENTITY_REGISTRY`) and action list (`AUDIT_ACTIONS`) are served by `GET /audit-logs/meta` for frontend dropdown population. High-value mutations call `recordAudit` after the business write; `class-types.ts` and `promotions.ts` were added in #69.

**A new `entityType` belongs in the registry, not only in the `recordAudit` call.** An unregistered type still writes rows, but they resolve no `entity_name` and the type is absent from `GET /audit-logs/meta` — so the Audit Log's entity-type dropdown cannot show it, and a Details view deep-linking to it (below) lands on a filter whose select has no matching option. #675 registered the nine types the Details views needed (`activity_type`, `theme`, `tax_rate`, `gym_charge`, `professional_service`, `nutrition_library_item`, `nutrition_plan_template`, `member_nutrition_plan`, `staff`).

Two read views share one endpoint and one React component (`AuditLogView`): **System → Audit log** (`/audit`, admin+) is scoped to the active gym; **Cordel → Audit log** (`/cordel/audit`, superadmin) sends `?scope=all` to see every gym's events with a Gym column joined in (#66). Filters: `entity_type` (dropdown), `entity_id` (exact match), `entity_name` (LIKE on stored snapshot), `actor` (name LIKE or Clerk ID exact), `action` (dropdown), `source` (dropdown), `from`/`to` date range.

`entity_type`, `entity_id` and `entity_name` are also read from the query string on mount, so any page can deep-link to one record's history — the Members → Details modal's **View Audit Log** button opens `/{locale}/audit?entity_type=member&entity_id=<id>` (#642). Link by id, never by name: `entity_name` is a snapshot and is neither unique nor stable. The `entity_id` filter is served by the existing `(gym_id, entity_type, entity_id)` index.

**Every** Details view offers that deep link (#675), through one component — `apps/admin/src/components/ViewAuditLogButton.tsx`. It owns the permission rule (superadmin, or a gym `admin` with the `system` and `system.audit` flags on — the same rule the sidebar applies, re-checked in `AuditLogView` and in the API) and the URL shape, and renders nothing when the viewer may not read the log or the record has no id. `scope="platform"` targets `/cordel/audit` instead of `/audit`, for entities administered outside a single gym (Gyms, base Themes, the Cordel Nutrition Library); `size="small"` suits an inline expanded row rather than a modal footer. In a `CrudModal` it goes in `extraFooter`. Its label is `common.action_view_audit_log`. See `docs/feature-patterns.md` → *Details view → View Audit Log*.

## Frontend Patterns

Both frontends follow the same proxy + context pattern. The admin app uses `GymContext`; the member app uses `AppContext`.

### API calls
All requests go through `apiFetch()` (from `useApiClient()`), which:
1. Gets a fresh Clerk token.
2. Attaches `Authorization: Bearer <token>`.
3. Attaches `x-gym-id: <activeGymId>`.
4. Hits `/api/proxy/<path>` → Next.js proxy route → backend. The proxy MUST stay on the Node runtime (no `runtime = 'edge'`). The API has no CORS — it is reachable only through these proxies. The proxy target is `CORDEL_FITNESS_API_URL` (deployed: `https://api.vdicube.com`; local dev: `http://localhost:3000`).

**Header allow-list gotcha (#362)**: the proxy route (`app/api/proxy/[...path]/route.ts` in both `apps/admin` and `apps/member`) only forwards headers on an explicit allow-list (`authorization`, `x-gym-id`, `x-center-id`, `x-impersonate-as`, `content-type`). Any new request header the frontend needs the backend to see (e.g. a future context header) must be added to this allow-list in **both** apps' proxy routes, or it is silently dropped and the backend never sees it — this is exactly what broke impersonation end-to-end until #362 fixed the member app's proxy.

Available via `useGym()`. Key fields:

'superadmin' : (activeGym?.role ?? 'member')` — `isImpersonating` from `useImpersonation()`. ### Theming (`ThemeProvider` + per-gym `theme_id`)

**Two tiers of themes (migration 065):**
- **Base Themes** — `gym_id IS NULL`. Platform-owned, managed by superadmins via **Cordel → Base Themes**. Never duplicated into customer data. Exactly one Base Theme carries `is_system_default = 1` (migration 072) — the factory default assigned when a new organization is created.
- **Customer Themes** — `gym_id = <gymId>`. Gym-owned, created by cloning any Base or Customer Theme. Editable and soft-deletable by gym admins via **System → Themes**.

Each gym references an optional **Theme** entity (`gyms.theme_id`, migration 057, FK on `themes.id`). Themes carry a versioned `tokens` JSON column (`v: 4` as of migration 157) covering typography (5 levels × `fontFamily` + `color`) and 33 named colors grouped as: **Application** (`pageBackground`), **Cards** (`cardBackground`, `cardBorder`), **Text** (`textColor` — labeled "Primary Text Color" in the editor, `secondaryTextColor`, `mutedTextColor`, `sectionHeadingTextColor`), **Separators** (`separatorColor` — application-wide, distinct from `headerSeparatorColor`), **Inputs** (`inputBackgroundColor`, `inputBorderColor`), **Header** (`headerBackground`, `headerText`, `headerSeparatorColor`, `headerSeparatorHeight`), **Sidebar** (`sidebarBackground`, `sidebarText`, `sidebarSelectedItemBackground`, `sidebarSelectedItemText`, `sidebarHoverBackground`), **Navigation** (`dropdownBackground`, `dropdownText`, `dropdownHoverBackground`), **Buttons** (`primaryButton`, `primaryButtonText`, `secondaryButton`, `secondaryButtonText`), **Status** (`statusSuccess`, `statusWarning`, `statusError`, `statusInfo`), **Links** (`linkColor`, `linkHoverColor`). `sectionHeadingTextColor` (#558, migration 157) drives `--gd-section-heading-text`, used by the theme editors' own accordion section titles and the `ThemeColorsEditor`/`renderReadOnly` per-group headings (e.g. "APLICACIÓN") — the theme card's other two previously-hardcoded elements named in #558 (empty-state text, inner card dividers) reuse existing tokens instead of adding new ones: `mutedTextColor`/`--gd-text-muted` (same one `DataTable`'s empty-rows message already uses) and `separatorColor`/`--gd-border` (same one several other admin pages' inline-editor row dividers already use) respectively — per #558's own "do not introduce duplicate properties if an existing token can correctly control the same UI element" requirement. Validation (`validateTokens`/`defaultTokens`, `HEX_RE`, `FONT_STACKS`) lives in the shared `api/src/domain/themeTokens.ts` (#489 stage 1), used by both `api/src/api/themes.ts` (superadmin base themes) and `api/src/api/gym-themes.ts` (gym-admin customer themes). Covered by unit tests (`api/src/test/theme-tokens.test.ts`) and, for the actual HTTP round trip through both routers — including that a legacy/partial `tokens.colors` shape and an existing `tokens.advanced` map persist unchanged — by integration tests in `api/src/test/themes.test.ts`/`gym-themes.test.ts` (#489 stage 5). ~52 finer-grained design tokens (layout, shape, shadows, per-component colors, animations) live in the `advanced` JSONB map; the Admin theme editors no longer group them under a standalone "Advanced" section — each attribute's `group` (`apps/admin/src/lib/themeTokens.ts`'s `ADVANCED_ATTRIBUTES`) matches one of the color groups above (plus **Cards** and a colorless **Tables** group) so it renders inline with that component's colors (#489 stage 2). Most of them are still admin-editable but not applied to any CSS variable anywhere — a pre-existing gap noted during #489's audit and explicitly out of scope for stages 1–4 (wiring it would be redone once the Advanced section's fate was settled; #489 stage 2 already deleted the standalone Advanced section by redistributing these attributes into the per-component groups above). Two groups have since been wired: the six `calendar*` attributes (#559 stage 2, below) and the Cards group's `cardBorderRadius` (#677) — see **Card surfaces** below.

**Card surfaces (#677):** the Cards group's two settings now reach the cards. `cardBorder` was already written as `--gd-card-border`, but `cardBorderRadius` was editable and persisted while never reaching a CSS variable at all, so configuring the Card Border Radius did nothing; `applyTokens()` now writes it as `--gd-card-radius` through the exported `CARD_ADVANCED_VARS` map (same shape as `CALENDAR_ADVANCED_VARS`, falling back to `DEFAULT_ADVANCED` for a theme with no `advanced` map or a blank value, via the shared `cssLengthValue()`). Independently of the variable, most admin card surfaces restated a border colour (`#e2e2e6`, `#ececf0`, `#e0e0e8`) and a `borderRadius` of their own, so even the border colour only applied on the pages that happened to use the variable. All of them — every `cardStyle`/`cardSt` plus the inline list cards on Themes, Staff and Centers — now spread one shared `cardSurfaceStyle` from `apps/admin/src/components/ui.tsx` (`border` + `borderRadius` + `background`, each `var()` with its default token value as the CSS fallback); a highlighted or being-edited card overrides `border` on top of the spread and keeps the themed radius. The base ↔ custom relationship is unchanged: both kinds of theme are applied through the same `applyTokens()`, so a base theme's values paint the cards when it is the applied theme and a custom theme's values override them when it is. Frontend-only — no schema, API or validation change (`themes.tokens` is schema-less JSON and `validateTokens()` does not format-check `advanced`). One deliberate visual change: card surfaces that hardcoded `borderRadius: 10` now follow the token, whose default is `8px`. Covered by `apps/admin/src/test/theme-card-css.test.ts` (variable emission for configured/legacy/blank values, the CSS fallback matching the default token, and a source scan asserting no card style declares a border radius of its own).

**Stage 2 — CSS variables + FullCalendar application (frontend only, no API or schema change).** `applyTokens()` writes one `--gd-calendar-*` variable per calendar token, driven by two exported maps (`CALENDAR_COLOR_VARS`, `CALENDAR_ADVANCED_VARS` in `apps/admin/src/lib/themeTokens.ts`, mirrored in `apps/member/src/lib/themeTokens.ts`) that are the single source for the variable names — shared by `applyTokens()`, the stylesheet and the tests. Each key falls back to `DEFAULT_TOKENS`/`DEFAULT_ADVANCED`, so a theme saved before #559 (no calendar keys at all) still resolves the full variable set. The only consumer is `components/CalendarThemeStyles.tsx` — a `<style>` block rendered inside the calendar page (same in-body pattern as `Toast`/`AppShell`, which also puts it after the stylesheet FullCalendar injects into `<head>`, so equal-specificity rules win on document order). Where FullCalendar v6 exposes a variable of its own the token is mapped onto it (`--fc-border-color`, `--fc-page-bg-color`, `--fc-today-bg-color`, `--fc-highlight-color`, `--fc-non-business-color`, and the six `--fc-button-*` entries), so one declaration covers every view and state; the surfaces FullCalendar hardcodes get an explicit rule (toolbar title, `.fc-col-header-cell`, month-view date numbers, other-month dates, the time axis and its cushions, slot height, weekend columns). Member Web reads the same tokens (it renders the same FullCalendar views off the same theme; the tokens are only ever *edited* in the Admin theme editors), so its `ThemeTokens`/`DEFAULT_TOKENS` gained the 16 calendar colors and its `CalendarThemeStyles` is a byte-identical copy of Admin's sheet, guarded by `apps/member/src/test/calendar-theme-css.test.ts`. Event colors were left to stage 3 (below). Covered by `apps/admin/src/test/theme-calendar-css.test.ts` (variable-map completeness, emission for configured/legacy/partially-configured themes, that the sheet consumes every variable it emits, that each CSS fallback equals the default token value, and that every selector is `.gd-calendar`-scoped).

**Stage 3 — event colors + the status pill badge (frontend only, no API or schema change beyond two more tokens).** An event's fill no longer encodes its status. Every event takes the theme's `calendarEventBackground`/`calendarEventBorder`/`calendarEventText`, and the booking status is carried by a pill-shaped badge rendered inside the event (`apps/admin/src/components/CalendarStatusBadge.tsx`) — the shape and palette the app's other status pills use (`StatusBadge`), at a size a calendar event can afford. This is #559's answer to the conflict with #541 ("event color depends only on `status`"): status still decides a color and nothing else does, it just paints the badge instead of the box, which is what frees the box to be themeable. `apps/admin/src/lib/calendarEventColors.ts` stays the single status → color mapping and now returns a `{ bg, fg }` pair per status, plus `full` — a status derived in the UI for a `scheduled` session whose bookings reached capacity, which takes the badge over `scheduled` as the more actionable of the two. The badge labels come from `calendar.status_*` (the raw uppercased DB value was shown before), with `status_full` added in en/es/ca. The admin calendar page stops setting a per-event `backgroundColor`/`borderColor`, since FullCalendar writes those as inline styles that would beat the theme. In the sheet, the tokens map onto `--fc-event-bg-color`/`--fc-event-border-color`/`--fc-event-text-color`, so one declaration each reaches `.fc-h-event`/`.fc-v-event` in every view; `--fc-bg-event-color` is a separate variable, so the greyed-out closed-hours blocks (#418) are untouched. Three rules are added on top: the event radius (which re-asserts FullCalendar's corner-flattening for continued multi-day events, since the radius selector is at least as specific), a hover background — FullCalendar has none of its own, hence the one default that isn't a FullCalendar built-in — and the selected/focused overlay, applied as the configured color at `opacity: .25` because the token is a plain color where FullCalendar bakes an `rgba()`. **Member Web is deliberately unaffected:** its events are colored by the session's *availability* to that member, set per event as an inline style that wins over these rules, so the event tokens only supply the base for an event that asks for no color of its own; the badge belongs to the Admin calendar, whose events convey a booking status. Event background/border default to `#6c63ff` — the purple `scheduled` events already had — so an unconfigured calendar still looks like the one admins had. Covered by `apps/admin/src/test/calendar-status-badge.test.ts` (no per-event inline color, the `--fc-event-*` mappings, background events left alone, the corner-flattening re-assertion and its ordering, the overlay weight, one badge per view, the badge holding no palette of its own, `full` winning over `scheduled`, and `status_*` translation parity) and by the reworked `apps/admin/src/test/calendar-event-colors.test.ts`.

**Stage 4 — accessibility pass (frontend only, no API or schema change).** Three things close the ticket's Accessibility requirements. (1) **A contrast report** in the Calendar section of both theme editors: `apps/admin/src/lib/calendarContrast.ts` scores each combination the eye actually has to separate (`CALENDAR_CONTRAST_PAIRS` — header/day/muted/time-axis/event/nav text against their backgrounds at WCAG AA 4.5:1, and the event box against the grid at the 3:1 non-text bar) with the WCAG 2.1 contrast formula, resolving each token the same way `applyTokens()` does so it scores what the calendar will paint. `CalendarContrastReport` in `ThemeTokensEditor.tsx` renders it under the section — **advisory only, never a save blocker**: a gym's branding is its own and the API-side `validateTokens()` stays a pure format check. The grid border and disabled-slot background are deliberately out of the pairs (decorative boundaries whose FullCalendar defaults sit below 3:1; scoring them would flag the stock calendar). The one shipped default that falls short is `calendarEventText` on `calendarEventBackground` (white on `#6c63ff`, 4.32:1) — kept because the ticket requires an unconfigured calendar to look unchanged, and reported instead. (2) **Focus indicators** the themed calendar has to keep (WCAG 2.4.7): a `:focus-visible` ring on events drawn inside the box in `--gd-calendar-event-text` (which already reads against the event fill, so it survives any surface), and a themed outline replacing FullCalendar's nav-button focus box-shadow (which was keyed to FullCalendar's own default button color and washed out once the buttons were themed). Both are added identically to Admin's and Member Web's `CalendarThemeStyles.tsx`. (3) **Fallback hardening** (the ticket's "sensible defaults and fallbacks when a theme property is missing or invalid"): `calendarVarValue()` in both `themeTokens.ts` files now falls back to the default for a persisted value that is *unusable*, not just missing — an empty string or a non-hex color would otherwise reach the CSS variable and, being invalid at computed-value time, drop the whole declaration rather than trigger the `var()` literal fallback (a `validateTokens()` gap for the un-format-checked `advanced` map and for rows written before #559). Covered by `apps/admin/src/test/calendar-a11y.test.ts` (the WCAG math, the pair definitions and their label/translation coverage, the report's advisory placement, the focus rules and their Member Web mirror, and the unusable-value fallback) with the Member Web mirror checks in `apps/member/src/test/calendar-theme-css.test.ts`.

**API surface:**
- `GET|POST|PUT|DELETE /platform/themes` — superadmin Base Themes CRUD only (`gym_id IS NULL`). `PUT` accepts `status` in `['draft','active','inactive']`; setting `draft`/`inactive` is blocked (409) when assigned as gym default or to centers. `DELETE` is also blocked (409) for the same reason.
- `PUT /platform/themes/:id/set-system-default` — atomically marks one Base Theme as `is_system_default = 1` and clears all others (superadmin only).
- `POST /platform/themes/clone/:id` — clone a Base Theme into a new Base Theme (superadmin only).
- `GET /system/themes` — gym admin: lists Base Themes + Customer Themes for the active gym. Each row carries `created_by_name`/`created_by_type` and `is_gym_theme` (#712).
- `POST /system/themes/clone/:id` — clone any accessible theme into a new Customer Theme.
- `PUT|DELETE /system/themes/:id` — update/soft-delete a Customer Theme (same protection rules as above).
- `GET /system/themes/:id/assignments` — returns `{ is_gym_default, centers: [{id, name, is_inherited}] }`.
- `PUT /system/themes/:id/set-default` — sets `gyms.theme_id`; rejects non-active themes (400).
- `GET /system/themes/:id/unassigned-centers` — centers not currently using this theme (for the assign picker).
- `POST /system/themes/:id/assign-centers` — body `{ center_ids }`; rejects non-active themes (400).
- `DELETE /system/themes/:id/centers/:centerId` — restores inheritance: sets `centers.theme_id = NULL`.

All strings live in each app's `locales/base/{en,es,ca}.json`, namespaced by feature. Use `useTranslations()` in every page/component. The admin app has a `LanguagePicker`.

### Member Web feature flags (#367)

Extends the `feature_flags` infrastructure (migration 110, see "Feature Flags" below) with a `member_web.*` namespace, deliberately separate from the Admin App's own flags (`membership.*`, `calendar.*`, etc.) — toggling one never affects the other, and the existing generic tree UI at `/cordel/feature-flags` renders `member_web` as its own top-level section with zero frontend changes (it groups by dot-namespace automatically). Migration 127 seeds five keys, all `enabled=1` (already-released features): `member_web.my_training_plan`, `member_web.my_nutrition`, `member_web.my_bookings`, `member_web.my_membership`, `member_web.profile`.

- **Backend**: each flag additionally gates the `/me/*` endpoints specific to that section — e.g. `member_web.my_nutrition` on `GET /me/nutrition-plan`, `member_web.my_membership` on `GET /me/membership`+`/me/billing-events`+`/me/promotions`+`/me/receipts/:id`+`/me/class-packages`, `member_web.my_bookings` on `GET/POST/DELETE /me/bookings`+`/me/upcoming`+`/me/activity-history`, `member_web.my_training_plan` on `/me/training-plans`+`/me/exercise-logs`+`/me/workout-block-logs`. `requireFeatureEnabled` is chained after any pre-existing flag on the same route (e.g. `calendar.calendar` stays on `/me/bookings`) — both must pass.
- **Superadmin bypass and impersonation precedence (#439)**: `requireFeatureEnabled` bypasses the check only in a superadmin's **native** capacity — `req.tenantCtx.isSuperadmin && !req.tenantCtx.impersonatedUserId`. `tenantCtx.isSuperadmin` itself stays `true` under impersonation (unchanged — other permission checks still treat an impersonating superadmin as having full access), so the exclusion is explicit at the feature-flag gate. This means a superadmin impersonating a member sees exactly that member's flags, not their own bypass — matching the frontend behavior below.
- **Shared-endpoint exception**: `GET /me/schedule` (also used by the un-flagged `/calendar` page under `calendar.member_calendar`) and `GET /me/payment-requests` (used by both `/membership` and `/profile`) are deliberately left ungated at the API layer — gating them under one Member Web flag would incorrectly block a different, independently-flaggable section that shares the same endpoint. `GET /me/profile` is likewise never gated: it's the core bootstrap call `AppContext.loadMemberData` uses to resolve `isLinked` for the whole app, not just the Profile page. These three cases rely on the frontend route guard alone for "no direct URL access"; every other `member_web.*` flag has both frontend and backend enforcement.
- **Frontend**: `apps/member/src/context/FeatureFlagsContext.tsx` mirrors the admin app's context (`GET /feature-flags`, no gym scoping) and exports `isFeatureEnabled(flags, key)` (ancestor-cascade lookup, same semantics as the backend's `requireFeatureEnabled`, defaults to enabled when a key has no row). It polls every 30s (matching the backend's in-memory cache TTL) so a toggle in Cordel → Feature Flags reaches an already-open session without a reload. Home (`page.tsx`) hides the My Training Plan / My Bookings / My Nutrition nav tiles, the Next Booking section, and the My Membership summary card when disabled (Calendar's tile is never gated — it isn't part of this flag set). Each of `/training`, `/nutrition`, `/schedule`, `/membership`, `/profile` redirects to Home in its existing `appLoading`/`isLinked` bootstrap effect when its flag is disabled. **Impersonation precedence (#439)**: each of these bypass checks uses `isSuperadmin && !isImpersonating` (`isImpersonating` from `useImpersonation()`), not raw `isSuperadmin` — while impersonating a member, the bypass does not apply and the page/tile follows the impersonated member's own flags, consistent with the backend. **(#438)** The Next Booking section explicitly gates on `member_web.my_bookings` in the frontend even though the `GET /me/schedule` call backing it is intentionally ungated at the API layer (see the shared-endpoint exception above) — without this, disabling the flag left the widget (and its `DELETE /me/bookings/:id` cancel button, which *is* backend-gated) visibly stuck rather than hidden.

### Code scanning (CodeQL) — how an alert is cleared (#767)

`codeql.yml` runs the **`security-and-quality`** query suite (advanced setup, not default
setup) and uploads SARIF, so a PR carries two separate checks: `Analyze
(javascript-typescript)`, which is the *scan* and goes green whenever the scan itself
finishes, and **`CodeQL`**, the code-scanning *results* check, which goes red while the PR
introduces an alert. A green Analyze and a red CodeQL on the same PR means the scan worked
and found something — not a broken workflow.

**Inline suppression comments do not work in this repository.** Both documented forms were
tried on the same alert and neither changed the check:

| Form | Result |
|---|---|
| `// codeql[js/xss-through-dom]` on the preceding line | still red |
| trailing `// lgtm[js/xss-through-dom]` | still red |

So a suppression comment in this tree suppresses nothing; it only makes the next reader
believe the alert is handled. **Do not add one** — the two
`// lgtm[js/missing-rate-limiting]` comments that sat on `/sellable-items` and `/taxes` in
`app.ts` were inert for that reason and were removed by #767, and
`api/src/test/codeql-suppressions.unit.test.ts` now fails the build if one comes back.
Write the reasoning as ordinary prose at the sink instead, saying why the flow is safe and
that clearing the alert takes a dismissal (see `apps/admin/src/lib/exerciseVideoUpload.ts`
for the shape).

The four routes an alert can take, in the order to consider them:

1. **Fix the code.** The default. An alert on a flow that really is unsafe is a bug, and
   restructuring away from the sink is worth doing even when the fix is only cosmetic *if
   it costs nothing* — #763 handed a detached `<img>` a base64 `data:` URL instead of an
   object URL (~100 KB) and the alert went with it. Weigh the cost: the same move on a
   video would have meant a ~67 MB `data:` URL in an element that then has to seek, i.e.
   trading a false positive for large uploads that silently stop working.
2. **Dismiss it in code scanning** (Security → Code scanning → *Dismiss alert* → **False
   positive**, with the reasoning in the comment). This is the route for a genuine false
   positive, and it is per-alert: it needs `security_events: write`, which the automation
   token does not have, so **a human with admin/maintainer rights has to do it** — an
   agent can neither dismiss nor re-open one.
3. **Merge with the results check red**, when the alert has been assessed as a false
   positive and the repository owner authorizes it. The authorization and the assessment
   go in the merge commit message, and the alert stays tracked until someone dismisses it
   (this is how #764 landed).
4. **Narrow the query suite** in `codeql.yml`. Repo-wide security posture change — only for
   a rule that is wrong *systematically*, never to get one PR green.

**The other suppressed-in-name-only rule.** `js/missing-rate-limiting` was marked on
`/sellable-items` and `/taxes` alone, which never reflected the code: `app.ts` applies a
global `apiLimiter` (500 requests / 15 min per IP) with `app.use()` ahead of every route,
and several routers add their own on top. Whatever the rule saw, those two routes are not
less throttled than the rest of the API — the `as any` cast the limiter needs to satisfy
Express 5's types is the likeliest reason the flow is invisible to it. Treat an alert of
that rule as (2), a dismissal, and `docs/go-to-production.md` carries the item.

**The known false positive.** `js/xss-through-dom` fires on a browser media helper that
hands a locally picked file to a **detached** media element: `URL.createObjectURL(file)` →
`el.src = url` on an element built with `document.createElement('video')` and never
inserted into the document. Nothing attacker-controlled reaches the sink and no HTML is
parsed — a media element fetches and decodes its `src`. The tell that it is element-type
imprecision rather than a real flow: the identical `img.src = url` in
`exerciseImageUpload.ts` is **unflagged**, because `new Image()` resolves to a known
element type while `createElement('video')` does not. Every future upload helper of that
shape will raise it again; the answer is (2) or (3), not a rewrite.

## Observability

### Structured logging (pino)

The API uses `pino` for structured JSON logging to stdout.

- **`api/src/lib/logger.ts`** — singleton logger. Set `LOG_LEVEL` env var (`debug` / `info` / `warn` / `error`; default `info`). In dev (`NODE_ENV !== 'production'`) output is formatted by `pino-pretty`; in production it emits raw JSON picked up by journald.
- **`api/src/middleware/requestLogger.ts`** — `pino-http` middleware mounted first in `app.ts`. Auto-logs every request/response with method, url, status, response time, and a unique `requestId`. All handlers can call `req.log.info(...)` to emit correlated log lines.
- **Never log**: card numbers, CVV, full payment token values, or member emails at DEBUG level. Only log IDs and status codes.

Payment-flow log convention:
```ts
req.log.info({ orderId, memberId, amount, provider }, 'Payment request created')
req.log.error({ orderId, err: e.message }, 'Provider API call failed')
```

### Log shipping (Phase 0b)

Grafana Alloy ships journald entries from both VPS to Grafana Cloud Loki.

**Architecture**:
```
corback (fitness-api)          corfront (fitness-admin, fitness-members, fitness-pay)
    journald                          journald
       ↓                                 ↓
  alloy (systemd)               alloy (systemd)
       └──────────── Grafana Cloud Loki (xavieregea-logs) ────────────┘
                              ↓
                    Grafana Cloud UI / alerts
```

**Config files**: `infra/alloy/config-corback.alloy`, `infra/alloy/config-corfront.alloy`, `infra/alloy/alloy.service`.

**Deployment**: Handled by `.github/workflows/deploy-alloy.yml` on push to `main`. The workflow SSHs into each VPS, downloads the Alloy arm64 binary, writes the config and unit file, and restarts the service. The API key is read from `~/.config/alloy/secrets` (not in git) as `GRAFANA_CLOUD_API_KEY`.

**Querying**: `{container="fitness-api"} |= "ord-001"` traces a single payment order across all log lines.
