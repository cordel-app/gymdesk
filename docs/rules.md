# Gymdesk rules

What the product does, stated for a person. One entry per business rule: the rule in one sentence, the ticket that decided it, one to three sentences on the behaviour, and the module or route that enforces it, so a reader can go from the sentence to the code.

This file is a **view** of the Hard constraints in `CLAUDE.md`, which is the agent's rulebook and carries the reasoning, the rejected alternatives and the implementation detail behind every entry here. The two are kept in step by the Finishing-a-task checklist: a ticket that adds or changes a constraint about product behaviour adds or changes the matching entry below. Where this file and `CLAUDE.md` disagree, `CLAUDE.md` is right and this file has a bug.

Three documents sit beside it: `docs/payments.md` (the first-payment and recurring-charge processes end to end), `docs/mobile-app.md` (the plan and design rules of the store app) and `docs/decisions.md` (the settled architectural choices). The current state of each area and the open issues are in `docs/roadmap.md`; the per-ticket history is `docs/changelog.md`.

Conventions in the entries: a **Membership Plan** is the gym's catalogue offer; an **Assigned Plan** is one member's copy of it, frozen when assigned; a **Product** is anything else the gym sells; a **Promotion** changes what a Plan or a Product costs; a **Professional Service** is what a session-based Product grants (a Personal Training session, say); **Cordel** is the platform's own back office, reachable only by a superadmin; the **Admin app** is the gym staff's and the **Members App** is the member's, in a browser or inside the iOS/Android shell.

## Platform, tenancy and roles

- **Every gym's data is its own; the shared platform catalogues are the one thing gyms have in common** (#947). Every record belongs to one gym and every screen and API call shows only that gym's rows. The exceptions are the platform catalogues — Base Exercises, the Nutrition Library foods, Base Themes, Personal Goals and Nutrition Goals — where a *System* row is owned by the platform, administered from Cordel (the platform back office), visible to every gym and read-only for them, while a gym's own rows in the same catalogue stay private to that gym. Enforced in `api/src/infra/tenantContext.ts`.

- **A staff member's access is decided by their profile, per section, with one feature-level exception** (#592, #1070). The profile chosen on the Staff form — Gym Manager, Personal Trainer, Personal Trainer & Nutritionist, Front Desk, Accountant or Nutritionist — fixes the role, and each role has one access level per section (Members, Calendar, Organization, Training, Nutrition, Financials, Payments, System, Cordel): full, read-only, own assigned records only, or none. A feature flag key can override one section's level for one role, in either direction; today the only override gives a Personal Trainer full access to Personal Goals without opening the rest of Nutrition. Cordel → Feature Flags shows such overrides in red beside the inherited level. A platform superadmin is treated as an admin of any gym; permissions are declared in code, never edited on screen. Enforced in `api/src/infra/permissions.ts`.

- **A gym's Website Integration is administered from Cordel → Gyms, not from the gym's own settings** (#1052, #645). Expanding a gym's card in Cordel shows the public registration endpoint with a Copy action, the current API key's prefix and creation date, and Generate / Rotate / Revoke, each behind a confirmation. The full key is shown once, when it is generated, and never again. The gym's website posts member sign-ups to that endpoint with the key. Because Cordel is superadmin-only, a gym admin no longer reaches this screen. Enforced in `api/src/api/website-integration.ts`.

- **Center selection lives on the Calendar, and only there** (#930). A multi-center gym picks a center — or all centers — in the Calendar's own filter bar, and the choice is remembered per gym. That selection decides which center a new class session, space, room or trainer availability is created in, and which center's theme is painted. Class sessions belong to one center and are filtered strictly; a manual calendar event may be gym-wide and stays visible under every center. A gym with a single center sees no center control at all, and the Members list keeps its own Center filter. Enforced in `api/src/infra/centerContext.ts`.

- **Only an active Staff record can be assigned as a trainer** (#986). Every trainer picker — an Activity Type's default trainer, a class session's trainer, trainer availability — offers each staff member whose employment status is `active`, whatever their profile (a Gym Manager or Front Desk member included) and even while they are on vacation or suspended; the list is ordered by first name, then last name. A trainer already stored on an activity or session is kept when that person is no longer selectable (shown as a disabled option rather than silently dropped) and is cleared only when the staff member is deactivated, which removes their login. Enforced in `api/src/domain/trainerAssignment.ts`.

- **Removing a person's last link to the product deletes their login** (#709). When a Member is deleted or a staff member's app access is revoked, the product checks whether that person's login account is still linked to any other gym or Member. If it was the last link, the login account itself is deleted, so no orphaned account survives to sign in to nothing. Enforced in `api/src/infra/clerk-account-links.ts`.

- **Every change is recorded in the Audit Log, and every Details view links to it** (#1182). The `⋮ → Details` view of any entity offers *View Audit Log*, which opens the log already filtered to that exact record, and the Audit Log can be filtered by entity type. Created by / Modified by / Deleted by are written as text at the moment of the change: `Pedro` when Pedro acted, `Oscar (impersonating Pedro)` when the superadmin Oscar acted as Pedro, `System` for a nightly run or a payment webhook, and blank when nobody can be named — the text stays even if the person is later renamed or removed. Enforced in `api/src/domain/auditActor.ts` and `api/src/infra/audit-registry.ts`.

- **A gym imports Base Exercises into its own catalogue, and only imported ones appear in its Exercises page** (#718, #804). The platform's Base Exercises are offered in the gym's Import dialog; importing creates the gym's own copy, badged *System sourced* (a gym-created exercise reads *Custom*). A Base Exercise the gym never imported appears nowhere in that gym's Exercises list — under no filter, search or ordering — and adding one to the platform library does not make it appear in every gym. Re-importing an already imported exercise refreshes its System media only. Enforced in `api/src/api/exercises.ts`.

- **Catalogue names can be translated per language, and each reader sees their own** (#967). An exercise or a Nutrition Library food has one base name plus optional translations per language (English, Spanish, Catalan); a reader sees the translation for their language and falls back to the base name. Search matches the base name or any translation, whatever language the screen is in. Duplicate, Clone and Import copy the translations with the row; re-importing a Base Exercise never overwrites a translation the gym corrected. Enforced in `api/src/domain/nameTranslations.ts`.

- **Each gym sets its own time zone, first day of the week and date, time and number formats; its currency is EUR** (#1246). The six Time & Localization settings default to Europe/Madrid, Monday, `DD/MM/YYYY`, 24h and comma decimals, so nothing changes until a gym edits them; the date formats offered are DD/MM/YYYY, MM/DD/YYYY and YYYY-MM-DD, the time formats 24h and 12h. Currency is display-only and EUR is the only accepted value — it never changes what is charged. The Admin Calendar follows the first day and the 12h/24h format, and the Admin's detail panels and audit timestamps use the gym's zone, while the calendar grid itself still runs in the browser's time zone. Enforced in `api/src/domain/gymLocalization.ts`.

- **An unexpected failure answers a generic error, never an internal message** (#966). When something the product did not anticipate goes wrong — a database or storage fault — the client sees `500 Internal server error` and the real error is written to the server log only. A refusal the product makes on purpose (a validation error, a conflict, a storage step reported with its stage and path) keeps its specific message. Enforced in `api/src/domain/httpErrorResponse.ts`.

- **The product is one application over one database, with no AI features** (`docs/decisions.md`). Gymdesk runs as a single API with a single MySQL database and integrates no AI or language-model service: nothing in the product generates text, recommendations or images automatically, and generated artwork (such as Base Nutrition images) comes from deterministic, offline generators. Stated in `docs/decisions.md` (an architectural decision, not a runtime rule).

## Members (Admin app)

- **A Member's Membership Plan Status is the status of their most recent Assigned Plan** (#809, #1108). The Members list shows it as *Enrollment status* and filters on it: whatever the latest plan assigned to the Member reads — active, paused, cancelled, expired — with a Draft or a plan awaiting payment not counted. A deleted Member counts nowhere. The Nutrition Dashboard's "active members" figure for a Nutrition Plan uses the same rule, so the count and the filter cannot disagree. Enforced in `api/src/domain/memberEnrollment.ts`.

- **A Member's Access Rights are an informational status: Granted, Revoked or To be reviewed** (#1238). Staff grant or revoke access from the Member card (audited), and `granted` is the default. A Member whose access is granted but whose worst Payment Status is `failed` or `expired` reads *To be reviewed* automatically, and returns to *Granted* by itself once the payment is settled; a revoked Member stays revoked whatever they pay, and cancelling a plan changes nothing. Nothing is gated by it — neither booking nor login. The Member header shows it beside Membership Plan Status and Payment Status. Enforced in `api/src/domain/memberAccessRights.ts`.

- **A Member's Account section shows when they were invited and when they enrolled** (#1234). Invite, Re-invite and a website sign-up stamp the invitation date; linking a login account stamps the enrolment date once. Whether the Member is enrolled, and whether an invitation is still pending, are read from the account link and the open invitation — never from the dates, which are history and are not cleared when an invitation is accepted or revoked. A Member created before the dates existed shows the line without one. Enforced in `api/src/api/members.ts` and `apps/admin/src/lib/clerkAccountLines.ts`.
- **A Member can have one profile photo, a 512 × 512 PNG stored in the gym's own Cloudflare folder** (#1374). Staff upload, replace or remove it from the Member card's Edit mode, or pick one while creating the Member (uploaded right after the Member is saved); the browser crops and scales whatever picture is chosen, and the server checks the bytes, so a rejected upload leaves the current photo untouched. Replacing overwrites the photo in place, renaming the Member moves it to the new name without losing it, and removing deletes only that Member's own object. A deleted Member keeps the photo for a restore. Enforced in `api/src/domain/memberImages.ts` and `POST`/`DELETE /members/:id/image`.

- **A Member can choose their default language, and the Members App opens in it** (#1039). The preference — one of the deployment's configured languages (English, Spanish, Catalan) — is stored on the Member and set from the Members App profile; with none set, the app follows the browser's language. A signed-in member who lands on another language is moved to theirs once; a superadmin impersonating a member sees the app in that member's language (the app's default if they have none), and returns to their own when the impersonation ends. Clearing the preference is explicit, and a language the deployment does not offer is refused rather than reinterpreted. Enforced in `api/src/domain/memberPreferredLocale.ts` and `apps/member/src/lib/memberLocale.ts`.

- **A Member is called a Member on every screen: Miembro in Spanish, Membre in Catalan** (#1026). *Socio/Socios* and *Soci/Socis* are retired from every label in both apps and from the privacy policy. The Membership Fee and the Membership Plan keep their own names (*cuota de membresía*, *plan de membresía*). The one exception is the Spanish fiscal receipt, where "Socio" is the placeholder printed where the person's name goes. Gate: `api/src/test/member-terminology.unit.test.ts` (a copy rule; nothing at runtime enforces it).

- **Training Plan Templates and Assigned Training Plans are named apart** (#970). The reusable, gym-wide definitions are *Training Plan Templates* (and, in Cordel, *Base Training Plan Templates*); the plans a Member actually holds are *Assigned Training Plans* — in the sidebar, the page heading, the Member card's section and their empty states. The Members App's own page stays *My Training Plan*. Stated in `apps/admin/locales/base/en.json` (a copy rule).

## Membership Plans, Assigned Plans and billing


- **A member's commercial configuration is a versioned ProductSet, and only one version is Active** (#1325 stage 1). Each change is a new version of the owner's chain; the Active version stays Active while the replacement is a Draft or awaits payment, and is superseded only when the replacement activates, in one transaction. At most one Active and one in-flight (Draft or Pending Payment) version exist per owner, enforced by the database. A Draft is saved as it is edited and expires after two hours without activity; a Pending Payment checkout may be cancelled only when no payment was initiated or every attempt definitively failed. Family members are covered by the owner's chain and never get a copy. Stage 1 adds the model only: nothing bills from it yet. Enforced by `api/src/domain/productSet.ts` and `api/src/api/product-sets.ts`.
- **The nightly run charges only a ProductSet's persisted Billing Events, and a rejected one stops after two failed days** (#1325 PR 3). Every committed Membership Plan is a ProductSet version whose obligations are already in the ledger; the run executes those due, from their own amount, one attempt per day, and the second failed day pauses the member's plan (reactivating is explicit). A membership status change is recorded in the audit log, not in the ledger. Enforced by `api/src/api/scheduled-event-execution.ts` and `api/src/api/billing-events.ts`.
- **A one-off purchase and a card verification are in the ledger but owe nothing** (#1325 PR 2). Each has its own Billing Event, written when the payment starts; neither counts as revenue or as something staff must chase, a paid purchase gets a receipt and the member's own list hides the verification. Enforced by `api/src/domain/billingEventStatus.ts`.
- **The development reset deletes assignments, the ledger and their payments, and nothing else** (#1325). `npm run billing:reset-dev` empties the assigned Membership Plans and what hangs from them, the Billing Events and their lines, every payment request, the one-off purchases and the audit rows of those entities, in one transaction; members, catalogue, stored cards, receipt sequences and other audit rows are preserved. It is a dry run unless `--execute` and `RESET_CONFIRM` are given, and the workflow that runs it on the deployed database is bound to the `dev` environment. Enforced by `api/src/domain/devBillingReset.ts`.
- **An Assigned Plan freezes the commercial terms it was assigned with** (#635). The moment a Membership Plan is assigned to a Member, the product copies the Plan's price, billing frequency, Free/Paid/Bonus durations, Auto Renew flag and every Product benefit onto the assignment itself. Editing the Membership Plan or a Product afterwards changes nothing for Members who already hold it: a price rise, a new benefit or a changed frequency reaches only assignments created from then on. Enforced in `api/src/api/assigned-plan-snapshot.ts` (`snapshotAssignedPlan()`).

- **Editing an Assigned Plan changes that one Member's agreement and nothing else** (#635 stage 6). Staff can change an Assigned Plan's benefits, fee and durations, and the change stays on that assignment — it never writes back to the Membership Plan, to another Member's assignment or to the Product. A `cancelled` or `expired` assignment cannot be edited at all. An assignment created before snapshots existed is captured in full the first time any part of it is edited. Enforced in `api/src/api/assigned-plan-snapshot.ts` (`materialiseAssignedPlanSnapshot()`).

- **What a Member is charged and what they are shown both come from the frozen assignment** (#635 §13–§17, stage 10). The nightly run, the staff Assigned Plan card, the Payments dashboard and the Member's own My Membership page all read the assignment's own cadence, prices and benefits, so the Member cannot be shown one set of terms and billed another. The live Plan catalogue is consulted only for an assignment that was created before snapshots existed and captured nothing. Enforced in `api/src/api/assigned-plan-snapshot.ts` (`ASSIGNMENT_CADENCE`, `loadPlanBenefitsForSimulation()`).

- **A Membership Plan bills either Monthly or Every 4 Weeks, and Billing & Duration is its only billing section** (#820, #635 stage 13). The Billing frequency says how often the fee is charged; the Free Period, Paid Duration and Bonus Duration say how long the contract runs, never how often it charges. Saving any other frequency is refused, but a Plan that still holds an older cadence keeps being billed and displayed exactly as stored rather than being silently relabelled as Monthly. Enforced in `api/src/domain/planBillingFrequency.ts`.

- **A newly assigned Membership Plan is a Draft, not yet the Member's plan** (#1108 stage 1). Every assignment — by staff, by the Plans page's bulk Assign or by the Member from the Members App — starts as `draft`. A Draft bills nothing, lets the Member book nothing, does not count as their plan anywhere (the Members list, the Member's own app, the Financials counts) and does not block them holding an Active plan beside it. It is fully editable and its Billing Event Forecast shows what committing it would bill. A Draft nobody commits never expires; staff discard it. Enforced in `api/src/api/user-memberships.ts` and `api/src/api/assignment-commit.ts`.

- **Cancelling a Draft deletes it outright** (#1240 PR 1). Cancel on a Draft removes the row and its frozen configuration for good, after a confirmation; the action is refused with `409 not_draft` on any other status, where closing or cancelling keeps the record of what was billed. In Edit mode a Draft closes with Cancel, Save or Save & Pay, and its "Negotiated Discount %" is the Personal Membership Fee Benefit described below. Enforced in `api/src/api/user-memberships.ts` (`DELETE /user-memberships/:id/draft`).

- **Save & Pay is the point of no return: the Draft becomes Pending Payment and is locked** (#1108 stage 2). Save & Pay moves a Draft to `pending_payment` — or straight to `active` when the first cycle owes nothing — and from then on its configuration, benefits and Promotions can no longer be edited. On a pending row staff may *Record cash payment* or *Send payment link*, and the Member's own *Pay now* reaches it ahead of any active plan. A pending assignment is still not the Member's plan: it bills nothing, books nothing and is invisible wherever "does this Member have a plan" is asked. Enforced in `api/src/api/assignment-commit.ts` (`submitForPayment()`).

- **An Assigned Plan becomes Active when its first payment settles** (#1108 stage 2, #1288). The payment webhook's `completed` notice, a staff-recorded cash payment, a `payment_recorded` event posted against the pending row, or an explicit staff activation each commit the row to `active` in one step. A cash first payment stamps no next billing date and stores no card. Only the first charge is created at Save & Pay; every later charge is the nightly run's. Enforced in `api/src/api/assignment-commit.ts` (`commitAssignment()`).

- **A Member holds zero or one Membership Plan, never two** (#956). A `paused` plan still counts as the one plan, so does a plan that has not started yet, and so does being a covered Member of a family plan somebody else owns. A Draft or a Pending Payment row does not count, which is what allows a replacement to be configured beside the plan it replaces. The rule is checked at the moment an assignment is activated. Enforced in `api/src/domain/oneActivePlan.ts` and `api/src/api/one-active-plan.ts`.

- **Replacing a Member's plan is explicit, immediate and keeps the old record intact** (#956). Activating a plan for a Member who already holds one answers `409 active_plan_exists`, naming both plans and the current plan's dates, and the Admin app asks for confirmation. On confirmation the old plan is `cancelled` and ends on the new plan's start date, so the two never overlap; its billing history, Promotions and next billing date are left untouched as the record of what it billed. A new plan starting before the old one did is refused. *Assign New Plan* needs no confirmation because replacing is its purpose; the Plans page's bulk Assign succeeds for all selected Members or none. Enforced in `api/src/api/one-active-plan.ts` (`supersedeLiveAssignments()`).

- **Adding a covered Member to a plan never replaces that Member's own plan** (#956). Covering somebody under a family plan is the fourth way a Member comes to hold a plan, so a Member who already holds a live one is refused with the same `409`, and here there is no confirm option: staff close the Member's existing plan first, then add them. Enforced in `api/src/api/user-memberships.ts` (`POST /user-memberships/:id/members`).

- **The Membership Fee is priced per billing cycle by one calculation, and every screen shows that same number** (#635 stage 12). What a cycle costs — and whether it is waived — is computed on demand for the date in question; no agreed or discounted price is stored. The Billing Simulation, the Assigned Plan card, the Payments dashboard, a payment request, the Member's My Membership page and the nightly run all ask the same calculation, so a Member cannot be shown one price and charged another. An applied Promotion's Membership Fee Benefit applies only inside that Promotion's own Free/Paid/Bonus months and ends with it; a Promotion configured with no months discounts nothing. Enforced in `api/src/domain/billingSimulation.ts` (`resolveMembershipFee()`) and `api/src/api/membership-fee-pricing.ts`.

- **The regular fee a discount is taken from is the assignment's frozen price, then the Plan's current price** (#635). A negotiated fee is stored on the assignment with a discount reason, and the Plan page's "Apply new price to assigned plans" skips any negotiated assignment. When a negotiated discount's expiry date has passed, the assignment falls back to the Plan's price window. "What does this Member pay now" is always the current cycle, never one already past. Enforced in `api/src/api/user-memberships.ts` (`regularMembershipFee()`) and `api/src/api/membership-fee-pricing.ts` (`currentCycleDate()`).

- **A Membership Plan's price is quoted both with and without tax, at the Plan's own rate or the gym's default** (#817). A Plan's Tax rate may be left as *Default*, which means the gym's system tax rate; the server reports the gross and net amounts and the rate it applied, so a Plan on Default shows a real price rather than a blank. A soft-deleted rate still shows as a Plan's own rate but is never picked as the gym default. Enforced in `api/src/domain/planTaxRate.ts` (`selectPlanTaxRates()`).

- **The Free Period, Pre-paid Duration and Bonus Duration charge no Membership Fee, counted in the assignment's own billing periods from its start date** (#635 stage 8, #892). The four durations are counts of the assignment's Billing frequency periods — two free periods on a 4-weekly plan are two 4-week periods, not two calendar months — and they run from the day the assignment started. Only the Membership Fee is waived: the Plan's Period Benefits (Products) are still charged in a free period. Where an applied Promotion governs a date, the Promotion alone decides the fee; a Promotion's own durations stay in calendar months. Enforced in `api/src/domain/planDuration.ts` (`classifyPlanDurationPeriod()`).

- **The Pre-paid Duration is paid once, up front, at the regular price** (#946). The first N periods of the Paid Duration are charged as one lump on the first of them — €70 a month with 3 pre-paid periods is a single €210 charge — and those periods then bill nothing further. The Pre-paid Duration can never exceed the Paid Duration. It is a real payment, not a waiver, and a Personal Membership Fee Benefit still discounts it. Enforced in `api/src/domain/planDuration.ts` (`prepaidPeriodsDueOn()`).

- **Auto Renew decides whether the Free → Pre-paid → Paid → Bonus cycle starts again** (#1130). With Auto Renew on, the whole cycle repeats indefinitely and the pre-paid lump is collected again at the start of every iteration; with it off, the cycle runs once and the assignment then continues at the regular fee — the membership does not expire. The flag is frozen onto the assignment when it is created, so changing the Plan's Auto Renew later affects new assignments only; every contract created before the setting existed is non-repeating. The Membership Fee Simulation and the Billing Event Forecast group their rows by cycle and say whether it renews. Enforced in `api/src/domain/planDuration.ts`.

- **A Personal Membership Fee Benefit discounts every cycle for the life of the assignment** (#772). Staff can give one Member a percentage discount (0–100 %) on their fee. It is applied last, on top of any Promotion discount, and it carries on after the Promotion ends. It is not a negotiated price (the regular fee is unchanged) and it is not carried over when the Member is moved to a new plan, which is a fresh agreement. Enforced in `api/src/domain/personalFeeBenefit.ts` and `api/src/api/user-memberships.ts` (`PUT /user-memberships/:id/fee-benefit`).

- **The nightly run charges each Active assignment the cycle its next billing date names, priced by the same calculation the screens use** (#635 stages 11–12). Each night the run takes every `active` assignment whose next billing date has arrived, prices that cycle, charges the Member's stored card and advances the next billing date by one period. A waived cycle (a free, pre-paid or bonus period) calls no payment provider and raises no payment: the run records a `waived_billing` event and moves the date on. Enforced in `api/src/api/billing.ts` (`POST /billing/run`) over `api/src/api/membership-fee-pricing.ts` (`priceMembershipFeeOn()`).

- **The next billing date is always in the future, and cycles that elapsed before the first payment are written off** (#790). The first payment is priced on the day it is made, and the first scheduled charge is set to the next cycle boundary strictly after today, counted from the assignment's start date. A back-dated start date is allowed: the cycles that passed before the first payment, and the cycles missed while an assignment was paused, are never charged afterwards — no catch-up charge and no adjustment. Reactivating an assignment walks a past date forward the same way. Enforced in `api/src/domain/nextBillingDateStamp.ts` over `api/src/domain/billingDate.ts` (`firstBillingDateAfter()`).

- **A declined recurring charge is retried the next run day, and the second decline pauses the assignment** (#785). When the provider rejects a charge, the billing date stays where it is and the next night tries the same cycle again; a second rejection on a later day moves the assignment from `active` to `paused`, after which it is no longer charged. Two rejections on the same day count once. A provider outage or a Member with no stored card neither counts nor clears. Any settlement — a successful or waived cycle, the Member paying their link, a staff Retry or Manual payment — clears the count, as does reactivation, which is always a staff decision: paying never un-pauses by itself. Enforced in `api/src/domain/billingDunning.ts`.

- **A nightly run completes at most once per UTC day** (#780). The billing run and the recurring-bookings run each record one row per run. A second attempt on a day whose run already completed is answered with `200` and `skipped_reason: 'already_completed_today'` with zeroed counters, so the scheduled retry is a safety net rather than an error. A run started while another is still in progress is refused with `429`; one that has been in progress longer than the stale limit is taken over, so a crashed run cannot lock the day. Enforced in `api/src/domain/runGuard.ts` and `api/src/infra/run-log.ts`.

## Billing simulations and the member's view of billing

- **A Membership Plan card shows a Membership Fee Simulation: one row per billing period, each saying whether that period is Free, Pre-paid, Paid or Bonus and what it charges** (#818, #892, #946). The rows step by the Plan's own Billing frequency (Month or 4 Weeks) and the Free Period, Pre-paid Duration, Paid Duration and Bonus Duration are counted in that same unit, so a 4-weekly Plan with a Free Period of 2 shows exactly two free rows. Only the first Pre-paid row charges anything: the regular price times the number of pre-paid periods, collected up front. Amounts are VAT-inclusive; a Plan with no price reads `—`, never €0.00. Nothing is persisted and nothing is charged. Enforced in `api/src/domain/planExampleTimeline.ts` over `api/src/domain/exampleTimeline.ts`.

- **An Assigned Plan's Membership Fee Simulation is priced by the same fee resolver the nightly billing run charges from, so the table cannot disagree with what the Member is billed** (#924 stage 3). Every row is priced from the assignment's own frozen configuration: its Billing & Duration, any Promotion applied to it and the Member's Personal Membership Fee Benefit. The rows start at the period containing today while their numbering counts from the assignment's start date. Where a Promotion governs a period, the Promotion alone decides the period's status and price. An assignment with no billing frequency shows no simulation. Enforced in `api/src/domain/assignmentExampleTimeline.ts`.

- **A Plan with Auto Renew shows its Free → Pre-paid → Paid → Bonus cycle starting again, and the simulation says so** (#1130). A renewing contract is shown as two complete cycles, each numbered and grouped, with a "cycle repeats" marker under the table; the cycle number is the real one, so a Member on their third cycle sees `3`, not `1`. A contract that does not renew shows cycle `1`, then its ordinary regular-price periods outside the grouping, with a "One cycle only — no renewal" marker. The flag is the assignment's own, frozen when the plan was assigned: changing the Membership Plan's Auto Renew later does not change an existing Member's billing. Enforced in `api/src/domain/exampleTimeline.ts` (`timelineCycleFor()`) and `api/src/domain/planDuration.ts`.

- **A Membership Plan card also shows a Billing Event Simulation: one group per billing date, listing every line charged on it — the Membership Fee plus each Product the Plan carries** (#915, #922). It projects what a Member enrolling today would be billed, with no Promotions, Additional Services or personal discounts, and runs far enough to show at least two charges of every recurring item (a yearly Product therefore extends it to two years). Each Product keeps its own frequency; a shared date is what puts two lines in one group. A waived line is still listed, at €0.00 beside its regular price. All amounts are VAT-inclusive. Enforced in `api/src/domain/planBillingEventSimulation.ts` over `api/src/domain/billingEventSimulation.ts`.

- **A Promotion's Billing Event Simulation shows the Products it grants and carries no Membership Fee line** (#922, #926). Each granted Product is listed at the price the Promotion's grant gives it for the units or periods the grant covers, and at the Product's regular price after them; the projection is anchored on the Promotion's start date when that is still in the future. What the Promotion does to a Membership Fee is shown by the Membership Fee Simulation beside it, and only for a Promotion about a Membership Plan — a Promotion about a Product has no Billing & Duration and no fee simulation at all. Enforced in `api/src/domain/promotionBillingEventSimulation.ts`.

- **An Assigned Plan's Billing Event Forecast is the real contract projected from today, with the amounts the nightly run will actually charge** (#924 stage 4). It is built from the assignment itself — the frozen plan snapshot, every standing Promotion application, the Additional Periodic Services and the Personal Membership Fee Benefit — so the forecast and the nightly run read one configuration. Billing dates already behind us are not forecast: the Billing Events ledger on the same card is the record of those. The frozen Membership Fee and each line's frozen unit price are the figures shown, and no line of an assignment is flagged Mandatory. Enforced in `api/src/domain/assignmentBillingEventSimulation.ts` over `api/src/api/billing-simulation.ts`.

- **Every Billing Event Simulation is read as one collapsible card per billing date, grouped by the same cycle the fee table above it uses** (#955, #1130 stage 3). Each card's header carries the date, how many lines fall on it and the date's total; the first date opens by default, the rest are closed, and an Expand all / Collapse all control appears when there is more than one. Opening a card fetches and recomputes nothing. Each date carries the cycle iteration it falls in, so the fee table and the event cards tell the same story: for a renewing contract the forecast is bounded to the same two cycles the fee table shows, however long the cycle is. Enforced in `api/src/domain/billingEventSimulation.ts` (horizon and grouping) and `api/src/domain/planDuration.ts` (`planDurationCycleIteration()`).

- **The Members App's Payments card shows the Member exactly the forecast the Assigned Plan card shows staff, scoped to their own plan** (#1123). On the *My Products and Services* page, **Next Payment** is the first forecast date and **Forecast Billing Events** are the dates after it, so the next charge is listed once and the two cannot disagree; the horizon is the same two cycles per recurring item. Past charges are listed from the Billing Events ledger with each event's own status (paid, pending, failed…), line by line, since one date can carry both a settled and a rejected charge. The Member is never named by the request — the card always reads the caller's own plan. Enforced in `api/src/api/me-billing-forecast.ts`.

- **A Member's finished Membership Plans are listed as history: a name, a status and the day each one ended, with no price and no action** (#1122 §7/§8). The Past Membership Plans card lists the plans the Member no longer holds, newest first; the end date is the plan's end date, or the day it was closed, and is left blank rather than invented when neither is known. A Draft never appears there, and a plan cancelled today is not shown both as current and as past. A Member with no history gets no card at all. Enforced in `api/src/domain/memberPlanHistory.ts`.

- **A Member adds a Membership Plan from the Members App through the same assignment the staff use, with the same checks** (#1122 §1–§6). The catalogue offers the gym's active, public plans and, under each, the Promotions a Member may actually apply: active, inside their start and end dates, targeting that plan and carrying a Membership Fee Benefit that changes something (a free first stretch counts); a new-members-only Promotion is hidden from a Member who is not new. The preview price is the first cycle under the chosen Promotion, with the Promotion's duration read in months; the authoritative fee is the assignment's own once it exists. The Member names no price. Enforced in `api/src/domain/memberPlanCatalogue.ts` and `api/src/api/me-membership-plans.ts`.

- **Save & Pay in the Members App creates the plan as Pending Payment, writes the first charge before the money moves, and never replaces a plan the Member already holds** (#1288 stage 1, #1108). A Member with a live plan is refused with `409 plan_change_via_gym` ("to change your plan, contact your gym") and one with a plan awaiting payment with `409 plan_pending_payment`; replacing a plan is a staff action in the Admin app. Otherwise the Draft is submitted for payment, one pending Billing Event is written with the checkout linked to it, and the Member pays through the hosted page or later through **Pay now**, which reuses that same open event rather than creating a second one. A first cycle that owes nothing activates the plan immediately. Only the first charge is written this way; every later one is the nightly run's. Enforced in `api/src/api/plan-checkout.ts` and `api/src/api/me-membership-plans.ts`.

## Products

- **The things a gym sells beside the Membership Fee are called Products; "Sellable Item" is a retired name** (#949). A Product is what a Membership Plan or a Promotion can include and what a member can buy on its own — a locker rental, an insurance fee, a package of personal-training sessions. The Admin app manages them under Financials → Products, behind the `financials.products` feature flag; two old links (`financials/sellable-items`, `financials/gym-charges`) still redirect there. Enforced in `api/src/api/products.ts`.

- **A new gym starts with a standard set of Products, and that set is never written over an existing gym** (#1149). When a gym is created or duplicated it receives one Product per catalogue charge type plus the Personal Training package, each with a declared price, Billing Frequency, statuses, units and Mandatory flag, priced VAT-inclusive of the gym's `Standard VAT` 21% rate (which is created first). Re-running the initialization adds nothing: a Product the gym has repriced, deactivated or deleted keeps what the gym decided. Existing gyms are not backfilled. Enforced in `api/src/domain/defaultGymProducts.ts` and `api/src/api/gym-default-products.ts`.

- **A Product's Billing Frequency is one of four: Once, 4 Weeks, Month or Year** (#945, #821). Two older values, `week` and `per_session`, are retired but not deleted: a Product already configured with one keeps it, keeps billing and keeps displaying it, and editing another field of that Product does not fail or silently change the frequency. A new Product cannot be created with a retired value, and no Product can be moved onto one. The editor shows a retired value as a disabled option with a notice naming it; Duplicate copies it as is. Enforced in `api/src/domain/productFrequency.ts`.

- **A billing frequency reads the same way everywhere in the Admin app** (#1128). `once` reads *Once*, `four_weeks` *Every 4 weeks*, `month` *Monthly* and `year` *Yearly* — on the Products page, in a Membership Plan's or Promotion's benefit rows and on an Assigned Plan alike — and a Membership Plan's own Billing frequency uses the same words. A retired value still has a label; an absent or unknown one reads `—`. The Members App says the same words in its own language files. Enforced in `apps/admin/src/lib/billingFrequency.ts`.

- **A Product of type Sessions is priced as a whole package, never per session** (#942). `Units: 5` beside `Price: €50.00` means €50.00 for the five sessions, not €250.00; nothing multiplies a price by the unit count and no per-session price is stored or shown. Every screen showing such a price adds the sentence *Total price for N sessions* (a package wording when units are unset) and a `(tax …)` note only where a tax rate is actually configured. Enforced in `apps/admin/src/app/[locale]/financials/products/productPriceNotes.ts`.

- **A Mandatory Product is part of every Membership Plan, and the gym cannot drop it from one** (#832, #893). The flag is editable on any Product, System or Custom. Only active, non-deleted mandatory Products count: when a Plan's benefit sections are read, a missing mandatory Product appears automatically at quantity 1 (marked implicit), and when a section is saved without it, it is kept rather than refused — which is also how an existing Plan picks up a newly mandatory Product the next time it is saved. Mandatory says the Product must be present, never what its quantity is. Enforced in `api/src/domain/mandatoryPlanBenefits.ts`.

- **On an Assigned Plan, a mandatory Product's quantity is the number of Members the Membership covers** (#1187). The configured quantity is replaced — never multiplied — by the count of covered Members, owner included and never below 1, and it is recalculated when a Member is added to or removed from a non-closed assignment. Staff and members see it read-only; the Membership Plan's own row and Billing Events already written are untouched. Enforced in `api/src/domain/assignedBenefitQuantity.ts` and `api/src/api/assigned-plan-snapshot.ts`.

- **A Periodic Product granted by a Promotion carries a Duration, counted in the Product's own billing periods** (#1135). The Promotion card's Periodical section labels the number *Duration* and captions it as `3 months` or `3 × 4 weeks` from the Product's frequency; a Product with no period (Once) gets no caption. During those periods the member is billed one unit per period under the Promotion's treatment; when the Duration ends the Promotion ends and the Product continues at its regular price. A fractional number (`3.5`) is refused. A Membership Plan's periodical quantity, and Session and One-off grants, stay plain quantities. Enforced in `api/src/domain/billingSimulation.ts`.

- **A member is shown exactly the Products the gym made active and public** (#1121 stage 1). The *Additional Products and Services* section of the Members App's *My Products and Services* page lists Products with `status = active` and `enrollment_status = public` — System or Custom, mandatory or not. Each shows one VAT-inclusive price with a *tax included* note only where a rate is configured (an unpriced Product reads `—`), its frequency, and for a Sessions package *Total price for N sessions*. If the gym has switched off the Members App's My Membership or the Products feature, the section is simply absent. Enforced in `api/src/domain/memberProductCatalogue.ts` and `api/src/api/me-products.ts`.

- **A member can buy a one-off Product from the Members App, and the payment is what grants it** (#1121 stage 2). Only a Product the member can be shown may be bought; a recurring one (4 Weeks, Month, Year) shows no Buy action. Buying writes a `pending_payment` purchase and a payment request together and sends the member to the hosted payment page; the provider's confirmation makes the purchase `active`, recording what was bought at the price shown, so a Product renamed, repriced or retired later changes nothing about it. A member may hold one pending purchase per Product at a time (a second attempt is refused as `purchase_pending`) but may buy the same Product again once an earlier purchase is active; a purchase whose payment lapsed becomes `cancelled` by the nightly cleanup. Enforced in `api/src/domain/memberProductPurchase.ts` and `api/src/api/me-products.ts`.

- **Buying a Product is not paying the Membership Fee** (#1121 stage 2, #1235). A completed purchase lands in the Billing Events ledger as a `payment_recorded` event but stores no card, stamps no next billing date and settles no rejected fee — a fee still owed is still owed after a member buys a locker. The hosted page tells the member it is a one-off purchase, not a recurring charge. A failed purchase does count toward the Member's Payment Status on the Members list, while the member's own *Pay now* prompt remains about the fee alone. Enforced in `api/src/api/webhooks.ts`.

- **A Promotion can lower the price of a Product a member buys, and only such Promotions are offered** (#1118). A member sees *Apply promotion* on a Product when a Promotion about Products (`applies_to = product`) is active, inside its start–end window, grants that Product, and — if it is for new members only — the member qualifies as new. It is offered only where it prices the Product lower than its regular price and above zero; a `fixed_price` above the Product's price is not a promotion, and a grant that makes it free has no payment to make. The price is the Promotion's treatment applied once to the VAT-inclusive price; a Sessions package is never divided by its units. Enforced in `api/src/domain/memberProductPromotion.ts` and `api/src/api/member-product-promotions.ts`.

- **A Promotion is applied to a purchase at the moment of buying, and the purchase remembers it** (#1118). Tapping *Apply promotion* saves nothing; the purchase request names the Promotion, the offer is re-checked then, and the Promotion's grant (treatment, regular price, discounted amount, and a Periodic grant's Duration) is frozen onto the purchase together with the payment request. A Promotion that lapsed in between is refused as `promotion_not_applicable` rather than charged at a price the gym no longer offers. Staff see the purchase on the Member card's *Products* tab, described as it was recorded — never from the Promotion's current configuration. Enforced in `api/src/api/me-products.ts`.

## Promotions and Plan benefits

- **A Promotion is about either a Membership Plan or a Product bought on its own, and that choice decides what it can configure** (#926). Every Promotion has an *Applies To* of `membership_plan` (the default) or `product`. A Membership Plan Promotion carries a Membership Fee Benefit, a list of Suitable Membership Plans, a Billing & Duration timeline and the Membership Fee Simulation that projects it; a Product Promotion shows none of those and holds only the Products it grants plus their Billing Event Simulation. Switching the target hides sections but discards nothing already stored, and Duplicate copies the target. Enforced in `api/src/domain/promotionTarget.ts`.

- **A Promotion is never configured on a Member; a Member benefits from it through what they are assigned or buy** (#931). The Member card has no Promotions section and no *Add Promotion*. A Member receives a Promotion either because their Assigned Plan was created with it (chosen in the Assign New Plan editor, or applied automatically by the Plans page's Assign) or because they buy a Product the Promotion offers from the Members App. The Promotions an Assigned Plan carries are shown on that Assigned Plan's card, from the snapshot each application took. Enforced in `api/src/api/membership-promotions.ts`.

- **A Promotion that reaches its End Date becomes `expired`; `inactive` is the staff's own decision and stays until they change it** (#900). A Promotion's lifecycle status is `active`, `inactive` or `expired`. A nightly sweep (the third step of the billing workflow) marks an `active` Promotion whose End Date has passed as `expired`, which is the same condition every apply path already refuses; inactive, deleted and already-expired rows are untouched. Expiring changes nothing for members already carrying the Promotion, since they are priced from their own snapshot. The Admin list filters on all three statuses; the editor offers only Active and Inactive, showing an expired row's status as a disabled option. Enforced in `api/src/domain/promotionLifecycle.ts` and `api/src/api/promotion-lifecycle.ts`.

- **A Member is a New Member when they have held no active Membership Plan in the previous 6 months, and that status is computed on every read rather than stored** (#927). The Admin shows it as a Yes/No value on the Member profile and as a badge beside the name in the Members list, and the same 6-month window is the one Promotions use to decide eligibility, so the two can never disagree. A Member who currently holds a live plan is not a New Member. Enforced in `api/src/domain/newMemberEligibility.ts` (the rule) and `api/src/api/new-member-eligibility.ts` (the read).

- **A Promotion is for New Members only unless staff clear that flag** (#634, #927, #1118). Every Promotion is created with *Only applicable for new members* switched on. Every path that applies a Promotion to an Assigned Plan checks the Member against the 6-month rule, leaving the plan being configured out of the count so a Member's own new plan does not disqualify them; a Product purchase and the Members App's plan catalogue use the Member-level status, hiding a new-members-only Promotion from anyone who is not one. Enforced in `api/src/api/new-member-eligibility.ts`.

- **A Promotion's Membership Fee Benefit is a single discount on the Membership Fee that runs for a chosen number of months inside the Promotion's own timeline** (#635, #814, #899). It has an action, a value, an enabled flag and a *Duration* in calendar months, and nothing else: no quantity and no frequency, because there is one Membership Fee per Assigned Plan and how often it charges is the plan's own billing frequency. The Duration cannot exceed Free Period + Paid Duration + Bonus Duration (Pay Beforehand does not lengthen it); the editor offers only the durations the Promotion can carry, plus `—` meaning the whole Promotion, and a Promotion with no months discounts nothing. Exactly one Membership Fee Benefit applies per applied Promotion, and it is the only Promotion benefit that changes the fee — everything else a Promotion gives is a Product grant. Enforced in `api/src/api/promotion-details.ts` (the Duration bound) and `api/src/domain/promotionBenefits.ts`.

- **Applying a Promotion to an Assigned Plan creates an application, and revoking it can be undone by applying again** (#635 stage 9). An Assigned Plan may hold several applications of the same Promotion over time, but only one may be standing (`applied`) at once. Revoking closes the application; applying again creates a new application with a fresh snapshot of the Promotion as it stands that day — the revoked one is never reopened, because its applied/revoked window is what tags the Billing Events it produced. Enforced in `api/src/api/membership-promotions.ts`.

- **An applied Promotion is priced and displayed from the snapshot taken when it was applied, so editing a Promotion later never changes what existing members pay** (#635 §16). Both the Membership Fee Benefit and the Product grants are frozen onto the application; staff screens, the Member's My Membership page and the nightly billing run all read that copy. Only an application made before snapshots existed (migration 149) falls back to the Promotion's live configuration, having nothing else to read. Enforced in `api/src/api/membership-promotions.ts` (fee benefit) and `api/src/api/assigned-plan-snapshot.ts` (Product grants).

- **A Product inside a Promotion or a Membership Plan carries its own treatment — an action and a value — which belongs to that Promotion or Plan, not to the Product** (#896). The same Product can be waived by one Plan and discounted by a Promotion. A Promotion may configure five treatments — *No promotion*, *Waive*, *% Discount*, *Fixed discount*, *Fixed Price* — and the default is no treatment, so a line nobody configured is charged at the Product's normal price. A percentage must be 0–100, an amount non-negative, and an action that takes no value may carry none; anything else is refused. Re-saving a line without mentioning its treatment keeps the stored one, so clearing a treatment is always an explicit *No promotion*. Duplicating a Plan or Promotion, and assigning a Plan to a Member, copy the treatment with the line. Enforced in `api/src/domain/productBenefitActions.ts`.

- **A Membership Plan benefit may only be No benefit, Waive or % Discount; Fixed discount and Fixed Price are Promotion-only** (#1184 stage 1, #896 §16). The Plans page offers the three and the API refuses the other two on a Plan line. The same stored value reads *Benefit* / *No benefit* on a Plan and *Promotion* / *No promotion* on a Promotion. Enforced in `api/src/domain/productBenefitActions.ts`.

- **A treatment prices the whole line — unit price × quantity — and a Promotion's grant is layered on top of the item's own treatment for the periods or units it covers** (#896 stage 3, #916, #919, #920, #924). In every simulation the Plan's own treatment applies to the line for the life of the contract, and each applied Promotion grant is folded on top for the periods or units that grant covers; a one-off or session line hands out its units grant by grant in order and prices whatever is left at the item's own treatment. A grant configured with no treatment covers its periods without moving the price. Every benefit section shows a per-row *Original* (or *Regular*) price and *Final* price, VAT-inclusive, with a Product that has no price reading `—` rather than €0.00; an Assigned Plan's sections show the prices frozen at assignment as *Agreed Price* / *Final Price*. Enforced in `api/src/domain/billingSimulation.ts` (what is charged) and `api/src/domain/planBenefitPrices.ts` (what a row displays).

- **Each Membership Plan benefit is Mandatory by default, and an optional one may be declined when the Plan is assigned** (#1184 stages 2–4). Every Plan benefit line carries a *Mandatory* Yes/No, Yes for every existing and new line; it is the Plan ↔ Product relationship's own flag, distinct from a Product's catalogue-wide Mandatory flag (#832) and from a Promotion line's Requirement. All four assignment paths — staff create, Assign New Plan, the Plans page's bulk Assign and the Members App's Add Plan — accept a list of declined benefits; declining a mandatory benefit, or one the Plan does not carry, is refused outright. A declined line is simply not copied onto the Assigned Plan, so billing and every projection read the accepted set while the Plan itself is untouched, and a non-empty decline is audited as `decline_benefits` against the Assigned Plan. Enforced in `api/src/domain/declinedPlanBenefits.ts` and `api/src/api/declined-plan-benefits.ts`.

- **A Membership Plan's Session Benefit has a renewal Frequency, so `2 | Weekly` means two included classes every week** (#918). The Frequency is Session benefits' alone (not one-off or periodical benefits, not Promotion grants) and is one of `—`, Once, Weekly, Every 4 weeks, Monthly or Yearly; `—` and Once both mean a one-time allowance granted on the start date. It is frozen onto the Assigned Plan at assignment, so changing the Plan later does not move what an existing member was agreed. In the Billing Event Simulation a renewing allowance is summarised onto the billing dates that already exist — a 4-weekly Plan with `2 | Weekly` reads 8 sessions per billing date, a monthly one 5 in a 31-day cycle and 4 in the next, and a cycle with no renewal shows no line — while a Promotion's session grant still grants its units in total. The Frequency is not multiplied into a Member's bookable session balance, and nothing tracks how many renewed sessions have been used. Enforced in `api/src/domain/sessionBenefitFrequency.ts`.

- **A Product inside a Promotion carries a Requirement, mandatory or optional, and today it is only configured, never acted on** (#959). Every Promotion grant line is `mandatory` unless staff mark it `optional`; the value is copied by Duplicate and frozen onto each application's snapshot. Nothing yet prices, projects or offers a member a choice off it — an optional grant is granted and charged exactly as a mandatory one — and it is unrelated to a Product's own Mandatory flag (#832) and to a Plan benefit's Mandatory Yes/No (#1184). Enforced in `api/src/domain/promotionItemRequirement.ts`.

## Calendar, bookings and Professional Services

- **Which members may book an activity is decided by the Professional Services the Activity Type requires, never by their Membership Plan** (#973). Staff name, per Activity Type, the Professional Services a member must hold sessions for; an activity that names none is open to every member. A member qualifies by holding at least one session of any required service, whatever Product granted it. Booking never spends a session. A member who does not qualify is refused with `professional_service_required` and the list of services that would unlock the activity. A service the gym has since switched off stays on the activity until staff remove it. Enforced in `api/src/domain/activityEligibility.ts` and `api/src/api/activity-eligibility.ts`.

- **A member's Professional Service balance adds up sessions from four sources** (#1189). Sessions come from a purchased session package, a Promotion's session grant, an Additional Service added to the Assigned Plan, and the Session Benefits of the member's own Membership Plan — the last counted from the Assigned Plan as it was agreed, only while that plan is `active` and inside its dates (a Draft, Pending Payment, paused or cancelled plan grants nothing). A member covered by a family plan somebody else owns holds that plan's sessions too. The booking gate and the staff view of a member's services read the same balance. Enforced in `api/src/domain/memberProfessionalServices.ts`.

- **A session is spent when the member attends, no-shows or cancels late — never when they book** (#1189). Each spend is one ledger row per booking, so a corrected attendance roll can never charge a booking twice. Plan-included sessions are spent first, then a Promotion's, then an Additional Service's, then a purchased package. Marking a booking `absent` spends it automatically as a no-show; staff may instead choose "return class", which gives the session back and keeps the row as the record. A staff cancellation inside the 24-hour notice window spends the session; a member's own cancellation never does, and a waiting-list place is never spent. A balance of zero spends nothing rather than going negative. Walk-ins and bulk "present" count as attendance. Enforced in `api/src/domain/serviceConsumption.ts` and `api/src/api/service-consumption.ts`.

- **A refused booking sends the member to the Products that would unlock it** (#1189). When the Members App refuses a booking for lack of a Professional Service, the Calendar offers *Buy sessions*, which opens the Additional Products and Services page narrowed to the Products linked to those services, with *Show all products* beside it. The narrowing only filters the catalogue the member could already see and buy; it never shows or sells anything extra. Enforced in `api/src/domain/memberProductCatalogue.ts` and `apps/member/src/lib/serviceRequired.ts`.

- **A member may cancel their own booking while the event is at least 24 hours away, or within 2 hours of having booked it** (#1162). Inside the window the Members App refuses the cancellation (`cancellation_window_closed`) and explains why where the Cancel action was, with a Professional-Service wording when the occurrence delivers or requires one; an event that has already started cannot be cancelled either way. Each booking records the moment the member gained it (*Booked on*, also stamped when a waiting-list place is promoted); a booking with no such record gets no grace period. Leaving a waiting list is allowed at any time until the event starts. Enforced in `api/src/domain/bookingCancellation.ts` and `api/src/api/booking-cancellation.ts`.

- **Every member with a live booking receives one training reminder about 2 hours before the event** (#1113). A scheduled run every 15 minutes alerts each booked member whose event starts within the next 120 minutes and who has not been reminded yet (`booking_reminder_2h`, reading *in 2 hours* in the member's language). A member on a waiting list is not reminded, and a reminder is sent at most once per booking even when a run fires late or twice. Enforced in `api/src/domain/bookingReminders.ts` and `api/src/api/booking-reminders.ts`.

- **A member's own booking actions raise no alert; somebody else acting on their booking does** (#1113, #979, #980). Booking or leaving a class from the Members App sends the member nothing — the only alert a member's cancellation raises goes to the member it promotes off the waiting list (`promoted_from_waitlist`). Staff actions alert the member concerned: added to a waiting list (`waitlist_joined`), taken off one that stays open (`waitlist_removed`), a waiting list switched off (`waitlist_closed`), a class cancelled (`event_cancelled`) or reactivated (`event_reactivated`). Alerts are rows in the member's Alerts page; a push notification is only a copy of one. Enforced in `api/src/api/bookings.ts` and `api/src/api/calendar-events.ts`.

- **An occurrence's Trainer and Space are changed on the occurrence, and the Activity Type's defaults stay as they are** (#980). Staff edit them from the event's own detail panel in Edit mode; the change is refused with the usual `409` when the trainer or space is already taken in that slot, and the space must be active and belong to the occurrence's center. Every change records previous and new values (with names) in the Audit Log, and an edit that changed nothing records nothing. A stored trainer or space that is no longer selectable is still shown, so an unrelated edit cannot fail on it. Enforced in `api/src/api/calendar-events.ts` and `api/src/domain/calendarEventChanges.ts`.

- **Where an activity normally runs is the Activity Type's default Space; a Space lists no activities** (#801). Each Activity Type names its default trainer and default space, and a new occurrence takes them unless staff override it on the occurrence (above). There is no activity list on a Space. Enforced in `api/src/api/activity-types.ts`.

- **An occurrence's waiting list has three settings, and only *disabled* empties it** (#980). An occurrence either follows its Activity Type's waitlist setting, is `closed` (no new joins, but every member already queued keeps their position) or `disabled` (the queue is emptied: every waitlisted member is removed and alerted with `waitlist_closed`, nobody is promoted, and booked members are untouched). The setting is saved together with the queue change, after a confirmation that shows how many members are waiting. Any other value is refused. Enforced in `api/src/domain/waitlistMode.ts`.

- **An occurrence's Eligible Professional Services follow its Activity Type unless staff override them on that occurrence** (#980). By default every occurrence inherits the Activity Type's list, including later changes to it. Staff may give one occurrence its own list — an empty own list means anyone may book that occurrence even when the activity is restricted — or return it to inheriting. Eligibility is therefore checked per occurrence, and the personal-training slot picker shows only slots the member could actually book. The override is audited with the service names before and after. Enforced in `api/src/api/activity-eligibility.ts`.

- **What happened to an event is worked out from the clock and its bookings; staff confirm only the outcomes a person decides** (#977). An event is `scheduled`, `not_used`, `completed` or `cancelled`. A scheduled event that has ended with nobody booked becomes `not_used` by itself; one that ended with bookings stays `scheduled` until staff mark it completed or cancelled, and *Completed · 0 attendees* is a legitimate outcome. A manual calendar entry still in `draft` has no execution status. Both staff transitions are audited with the previous and new status. Members are never shown that a slot went unused. Enforced in `api/src/domain/eventExecutionStatus.ts`.

- **A cancelled session is reactivated, not recreated** (#979). Reactivating is the one way back from `cancelled`: the session returns to `scheduled`, its cancellation reason is cleared (the Audit Log keeps it), and every booking and waiting-list position is exactly as it was, because cancelling never removed them — a member who had cancelled themselves stays cancelled. The slot must still be free of trainer and space conflicts (`409` otherwise). Booked members are alerted (`event_reactivated`); waitlisted members are not. A past cancelled session may be reactivated and is then classified by the rule above. Manual calendar entries have no reactivate action: their status is edited directly. Enforced in `api/src/api/calendar-events.ts`.

- **A calendar event is painted in the gym's colour, the same for every member** (#975, #976). The box takes the occurrence's own colour, else its Activity Type's; an event with no usable colour takes the Theme's event colours. Text on a coloured box is black or white, whichever reads better by WCAG contrast. A member's own booking state never changes the colour, in the Members App or the Admin app. Enforced in `apps/member/src/lib/calendarEventDisplay.ts` and `apps/admin/src/lib/calendarEventPaint.ts`.

- **A member's booking state is text, and a member never sees a slot's operational state** (#976). The Members App shows *Booked*, *Waitlist · Position #2 · 4 waiting* or *Completed* beside an event the member booked, and nothing at all beside one they never booked — a past class they skipped is just a past class. *Cancelled* reaches only a member who held a booking on it, and the waiting-list total appears next to *Booked* only while the list can still move. The Admin calendar shows its states as a status badge rather than a colour. Enforced in `apps/member/src/lib/calendarEventDisplay.ts`.

- **An event box names the occurrence's own trainer and space, and says nothing when one is missing** (#981). The lines under the title come from the occurrence as scheduled (the stand-in trainer when one is set), never from the Activity Type's defaults; a missing trainer or space produces no line and no placeholder. Day and Week views show *Trainer · Space* on one line under the time, activity, status and occupancy; month cells keep only the title, time and badge. Enforced in `apps/admin/src/lib/calendarEventMeta.ts` and `apps/member/src/lib/calendarEventDisplay.ts`.

## Members App

- **A Section Card's shape, border edges and shadow are theme settings** (#1321 stage 1). A gym chooses whether cards have rounded, square or no corners, which edges carry a border (all, none, or one side only) and how strong the shadow is (none to strong); the border's colour and thickness stay their own settings, and the defaults are the card as it already looked. The Theme editor shows a small live card beside each option. Enforced in `api/src/domain/membersAppTokens.ts` and `apps/member/src/lib/memberChrome.ts`.
- **The browser tab names the app, its role and the environment, and nothing is invented when a value is missing** (#1114). A Members App tab reads `(Dev) Members - Cordel.tech Fitness` on the development deployment and `Members - Cordel.tech` on production: the environment label and the brand are deployment settings (`NEXT_PUBLIC_APP_ENV_LABEL`, `NEXT_PUBLIC_APP_BRAND_NAME`), production has no label, and a deployment with no brand configured shows `Members` alone rather than a default brand. The title is English in every language. It is not the installed mobile app's name, which comes from the app profile. Enforced in `apps/member/src/lib/appTitle.ts`.

- **Every colour a member sees comes from the gym's Theme** (#983, #982). Page background, cards, text, titles, inputs, buttons, status pills and the Calendar's own controls all follow the Theme's Members App settings (each of which inherits its Admin counterpart unless overridden), so a gym that changes its Theme repaints the whole app. A status pill is tinted from the Theme's own status colour over the card surface, so it stays readable over a card that carries artwork. Exactly three things are fixed on purpose: the browser's chrome tint, and the two bars that tell a superadmin whose account they are looking at — a gym may not restyle those away. Enforced in `apps/member/src/lib/memberChrome.ts`.

- **Opening the app blanks the screen only when the signed-in identity changes** (#1300). On a cold start the app waits for the sign-in system to load before deciding anything, so the screen no longer flashes blank, loads, and blanks again. The member, their centres and the loading state are reset only when a different member signs in, a superadmin starts or ends an impersonation, or the app is explicitly asked to reload; a refresh for the same member updates the screen in place. Enforced in `apps/member/src/context/AppContext.tsx`.

- **The avatar is a menu on every page, and Log out always confirms first** (#1282). The avatar in the top bar — present on every screen, Profile included — opens a menu showing the member's email, **Profile** and **Log out**. Log out asks for confirmation in the app's dialog; only after the member confirms does the app remove this device's push registration, sign the member out and return to the sign-in page. A superadmin gets Log out too: in the Support bar, which has no avatar because they are linked to no member, and in the avatar menu while impersonating, where confirming ends and audits the impersonation and returns to Support mode, leaving the superadmin signed in. Enforced in `apps/member/src/components/LogoutConfirmDialog.tsx` (the confirmation), `apps/member/src/lib/memberLogout.ts` (the sequence) and `apps/member/src/lib/memberUserMenu.ts` (what the menu offers).

- **My Nutrition is read-only: it shows what the member's plan carries and offers no control** (#932). Its **Dietary Restrictions** and **Nutrition Goals** sections are both lists the member can read but not change — the plan is the gym's to configure. A restriction is always a food from the Nutrition Library, shown with that food's own picture and its name in the member's language. A goal is one of a fixed set of goal items (water, fibre, …) read as a label plus its quantity and frequency, `1 l · daily`, worded the same on My Nutrition and on the Home page's *Today's Nutrition Plan* card. Enforced in `api/src/api/me.ts` (`GET /me/nutrition-plan`) and `apps/member/src/lib/nutritionFood.ts` (the goal wording).

- **A Nutrition Goal may be illustrated by a Nutrition Library food, chosen by staff; otherwise it shows the standard placeholder** (#932). When staff configure a goal on a Nutrition Plan or a template they may pick one Library food whose picture illustrates it; the food must be visible to the gym and not deleted, and a goal on a Base (Cordel) template may name only a System food, because its goals are copied into every gym. The illustration travels with the goal when a plan is duplicated, cloned from Base or created from a template, and clearing it is an explicit action. A goal with no illustration shows the same fallback image the rest of the page uses; nothing guesses a picture from the goal's name. Enforced in `api/src/api/nutrition-goal-illustration.ts`.

## Mobile app (iOS / Android shell)

- **Stage 1 is one generic store app, "Cordel Fitness"; a gym's own app is a second profile of the same shell, never a separate code base** (#1078, #1074). The generic app is published by Cordel: a member signs in and their gym's Theme is applied after login, exactly as on the web. A per-gym app (stage 2, on request) is a new profile file (`apps/mobile/profiles/<id>.json`: app id, display name, server URL, allowed hosts, Google client ids) plus its own store plumbing — its own Bundle ID / package, Google clients, Firebase app, signing identity and store listing — with no code change. Stage 1 ships exactly one profile, `cordel-fitness` (`com.cordel.fitness`), and CI builds a `cordel-fitness-dev` variant (`com.cordel.fitness.dev`) for testing. Enforced in `apps/mobile/src/appProfile.ts`.

- **The app is the deployed Members App inside a native shell, so a web release reaches phones without a store review** (#1074, #1073). The shell (Capacitor 8) loads the live Members App from the profile's `serverUrl`; there is no second front end, and a member can do in the app exactly what they can do in the browser. Only native code, plugins or permissions need a store release. Because the UI is remote, the app is down whenever the web is: the native build shows a splash while the first load completes (close to a minute on a clean install) and an error screen with **Retry** when the API is unreachable — never "you have no gym" — and the retry keeps the member's session. The session survives killing and reopening the app. Enforced in `apps/mobile/capacitor.config.ts` and `apps/member/src/components/NativeAppState.tsx`.

- **An app's identity is never a default: a build with no app id, name or server URL fails rather than installing over another app** (#1074). `appId`, `appName` and `serverUrl` have no fallback in code; each profile field can be overridden by its own `MOBILE_*` environment variable, which is how CI points the generic app at a staging URL without editing a profile. `npm run profile:apply` is the only step that writes the identity into the Xcode and Android projects (Bundle ID / `applicationId`, display name, URL schemes, the app-link host), and it fails loudly when it cannot. The profile's `allowNavigation` lists the hosts the shell may show in-app; any other host opens in the system browser, which is why a Clerk development instance's own host has to be listed or the first launch hands the session to Safari. Enforced in `apps/mobile/src/appProfile.ts` (resolution) and `apps/mobile/src/nativeProjectFiles.ts` (what is written).

- **A plain browser never runs native code, and a native control that cannot work is absent rather than broken** (#1073). The Members App decides whether it runs inside the iOS or Android shell from the native bridge itself (exactly the two platforms the API accepts for device tokens), resolved after the page has mounted so the server-rendered page and the app agree. Where no bridge exists, or the build carries no Google client ids, the sign-in page shows the ordinary email-and-password form and nothing native; a plugin the installed shell does not have loads as absent rather than taking the page down, so a web release newer than the shell on a member's phone keeps working. Enforced in `apps/member/src/lib/native.ts`.

- **In the app, "Continue with Google" opens the native Google sheet instead of leaving for the browser** (#1073, #1285, #1077). Clerk's own Google button keeps its logo, label and place, but a tap in the native app opens the system Google sign-in sheet and the session lands inside the app — the web button, which hands the session to Safari, is unusable in a WebView. The exchange with Clerk is three calls: the Google session is cleared before every login (otherwise a previous member's token is replayed and refused), the token is requested with a fresh nonce (Android tokens are refused without one), and the returned sign-in is completed so the session activates and the app navigates. A dismissed sheet is not an error; a refusal is shown under the notice. Enforced in `apps/member/src/lib/useNativeGoogleSignIn.ts`.

- **Sign in with Apple exists on iOS only, is off by default, and is not yet verified against Clerk** (#1075). App Store guideline 4.8 asks for an equivalent login when an app offers Google, so the shell carries an Apple button beside Google's on iOS. It renders only when the Members App build enables it (`NEXT_PUBLIC_APPLE_SIGN_IN`) and the profile enables the Sign in with Apple capability (`appleSignIn` / `MOBILE_APPLE_SIGN_IN`), because a build declaring the capability without it fails to sign. The Clerk token exchange is written as a hypothesis and awaits a spike with a real Apple developer account and a physical iPhone. Enforced in `apps/member/src/lib/nativeSignIn.ts` and `apps/member/src/components/NativeAppleButton.tsx`.

- **An invitation names the member it is for, so a sign-in with a hidden (relay) e-mail address still links to the right Member** (#1075). Apple lets a user hide their address and returns `…@privaterelay.appleid.com`, which does not match the address the gym invited. Invite and Re-invite therefore stamp the Clerk invitation with the gym and the Member it was issued for, and linking a new login matches that stamp first and the e-mail address second. Invitations issued before this rule carry no stamp and still link by e-mail; the guard against linking a staff login as a member applies on both paths. Enforced in `api/src/domain/memberInviteTarget.ts` (matching) and `api/src/api/me.ts` (`POST /me/link`).

- **The app registers for push on every sign-in and unregisters before every sign-out, and a tapped notification opens the Alerts page** (#1073, #1282). Once a signed-in member is known, the native app asks for notification permission and registers this device under the installed app's own id (a dev build files its tokens under `com.cordel.fitness.dev`); registering again is harmless. Removing the registration is an action of the member who owns the device, so it runs before the sign-out that would end that session. Tapping a push opens `/notifications`, the page listing every alert, never a per-type screen; a push arriving while the app is open refreshes the unread badge. Enforced in `apps/member/src/lib/nativePush.ts`.

- **A push is a courtesy copy of an alert, never a condition of it** (#1072). Every alert is written to the member's notifications first and shown in the Members App from there; the push is sent afterwards and nothing waits for it, so a deployment with no push credentials, an unreachable Firebase or a member with no registered device costs only the push. The push carries the alert's title and routing data and no sentence — the wording a member reads is the Members App's, in their language. A device registration is deleted only when Firebase says it can never work again (`UNREGISTERED`, `SENDER_ID_MISMATCH`); a malformed message, a rate limit or a server error leaves it in place. Enforced in `api/src/infra/push.ts` over `api/src/domain/pushDelivery.ts`.

- **A device registration identifies an app installation, not a person: a shared handset belongs to whoever signed in last** (#1072). `POST /me/devices` takes a platform (`ios` or `android`), the push token and the app id; the token is unique across the whole platform, and registering a token already on file re-points it to the member now signed in, so one phone never receives two members' alerts. An unknown platform, a blank token or an over-long value is refused with a 400. `DELETE /me/devices/:token` removes only the caller's own registration — another member's token answers 404. Enforced in `api/src/domain/deviceTokens.ts` (what is accepted) and `api/src/api/me.ts` (the routes).

- **Push credentials are configured per app id, and an app with none is skipped rather than failed** (#1072, #1074). `FCM_SERVICE_ACCOUNTS` on the API is one JSON object keyed by app id, each value a Firebase service account; a second (per-gym) app is a new key. A token whose app has no entry is simply not pushed to. On iOS, delivery works only once the Firebase Messaging package has been added to the Xcode project — until then iOS registers a token Firebase cannot deliver to. An Android build without its `google-services.json` installs and runs normally and simply receives no push; it no longer crashes on first sign-in. Enforced in `api/src/infra/push.ts` (credential resolution) and `apps/mobile/ios/App/App/AppDelegate.swift` (the iOS token).

- **An invitation link tapped on a phone opens the app when the domain publishes the app and the app declares the domain; with neither configured it opens in the browser and completes there** (#1076). The Members App serves `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json` from `MOBILE_APP_ASSOCIATIONS`, one JSON object keyed by app id naming each app's Apple Team ID and Android SHA-256 signing fingerprints (Play App Signing's fingerprint included). Either platform may be omitted. A malformed entry is dropped and logged and costs only that app its links; a file with nothing to publish answers 404 rather than an empty document. The app's side — the iOS associated domain and the Android App Links host — is derived from the profile's `serverUrl`. Enforced in `apps/member/src/lib/appAssociations.ts` (the files) and `apps/mobile/src/nativeProjectFiles.ts` (the app's declaration).

- **The app claims only the invitation path, never the whole domain** (#1076). Only `/{locale}/link?gym_id=…&__clerk_ticket=…` opens the app; every other Members App URL — including the OAuth and Clerk redirects a sign-in bounces through — stays in the browser, so a link the app took at the wrong moment could never strand a sign-in. The app's own URL scheme (defaulting to the app id, `com.cordel.fitness://…`) stays registered beside it for links a universal link misses: an in-app browser that does not trigger one, or a build whose domain is not yet verified. Enforced in `apps/member/src/lib/appAssociations.ts` (`APP_LINK_PATH_SEGMENT`) and `apps/member/src/lib/native.ts` (`appUrlOpenPath()`).

- **A Clerk invitation e-mail never opens the app by itself, so the link page offers "Open in the app" before redeeming the ticket** (#1076, #1077). Clerk's invitation button points at Clerk's own domain and redirects to our `/link` page, and a redirect does not trigger a universal link. On a phone's browser holding an invitation ticket, `/link` therefore shows **Open in the app** / **Continue in the browser** *before* the single-use ticket is redeemed; the first opens the app through its URL scheme (`NEXT_PUBLIC_MOBILE_APP_SCHEME`), and the choice is not offered when no scheme is configured. Some in-app mail browsers never hand a link to the app at all, so the invitation always completes in whichever browser has it. Enforced in `apps/member/src/lib/openInApp.ts`.

- **Internal test builds are published by CI and listed in Cordel → Mobile builds; an iPhone gets a TestFlight link, not a file** (#1077). A manual run (choosing the `dev` or `pro` environment), a `mobile-v*` tag or a change to the shell's own files builds the Android debug APK and uploads it to `cordel/mobile-builds/<app id>/android/`, keeping the newest 20 per app; a pull request builds it as a check but publishes nothing, and the iOS simulator build is a CI check only and is never published. The superadmin-only page lists the Android builds with a download and shows an *Open in TestFlight* button that is disabled until `MOBILE_TESTFLIGHT_URL` is set. Each build is numbered from `apps/mobile/package.json`'s version and the CI run number. These are debug builds against the dev backend and are not what a gym receives. Enforced in `api/src/domain/mobileBuilds.ts` and `.github/scripts/publish-mobile-build.sh`.

- **A gym that wants its own store app publishes it from its own developer account, pays the store fees, and is told in writing that approval is not guaranteed** (#1078). The gym owns the app and the accounts (Apple Developer Program 99 USD/year plus a D-U-N-S number for an organisation; Google Play 25 USD once); Cordel builds and uploads it from a new profile. Apple may reject template-like apps (guidelines 4.2, 4.2.6, 4.3), so the first gym is a pilot. A gym's beta is a release build of its own app id against production, handed out through TestFlight or a Play testing track — never the Cordel Mobile builds page. Stated in `docs/mobile-app.md` §4 (a plan, not enforced in code).

## Nutrition & Goals

- **The Nutrition Library holds three separate catalogues: Foods, Personal Goals and Nutrition Goals** (#947, #948). A Personal Goal is what the Member wants to achieve (Weight Loss, Muscle Gain, Performance…); a Nutrition Goal is what a plan should target nutritionally (Calories, Protein, Water…). Each row is either a System row — owned by the platform, seeded with seven goals per kind, administered from Cordel and read-only for every gym — or a gym's own row, which only that gym sees and edits. A deleted goal's name can be reused; a live duplicate name is refused. Nutrition Goals are catalogue-only today: nothing assigns one to a Nutrition Plan yet. Enforced in `api/src/domain/goalLibrary.ts`.

- **Personal Goals are their own section of the Admin app; Nutrition Goals are a tab of the Nutrition Library** (#948). A gym manages Personal Goals at `/personal-goals` (Cordel manages the System ones at `/cordel/personal-goals`) under the *Nutrition & Goals* navigation group, behind the gym's own `nutrition.personal_goals` feature flag, so a gym can switch Personal Goals off without hiding its Foods. Nutrition Goals sit beside Foods as the Library page's second tab and follow the Library's flag. A Personal Trainer may read and write Personal Goals but not Nutrition Goals (#1070). Enforced in `api/src/domain/goalLibrary.ts`.

- **A Personal Goal can carry a measurable target: a number and a free-text unit** (#1034). A unit with no value is refused; a value with no unit is accepted as incomplete. The seeded System goals come with a target where one makes sense — Weight Loss 3 kg, Weight Gain 3 kg, Muscle Gain 2 kg, Maintenance 0 kg — and none for Performance, Recovery and Energy, whose target reads `—`. Nutrition Goals have no target values yet. Enforced in `api/src/domain/goalTarget.ts`.

- **A Personal Goal can have one PNG image of at most 512×512 pixels, uploaded from Edit mode** (#1035). The file is checked by its bytes (PNG signature and dimensions, up to 2 MB), a rejected upload leaves the current image untouched, and replacing an image overwrites it in place. A gym uploads images only for its own goals and Cordel only for System goals; a gym goal never borrows the System goal's picture, and nothing is seeded, so a goal starts without one. The create form offers no image control. Enforced in `api/src/domain/personalGoalImages.ts`.

- **A gym can activate or deactivate any Personal Goal it sees, System goals included, for itself alone** (#1181). A goal with no gym decision is active, so a System goal Cordel adds later is available everywhere at once. Deactivating only prevents *new* assignments: the catalogue still lists the goal as *Inactive*, every picker stops offering it, assigning it answers `409 goal_inactive`, and the Members already holding it keep their assignment. Gym A's deactivation changes nothing for Gym B or for the platform. Enforced in `api/src/domain/goalLibrary.ts` and `api/src/api/goal-library.ts`.

- **A gym can duplicate any visible Personal Goal, a System one included, into a goal of its own** (#1181). `⋮ → Duplicate` creates `<name> - Copy` as a gym-owned, active goal with the source's name, description and target, plus its own copy of the image; a second duplicate of the same goal is refused (`409`) until the copy is renamed. The copy is fully editable and independent of the source. Enforced in `api/src/api/goal-library.ts`.

- **An Assigned Personal Goal is a snapshot of the catalogue goal, with a per-Member target** (#948, #1034). Assigning a goal copies its name and target onto the assignment, and staff may override the target value for that Member (so three Members can pursue one goal at three targets); it also records a start date, a target date, a progress status and notes. Renaming or retargeting the catalogue goal afterwards changes no existing assignment. Any System goal is assignable by every gym; a deleted goal by nobody. Enforced in `api/src/domain/personalGoalAssignment.ts`.

- **A Member holds at most one live, in-progress assignment per goal, and progress has three states** (#948). Status is `in_progress`, `achieved` or `abandoned`; removing an assignment is separate from its status, so a removed goal keeps the progress it had. Assigning a goal the Member already pursues is refused (`409`), while an achieved or abandoned goal can be assigned again. The Member and the goal on an assignment never change — re-pointing is a remove plus a new assignment. Goals never affect pricing, billing, bookings or Nutrition plans. Enforced in `api/src/domain/personalGoalAssignment.ts`.

- **Staff manage assigned goals from the Assigned Personal Goals page, the Member card and the catalogue itself** (#948, #1034). `/assigned-personal-goals` lists every assignment of the gym; the Member card's *Personal Goals* tab edits one Member's (controls appear in Edit mode only); and the gym's Personal Goals page offers `⋮ → Assign goal to member`, which preselects the goal, pre-fills its target and lets staff adjust the unit before saving — disabled for a deactivated goal, and absent from Cordel's Base library. Enforced in `api/src/api/member-personal-goals.ts`.

- **A Member manages their own goals from My Goals in the Members App** (#1036). The screen exists only where the gym enables both `member_web.my_goals` and Personal Goals. A Member can add any active goal they do not already pursue (the picker hides retired, inactive and already-held goals), set their own target, start and target dates and notes, and remove a goal — but cannot create goal definitions and cannot set progress status, which is the staff's; removing the goal is how a Member ends it. Removed, achieved and abandoned goals move to *Past Goals*. Enforced in `api/src/api/me-personal-goals.ts`.

- **An assignment's end date is stamped automatically, never typed** (#1036). The day a goal stops being live and in progress — removed, marked achieved or abandoned — is recorded as its end date; the first such date is kept, and it is cleared if the goal is pursued again. Who acted is recorded as staff, superadmin or member (a superadmin impersonating a member is recorded as superadmin). Enforced in `api/src/domain/personalGoalAssignment.ts`.

- **A goal's readings are an append-only history of measurements in the goal's own unit** (#1037). Staff and the Member each add readings (a number plus a date defaulting to today) from their own screen; a date in the future is refused and a date-only value counts as midnight UTC. Readings can be neither edited nor deleted, removing the goal leaves them in place, and an initial reading given at assignment is saved with it. Enforced in `api/src/domain/goalReadings.ts` and `api/src/api/goal-readings.ts`.

- **Setting a new initial reading starts a new period without erasing anything** (#1037). An initial reading is a measurement flagged as the baseline; it is added through a separate action from an ordinary reading, so a client cannot re-baseline a goal by accident. The latest flagged reading is the active baseline (the earliest reading when none is flagged), every reading belongs to the period opened by the baseline before it, and the history marks the first boundary *Initial* and later ones *New initial reading*. Enforced in `api/src/domain/goalReadings.ts`.

- **Progress is a percentage computed on every read, never stored** (#1037). It is `(initial − latest) ÷ (initial − target) × 100`, which works for losing and gaining alike, rounded to one decimal and clamped to 0–100. A goal whose target equals its baseline is maintenance: 100% while the latest reading still equals the target, 0% otherwise. With no readings or no target the figure is not computable and reads `—`, never `0%`. The header also shows the initial reading, the latest reading and the target. Enforced in `api/src/domain/goalReadings.ts`.

- **Each goal with readings draws one line chart, the same in both apps** (#1037). The chart changes colour at every initial-reading period, shows the target as a dashed reference line (no target, no line), and shows nothing at all for a goal with no readings. Points are tappable, and zooming never captures the page scroll. Enforced in `apps/admin/src/components/personalGoals/goalReadings.ts` and `apps/member/src/lib/memberGoals.ts`.

- **In the Members App each goal is a collapsed card, created and edited in place** (#1115). `+ Add personal goal` opens a draft card at the top with today as start date; `⋮ → Edit` turns a card into the same form; Cancel discards the draft or leaves the card as it was. The unit is read-only because it is the gym goal's — clearing the target clears the unit with it. Add reading and Remove are on the card's `⋮`; removal asks for confirmation. Enforced in `apps/member/src/lib/memberGoals.ts`.

- **A meal item's Food Type offers seven types in a Nutrition Plan Template and four in a Member's plan** (#294, #812). A template meal item may be `main_dish`, `side`, `sauce`, `drink`, `dessert`, `other` or `additional`; an item of an assigned plan only `main_dish`, `side`, `sauce` or `additional`. The selector on each screen offers exactly the set that screen accepts. A Nutrition Library food's own type is its list of categories, not a single value. Enforced in `api/src/domain/nutritionComponentTypes.ts`.

- **A Nutrition Library food has one image, uploaded from Edit mode and replaced in place** (#1035). The create form offers no image. For a System food Cordel uploads a PNG of exactly 512×512 with transparency; for a gym's own food the gym uploads a PNG, JPEG, WebP or GIF of up to 5 MB, and a gym may not change a System food's picture. Nothing is written until the file passes validation, so a rejected upload leaves the existing image. Enforced in `api/src/domain/baseNutritionImages.ts`.

## Training and exercises

- **The Base Exercise catalogue is imported from the Free Exercise DB by an operator, never by a gym** (#964). The import is a script (`npm run exercises:import-free-db`, or the `exercises-import` GitHub workflow against a deployed database, dry-run by default) and it writes only platform-owned Base Exercises: a gym's own exercises, training plans and assigned plans are never touched. An exercise is matched by its source id first, then its slug, then its exact name; a name already claimed by a different source exercise is reported as a possible duplicate and never merged, and a Base Exercise an administrator deleted is skipped rather than brought back. Enforced in `api/src/domain/freeExerciseDb.ts` and `api/src/scripts/import-free-exercise-db.ts`.

- **Re-running the import never overwrites what an administrator has edited, and never imports a picture** (#964). An update only fills an empty name or description, keeps the source facts in step (provenance, slug, `category`, `equipment`, `level`, `mechanic`, `force_type`) and adds missing muscle links without removing any, so a second run reports every exercise as unchanged. The dataset's images are ignored: a Base Exercise has no artwork until someone uploads it in Cordel. Source metadata is stored word for word (there is no exercise-level "Exercise Type"; the type-like list is the `equipment` axis), a muscle the catalogue already knows under another name reuses that key (`quadriceps` → `quads`, `abdominals` → `core`), and an unknown muscle is kept and reported rather than failing the import. Exercise names arrive in English only. Enforced in `api/src/domain/freeExerciseDb.ts` and `api/src/domain/muscles.ts`.

- **The three exercise lists are filtered by the server and show everything that matches, with no pages** (#969). Base Exercises (Cordel), the gym's Import picker and the gym's own Exercises share one filter vocabulary: text search (name, and slug where the exercise has one), muscles with a *Match any/all* and *Role any/primary/secondary* qualifier, Status, and the Equipment and Category dropdowns. Those two dropdowns offer only the values present in the exercises on screen, and a dropdown with nothing to offer is not shown — a gym with no imported metadata sees Search, Muscles and Status alone. An unknown Status or match value is refused (400); an unknown muscle key simply matches nothing. Enforced in `api/src/domain/exerciseListFilters.ts`.

- **Re-importing a Base Exercise is how a gym gets the System image and video back** (#719). The gym's *Import* action reports each exercise as `imported` (a new copy), `refreshed` (the gym already had it, and its media links were updated to the Base Exercise's current ones) or `skipped`. The image pair and the video pair are refreshed independently, and a Base Exercise that has no image or no video restores nothing — media the gym uploaded itself is never deleted by an import. A refresh changes media only: the gym's edited name, description and defaults are kept, and an exercise the gym created still reads as Custom. There is no other "restore System media" action and no automatic fallback. Enforced in `api/src/domain/exerciseMediaImport.ts` and `api/src/api/exercises.ts`.

- **A result type belongs to each exercise inside a workout; a block records at most one free-text result in a declared unit** (#966, #1009, #1232). Each exercise instance in a workout template or plan carries its own result type and targets (per-set, typed results go in the exercise logs), and a block has none to snapshot. A block of type Circuit, EMOM, AMRAP or Tabata may be given an optional *Result Unit*; every other block, and every block created before #1232, records no overall result. When a member logs a block the unit is copied onto the log so the number stays readable after the block is reconfigured; a value on a block with no unit is refused and a value that does not fit the unit is refused, while an empty value is always accepted — marking a block done never depends on entering a result. Duplicating a template, building a plan from one or assigning it copies the unit. The Members App shows no result input for a block without a unit. Enforced in `api/src/domain/blockResultUnits.ts` and `api/src/api/me.ts`.

## Stored media (Cloudflare R2)

- **Every stored picture and video lives in its owner's own folder, and an operation never deletes an object outside that folder** (#716, #717, #719, #1035). A gym's media sits under the gym's storage prefix; platform media (Base Exercises, Base Themes, System foods and goals) sits under `cordel/`. Before deleting anything a gym operation checks that the object is under its own prefix — a System object, another gym's object or an external URL is left alone — and a platform operation checks that it is under `cordel/`. Because Duplicate, Clone and Import copy media *links* rather than files, an object is also kept while any other non-deleted exercise, in any gym, still points at it through any of its four media columns. Public URLs are served from the bucket's public origin (`CLOUDFLARE_R2_PUBLIC_URL`); rows written before that origin existed may still hold the older private form until `npm run storage:rewrite-urls` is run, so "same object" is decided by key, not by comparing URL strings. Enforced in `api/src/domain/exerciseMediaReferences.ts` and `api/src/infra/storage.ts`.

- **A Gym Exercise's image is a 2048×2048 master plus a 512×512 thumbnail, both PNG, square and with transparency** (#719). The browser produces the thumbnail and uploads both files together; the server checks each file's actual bytes (PNG signature, exact square, alpha channel) rather than its name or declared type, and if either fails nothing is uploaded and nothing changes, so a bad upload can never replace good media. Removing the image leaves the exercise with none — it does not fall back to the Base Exercise it was imported from — and uploading or removing media never changes whether the exercise reads as System sourced or Custom. A Base Exercise cannot be edited through the gym's routes (403). Enforced in `api/src/domain/exerciseImages.ts` and `api/src/api/exercises.ts`.

- **A Gym Exercise's video is an MP4 plus a 512×512 poster frame, validated as a real video file** (#719). The file is read as MP4 structure (a video track must be present), so a QuickTime file renamed `.mp4` or an audio-only file is refused; the poster is a square PNG that need not be transparent. The maximum size is the deployment's `EXERCISE_VIDEO_MAX_MB` (default 50, never above 200). All the image rules apply: both files in one request, all-or-nothing validation, ownership-aware deletion, no fallback to the Base Exercise, System sourced stays System sourced. Enforced in `api/src/domain/exerciseVideos.ts` and `api/src/domain/mp4Video.ts`.

- **A Base Exercise's image and video are the same pairs, uploaded from Cordel into the platform folder** (#716, #717). Only a superadmin can upload or remove them (`cordel/exercises/images/…`, `cordel/exercises/videos/…`), with exactly the validation a gym's upload gets; the video's poster is mandatory, because an imported copy has nothing else to show. A Base Exercise has no artwork until an administrator uploads it — nothing is generated and nothing substitutes another image. Deleting platform media first checks that no exercise in any gym still links to the object, since every gym that imported the exercise points at the platform's own file. Enforced in `api/src/domain/baseExerciseImages.ts` and `api/src/domain/baseExerciseVideos.ts`.

- **An upload button is disabled, with the reason shown, whenever the gym's storage cannot be written to** (#823). Two states block it: the deployment has no Cloudflare R2 configured (*not configured*), or this gym's storage folder has not been initialized yet (*not initialized* — the API refuses the upload with 409 until Gym Bucket Initialization has run). Only the upload is blocked: the current image, *Remove*, the accepted formats and the size limits stay visible. Platform media (a Base Exercise, a Base Theme) is never blocked by the selected gym's storage state. Enforced in `apps/admin/src/lib/gymStorageReadiness.ts`.

- **A failed storage save says which step failed, why, and what to do** (#828, #1042). The error names the step (upload, delete, folder creation, settings save…) and the object path it was working on, plus one of six causes: `not_configured`, `not_initialized`, `not_found`, `access_denied`, `invalid_file` or `unreachable`. The cause comes from what the storage service actually answered, not from the step that was running. An *Initialize bucket* button is offered beside the error only for `not_initialized`; a permission or network failure never suggests re-initializing. Enforced in `api/src/domain/storageFailureCause.ts` and `apps/admin/src/lib/storageErrorMessage.ts`.

- **A Theme's logo is a file in the Theme's own folder, one per Theme, never bytes in the database** (#824, #829). A Custom Theme's logo is stored at `<gym prefix>/themes/<theme>/logo/logo.<ext>` and a Base Theme's at `cordel/themes/<theme>/logo/…`; the extension comes from the validated file type, not the uploaded name. Replacing a logo deletes only the previous object of that same Theme — a sibling Theme's logo is untouched. A gym whose storage has not been initialized cannot upload one (409); the platform side has no such step. Logos stored under older keys (or as database bytes, from before #829) keep rendering until they are next replaced, which is what moves them. Enforced in `api/src/domain/themeLogo.ts` and `api/src/api/gym-themes.ts`.

- **Saving a Theme attempts every asset and keeps the failed ones queued for the next Save** (#830). The logo and each Members App background image are uploaded or removed one by one: a rejected `training` image does not stop `nutrition` from being saved, each failure is shown beside its own control, and a failed asset stays pending so pressing Save again retries it without re-uploading what already succeeded. The one step that aborts the whole save is the Theme settings themselves, because the asset file names are built from the Theme's saved name. The same behaviour applies to a gym's Custom Themes and to Cordel's Base Themes. Enforced in `apps/admin/src/components/themes/themeAssetSave.ts`.

## Themes and branding

- **A Custom Theme is created by cloning, and only when the gym's storage is ready** (#712, #827). A gym's Theme is a clone of a Base Theme (administered in Cordel) or of another of the gym's own Themes. Before the Theme is written the API checks the gym's Cloudflare storage: with no storage configured the request answers 503, with the gym's bucket not yet initialized it answers 409, and in both cases no Theme is created. The Theme's own folder (with its `logo/` and `members_app/` leaves) is created first, then the Theme itself, which records who created it; that name is shown in the Custom Themes header. Enforced in `api/src/api/gym-themes.ts` over `api/src/domain/themeFolders.ts`.

- **Cloning a Theme copies its logo and its background images, so the clone and its source are independent** (#1041). Every asset the source Theme owns is copied into the clone's own folder before the clone exists; if any copy fails the clone is not created (a 502 naming the asset) and the copies already made are removed. Afterwards, replacing or removing an asset on either Theme leaves the other untouched. Cloning a Base Theme into a gym reads the platform's files and writes only into the gym's folder; cloning a Base Theme into another Base Theme in Cordel copies no assets. Enforced in `api/src/domain/themeAssetClone.ts`.

- **Initialize bucket on a Theme recreates its folders and changes nothing else** (#828). Both a gym's Theme and a Base Theme in Cordel offer the action in their `⋮` menu. It writes the Theme's folder markers only: no image is read, deleted or replaced and no setting of the Theme changes. On a gym whose bucket has not been initialized the action is disabled with the reason shown, and the API answers 409. Enforced in `api/src/api/gym-themes.ts` and `api/src/api/themes.ts`.

- **A Theme's Center assignments are one list, saved as a whole** (#985). Each Center either has its own Theme or follows the Gym Default. The Theme card lists every Center of the gym with a checkbox: ticking assigns the Theme, unticking returns the Center to the Gym Default, and *All Centers* is simply every box ticked. Save replaces the whole set in one transaction (an empty set is a valid save), and a Center pointing at a different Theme is left alone. Only an Active Theme may be assigned (a draft or inactive one answers 400), but an inactive Theme can still be cleared off its Centers. A Center that follows the Theme because it is the Gym Default shows an *inherited* tag rather than a ticked box. A Base Theme has this section too, since the assignments are the gym's even when the configuration is the platform's. Enforced in `api/src/domain/themeCenterAssignments.ts`.

- **Members App theme settings inherit from the Admin settings until a gym overrides them** (#833). Every Members App setting names the Admin setting it follows (*Application Surface* follows the modal background, *Input Background* the input background colour, and so on). Only an overridden setting is stored; an untouched one follows the Admin value as it changes later, and *Restore inherited value* removes the override. A new or cloned Theme starts with no overrides. Inheritance is decided per setting, so overriding one never affects another, and an unusable stored value falls back to the inherited one. Both Theme screens (a gym's Custom Themes and Cordel's Base Themes) use the same editor under the Theme's own Save/Cancel; there is no Members App preview in the Admin app. Enforced in `api/src/domain/membersAppTokens.ts` (validation) and `apps/member/src/lib/membersAppTokens.ts` (resolution).

- **Typography and Section Card text are Members App settings, and a setting with no Admin counterpart has a default instead** (#1152). *Typography (Members App)* gives each of the three Titles a Color and a Font Family, and the Admin's Typography Font Family reaches the Members App through them. The Section Cards section holds the card text's Color, Size (8–48 px), Font Family, Vertical Position (top, center, bottom) and Horizontal Position (left, center, right). Size and the two positions have nothing in the Admin app to inherit from, so they ship with a default — 13 px, centred both ways — and the editor reads *Default value* / *Restore default value* for them. Every navigation tile on the dashboard follows these five values. Enforced in `apps/admin/src/lib/membersAppTokens.ts`.

- **Buttons, inputs and the Calendar's two areas are Members App settings too** (#1212, #1283, #1213, #1214). *Buttons (Members App)* holds the Primary and Secondary button colour and each one's text colour, inheriting the Admin button settings, so every button in the Members App follows them. *Inputs (Members App)* holds the text-input background. The Calendar's open hours are painted with *Calendar Active Area Background* and its closed hours and holidays with *Calendar Inactive Area Background*, both Admin Global Style settings that the Members App inherits per setting. Enforced in `apps/admin/src/lib/membersAppTokens.ts`.

- **A Theme carries eight Members App background images, one per fixed slot** (#725, #732, #1038, #1158). The slots are `training`, `nutrition`, `calendar`, `bookings`, `next_bookings`, `membership`, `personal_goals` and `background`, uploaded under *Members App → Images* on the Theme card; each slot is labelled with the Members App section it paints (`membership` reads *My Products*). An upload is validated by the file's own bytes, never its declared type. A Base Theme's slots are uploaded in Cordel and seen by every gym using it; a gym's Theme never reads another Theme's images. Removing an image clears the slot, and an empty slot means the Theme's background colour and nothing else — there is no fallback to another image. Enforced in `api/src/domain/themeMemberImages.ts`.

- **Which slot paints which screen is one fixed map** (#728, #984, #1036, #1158). The `background` slot paints every Members App page that has no slot of its own (home, profile, notifications, payment, and the Calendar page), under a light scrim so the page's text stays readable. My Training takes `training`, My Nutrition `nutrition`, My Bookings `bookings`, My Products & Services `membership` and My Goals `personal_goals`. `calendar` paints the dashboard's Calendar tile only — the Calendar page is styled by the Calendar's own theme settings instead — and `next_bookings` paints only the dashboard's My Next Bookings card, never the My Bookings page. Enforced in `apps/member/src/lib/membersBackground.ts`.

- **A Section Card's artwork is shown at full opacity and replaces the tile's default icon** (#982, #728). On a dashboard tile or a section card the uploaded image is the surface itself: no overlay, fade or colour blend is applied, so a dark photograph reads dark rather than washed out. A tile shows its default icon only while its slot has no image; uploading one replaces the icon and removing it brings the icon back. The one label the card carries follows the Section Cards text settings above. Enforced in `apps/member/src/components/MembersSectionCard.tsx`.

- **The dashboard's My Products & Services and My Next Bookings cards are tiles of the same grid** (#1116, #1218, #1158). My Products & Services sits beside My Goals, painted by the `membership` slot, and reads `{plan} ({status})` or *No plan* followed by `{N} additional products` — the Products the member has bought and still holds; it opens the My Products & Services page. My Next Bookings is painted by `next_bookings`, takes the ordinary card surface when no image is configured, and with no upcoming booking says only that there are none, since the Calendar tile is where a member books. Enforced in `apps/member/src/app/[locale]/page.tsx`.

- **Reloading the Admin app paints the last applied Theme, not the default one** (#1299). The gym's Theme is only known after sign-in and the gym list have loaded, so the app remembers the variables it last applied, per gym, in the browser and replays them before the first paint whenever the remembered gym is the one selected. While the gyms are loading nothing is painted, so the default blue never flashes before a gym's colours. Enforced in `apps/admin/src/lib/themeSnapshot.ts`.

- **Every chart takes its colours from the Theme of the screen it sits on** (#1037 stage 4). Both apps draw charts through one shared charting layer whose palette, grid, axis and tooltip colours are read from the Theme (a Center's own Theme reaches a chart on its page); a series beyond the palette repeats it rather than inventing a hue. A change of period on a line is a change of colour, never a gap in the line; the curve is drawn so it never overshoots a recorded value; the tooltip opens on tap as well as hover; and the mouse wheel scrolls the page rather than zooming the chart, which zooms by drag or pinch inside it. Enforced in `shared/charts/src/chartTheme.ts`.

## Admin app conventions

- **Expanding a list row reads; `⋮ → Edit` writes, in an inline form** (#797, #800, #805, #816, #897, #957, #1029). An expanded card shows the entity's fields as values and holds no control of any kind; `⋮ → Edit` is the single way into the form, which opens inside the row — never in a modal — seeded from the row on screen, with its own error line and Save/Cancel, and stays open with the typed values if the save fails. `+ Add <entity>` opens that same form as an inline card at the top of the list. Inside Edit mode a card's sections offer their own *Edit*, add and remove actions, and those are absent outside it; Cancel leaves the mode and discards every open section editor. A field only some rows may edit (a System Product's name and type) is shown as a value in both modes. The pattern is documented in `docs/feature-patterns.md`; the menu is `apps/admin/src/components/ContextMenu.tsx`.

- **`⋮ → Details` carries the audit information and the View Audit Log link** (#799, #965). The Details view of any entity shows its internal id, who created, modified and deleted it and when, and a *View Audit Log* button that opens the Audit Log filtered to that one record. None of that appears on the expanded card or in the Edit form. For a shared platform catalogue row (a System food or Base Exercise) a gym sees the dates but not the platform actor's name. Enforced in `apps/admin/src/components/ViewAuditLogButton.tsx`.

- **Red in a `⋮` menu marks a destructive action and nothing else** (#802). *Deactivate* and *Delete* read in red; *Activate*, *Duplicate* and *Details* never do. A user without write permission sees the write items disabled, with the reason as a tooltip. The order of a menu is each page's own (Professional Services: Duplicate, then Deactivate/Activate, then the rest, with Details always last). Enforced in `apps/admin/src/components/ContextMenu.tsx`.

- **The Member card is five tabs, and the tab is part of the link** (#961, #1051). An expanded Member shows Profile · Products · Nutrition · Personal Goals · Training Plan. Profile holds the Member's own fields and their login; Membership Plans is the first section of Products, followed by the Member's bought Products and services; the other tabs hold what their names say. `⋮ → Edit` switches to Profile before opening the form, and switching tabs discards nothing typed. The selected Member and tab are mirrored in the URL (`?member=…&tab=…`), an unknown tab falling back to Profile; there is no separate Member page. Enforced in `apps/admin/src/app/[locale]/members/memberTabs.ts`.

- **An Assigned Plan reads the same on the Assigned Plans page and on the Member card** (#958, #1051). Both screens render the same list (columns, Status badge, expand chevron) and the same expanded body: the frozen configuration, the applied Promotions, the additional Products and `⋮ → Details`. On the Member card the Plan's name identifies the row (the Member is already known), Active and Past plans are two lists, and the row's actions are *Assign New Plan* · *Cancel Plan* · *Details*, with *Details* alone on a past plan; editing an assignment happens on the Assigned Plans page only. Status is the date-aware lifecycle status, so a future-dated plan reads *Pending* on both screens, and who created the assignment is in Details. Enforced in `apps/admin/src/components/assignedPlan/AssignedPlansTable.tsx`.

- **An entity administered from two pages has one editor** (#806, #965). Exercises are edited from a gym's Exercises page and from Cordel's Base Exercises, and both render the same form, the same read-only card, the same media preview (one clip plays at a time) and the same Details modal, so a field or a validation changes in one place. Where the two screens used to differ the stricter behaviour applies to both — removing an image or video asks for confirmation on either. The Nutrition Library and its Base library in Cordel follow the same rule. Enforced in `apps/admin/src/components/exercises/ExerciseEditor.tsx`.

- **The sidebar collapses to icons on desktop and has one scroller** (#883, #1003, #884, #1020). On a desktop screen the sidebar is 250 px with labels or 64 px of icons only; the choice is remembered in the browser. Every section carries an icon beside its expand chevron, and when collapsed the section containing the current page is highlighted; clicking a collapsed icon expands the sidebar and opens that section rather than navigating. On a phone the sidebar is a drawer bounded to the screen below the top bar, the navigation list itself scrolls, and the collapse preference is ignored. Enforced in `apps/admin/src/lib/sidebarCollapse.ts`.

- **On a phone a list keeps its name, its status and its actions, and never scrolls the page sideways** (#1011, #637). Below 768 px the row's identity (truncated, with the full value in the cell's tooltip) is pinned at the left and the chevron or `⋮` at the right, with the primary status beside the name. A list whose rows expand hides its other columns, since their values are one tap away; a flat list keeps them and scrolls them inside the list between the two pinned cells. Desktop and tablet lists keep their full width and scroll horizontally inside the list when narrower than it. Enforced in `apps/admin/src/components/listChrome.ts`.

## Payments, receipts and the payment provider

- **A payment request is one attempt to move money, and it is always in one of four states** (#640, #788, #1121). Every attempt to take money from a Member — a checkout link, a nightly charge, a staff Retry, a cash payment, a card verification or a Product purchase — is a `payment_requests` row carrying a euro amount and one status: `pending`, `completed`, `failed` or `expired`. The row names where it came from (`admin`, `customer`, `billing_run`, `retry`, `manual`, `card_update`, `product_purchase`) and, once settled, the Billing Event it paid, which is how a Billing Event's own status (paid, failed, pending) is worked out: a Billing Event is the charge, a payment request is an attempt to settle it. Recorded by `api/src/api/payment-requests.ts` and `api/src/api/me.ts`.

- **Nothing is charged automatically until the Member has paid once through the hosted page** (#786, #1108, #946). A first payment is a checkout link: staff raise it from the Admin app or the Member taps *Pay now* in the Members App (at most 3 requests per hour per Member, with their consent to future charges recorded). The link is priced on the current billing cycle — a cycle that owes nothing is refused with *This membership owes nothing for its current billing cycle*, and a Plan with a Pre-paid Duration collects the whole lump here (€70/month with 3 pre-paid months asks for €210). The staff user who raised it is recorded. Enforced in `api/src/api/payment-requests.ts` and `api/src/api/me.ts`.

- **A checkout link opens once and must be opened within 10 minutes** (#789, #488, #489). The link carries a single-use token; the hosted page (at the `pay.` domain, outside both apps) exchanges it once for the display details only — amount, gym name, Member name, logo, the gym's theme colours and whether it is a membership fee or a card update — and the token is then dead, so a copied link cannot be reused. The page shows the provider's own card form with a consent checkbox; card numbers and 3-D Secure never touch a Gymdesk server. The exchange is limited to 20 requests per minute per address. Enforced in `api/src/api/payment-page.ts`.

- **The provider's confirmation is what completes a payment, stores the card and puts the plan on the billing schedule** (#789, #790, #1108). When Monei reports a payment `completed`, the request is marked completed, a `payment_recorded` Billing Event is written for its amount, any failed-charge count on the Assigned Plan is reset and, where the provider returned a reusable card token, the card is stored and the plan's first `next_billing_date` is set to the first cycle boundary strictly after today (cycles that elapsed before a back-dated start are written off, never charged). A plan awaiting payment becomes `active` at that moment. A `failed` or `expired` report only marks the request so; an intermediate status changes nothing; a request already completed is never processed twice, and only a `completed` report may revive a request that had been written off as expired. Enforced in `api/src/api/webhooks.ts`.

- **An opened checkout is not written off for 24 hours; an unopened link expires with its 10 minutes** (#789). The twice-daily cleanup expires a pending request whose link was never opened as soon as its 10-minute window passes, because no payment can be in flight. A request whose page *was* opened is left pending for `PAYMENT_REQUEST_ABANDONED_HOURS` (default 24, never less than 1) after that window, since the Member may be inside the card form or a bank's 3-D Secure redirect. The same pass cancels a Product purchase whose payment request is no longer pending, so the Member can buy that Product again. Enforced in `api/src/domain/paymentRequestExpiry.ts` and `api/src/api/billing.ts`.

- **After paying, the Member lands on a success or error page in their own language** (#1081, #1039). The provider sends every Member of every gym back to the same two addresses, which name no language; the Members App then shows the page in the language of the Member's last visit, else the browser's, else English, and a signed-in Member whose profile has a preferred language is moved onto that. Both pages require a signed-in session, since each one checks the Member's own payment state. Enforced in `apps/member/src/middleware.ts`.

- **Replacing a stored card charges nothing** (#788). *Replace card* opens the same hosted page as a payment but as a €0 card verification: it creates no Billing Event, does not move the next billing date, does not clear a failed-charge count, and is not listed in the Member's payment history, the staff transaction list or the Member's Payment Status. If the verification is rejected or returns no usable token, the card already on file is left exactly as it was; a rejected recurring charge is still owed after the card is replaced. Enforced in `api/src/domain/storedCards.ts` and `api/src/api/card-updates.ts`.

- **A stored card cannot be removed while a plan still depends on it** (#788). A Member (or staff on their behalf) may remove the stored card only when no Assigned Plan of theirs is `active` or `paused` with a `next_billing_date`, because the nightly run simply skips a plan with no card and nobody would be told. The card's provider credentials are never shown or sent anywhere; the apps see only the brand, last digits and the date it was stored. Enforced in `api/src/domain/storedCards.ts`.

- **A failed recurring charge is settled by staff, never retried automatically** (#640, #779). A failed Billing Event offers two staff actions on the Payments pages: *Retry*, which charges the stored card again up to 2 times and pauses the Assigned Plan if both are rejected, and *Manual payment*, which records money received outside the provider. Either success advances the next billing date (only when it is today or earlier) and clears the plan's failed-charge count; neither creates a second Billing Event, so the original charge reads as paid. Failed charges awaiting action are counted in a red badge beside *Payments* and on the dashboard, oldest first; the Member is not notified. Enforced in `api/src/domain/billingEventPayments.ts`.

- **A receipt is issued only for money actually received, numbered without gaps per gym and year** (#787). A receipt ("factura simplificada") can be issued for a Billing Event that records a payment (`payment_recorded`, `recurring_payment`, or a `failed_billing` later settled by Retry or Manual payment) and whose status is paid; a waived cycle, an adjustment and anything pending, failed or expired have no receipt. The number is `<year>-<4-digit sequence>` in the year of issue, one sequence per gym per year, and a payment can never consume two numbers. The nightly run issues one for every charge it settles; a receipt that was not issued automatically can be issued from the Payments page. Enforced in `api/src/domain/billingEventStatus.ts` and `api/src/domain/receiptNumbers.ts`.

- **A Member's Payment Status is the worst status across everything they are billed for** (#1235). The Members list badge looks at each thing the Member pays for separately — their Assigned Plan and each Product bought on its own — takes the latest payment request of each, and reports the worst of them in the order `failed` > `expired` > `pending` > `completed`, so a failed locker purchase reads *failed* even when the plan is paid. A card verification is ignored, since no money is involved. The status is independent of the Member's login, enrollment and access rights. Enforced in `api/src/domain/memberPaymentStatus.ts`.

- **Every amount is a euro figure, and only the payment provider sees cents** (#773). Fees, Billing Events, payment requests and everything the apps show are decimal euros; the one conversion to minor units (2999 for €29.99) happens at the moment a charge or a checkout is sent to the provider, and nowhere else. Enforced in `api/src/payments/money.ts`.

- **Which payment provider a gym uses is a catalogue choice; how to talk to it is deployment configuration** (#636). Every gym names a payment provider from the platform's catalogue (Monei today, with a default for new gyms), and the provider's keys, webhook secret, hosted-page address and return addresses are environment settings of the deployment — no credential is ever stored in the database or shown in an app. Enforced in `api/src/payments/index.ts`.

## Webhooks, scheduled runs and relays

- **Monei's payment confirmations reach the API through the payment app, which forwards them unchanged** (#1083). The provider posts each confirmation to the hosted payment app's address, and that app passes the request, body and signature untouched, to the API's internal address, so the provider needs no route to the API itself. The API checks the signature on the exact bytes it received (a tampered message is refused and nothing is written) and the provider is answered with the API's own result, never a blanket OK, so a confirmation the API could not record is retried by Monei. The confirmation route accepts 60 messages per minute per sending client, counted per payer rather than per relay. Enforced in `apps/payment/templates/default.conf.template` and `api/src/api/webhooks.ts`.

- **Clerk's account events reach the API through the Admin app, which forwards rather than verifies** (#1085). Clerk's sign-in service posts user events (created, deleted, …) to the Admin app's address; the Admin app passes the body as raw bytes with Clerk's signature headers to the API, which is the only place the signature is checked. Clerk receives the API's own answer, so an event the API could not process (an unreachable API answers 502) is retried or replayed from Clerk's dashboard rather than silently lost, which is what keeps deleted logins from lingering as orphaned accounts. Enforced in `apps/admin/src/lib/clerkWebhookRelay.ts` and `apps/admin/src/app/api/webhooks/clerk/route.ts`.

- **The scheduled runs are triggered through the Admin app, which relays exactly four of them and nothing else** (#1086). The GitHub-scheduled jobs call the Admin app, which forwards only the nightly billing run, the payment-request cleanup, the Promotion expiry sweep and the recurring-booking run to the API; any other path is refused by the relay with 404. The job is handed the API's own status and counters byte for byte, so a run reported as failed really failed, and the relay waits up to 11 minutes for a long night (an unreachable or slow API answers 502/504, never a false success). Enforced in `apps/admin/src/lib/internalRunRelay.ts` and `apps/admin/src/lib/internalRunUpstream.ts`.

- **A scheduled run is authorised by a shared secret, and guessing it is budgeted** (#783, #1086). Each internal run route compares an `X-Internal-Secret` header against the secret the deployment holds; a wrong or missing secret is a 401. Ten failed attempts within 15 minutes from one client address (`INTERNAL_RUN_RATE_LIMIT_MAX` / `…_WINDOW_MINUTES`) lock that address out with 429 until the window ends — only a 401 spends the budget, so the legitimate job, including its second daily attempt, can never lock itself out, and the address counted is the job's own, not the relay's. Enforced in `api/src/domain/internalRunRateLimit.ts` and `api/src/domain/forwardedClient.ts`.

- **A public health check says when each nightly run last completed, and flags one that is overdue** (#782, #872, #1166). `GET /health/runs` reports, for the billing run and the recurring-booking run, the time of the last completed run, its age in hours and a `stale` flag set once the age exceeds `RUN_FRESHNESS_THRESHOLD_HOURS` (default 26); a run that failed or is still in progress does not count, and a log with no completed run is stale. It answers 200 whenever the database can be read (stale or not — Grafana's two alert rules read the flag) and 503 only when it cannot; it carries no counters, gym or Member and needs no credentials. Grafana reads it through the Admin app, which relays that one fixed path and no other. Enforced in `api/src/domain/runFreshness.ts` and `apps/admin/src/lib/healthRunsRelay.ts`.

- **A gym website's sign-up form posts to one address the Admin app relays, and the gym is told exactly that address** (#599, #1175). A website registration creates a Clerk invitation for the person and nothing else — no Member row and no Assigned Plan until they sign in and staff act. The request carries the gym's API key, which the API alone checks, and the relay forwards that one route and no other under its public prefix; sign-ups are rate-limited per website client, so one site cannot spend another gym's budget. Cordel → Gyms → Website Integration shows the gym the relay's address (`PUBLIC_REGISTRATION_BASE_URL` plus the path) and never a derived one. Enforced in `apps/admin/src/lib/publicRegistrationRelay.ts` and `api/src/api/public-registrations.ts`.

- **Every secret and setting the API runs with is written by the deployment, and none of it is visible in logs** (#1177, #1192, #1186). Deploying rewrites the API's whole environment file from the GitHub environment's variables and secrets — relay hop counts, internal secrets, provider keys — so a value edited by hand on the server is lost on the next deploy and a setting that is not forwarded there does not exist (the gate `api/src/test/deploy-env-forwarding.unit.test.ts` fails the build for one). No value is ever placed on a container's command line, because the hosts' command lines are shipped to the central log store; the API's own log lines are sent to that store through journald. Enforced in `.github/workflows/deploy.yml`.

## Not in this file

Constraints that are purely about how the code is organised stay in `CLAUDE.md` alone: where a new status or notification type must be declared, which component renders what, the shared form and list chrome, test gates, naming of identifiers, and the "one place decides it" structure behind most of the entries above. They change how a feature is built, not what a gym or a member sees.
