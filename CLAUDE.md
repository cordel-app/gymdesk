# Gymdesk

Multi-tenant Gym Management SaaS. Express backend + Next.js frontend + MySQL 8 (Oracle HeatWave) + Clerk auth.

## Before implementing any feature

For any issue that involves new API surface, DB schema changes, or significant UI work, write a plan first and get approval before coding. A plan should cover: migrations, API endpoints, frontend sections, tests, and doc updates. Keep it concise — bullet points per layer, not prose.

**Issue type `Task` is the marker for work that needs no plan.** A GitHub issue whose type is set to **Task** is a small, self-contained fix or change that needs no new API surface, no migration and no significant UI, so the plan-first rule above does not apply to it. Whoever writes the issue (Oscar, usually) sets the type by hand; that is the whole opt-in. Tasks are consumed only by the `gymdesk-tasks` routine (`skills/routines/gymdesk-tasks.md`); every other issue is the `gymdesk-issues` routine's, which searches with `-type:Task`. If a Task turns out to need any of those after all, it is not implemented: comment and retype it as a normal issue. Do not mark such work with a label or a `fix:` title prefix — the type is the one signal both routines filter on.

Read these files first — they contain the full context needed to implement correctly:

- `docs/architecture.md` — starts with a TL;DR; full codebase structure, auth, roles, DB conventions below it
- `docs/feature-patterns.md` — step-by-step checklist and code templates for new features
- `docs/roadmap.md` — ticket order, current status, and phase decisions
- `docs/decisions.md` — settled architectural choices (MySQL, Clerk, no ORM, etc.) — don't re-litigate these
- `docs/payments.md` — **required reading for anything that touches money**: the first-payment (CIT) and recurring-charge (MIT) processes end to end, the data model with its CHECK sets, the provider boundary, and the manual test runbook. The constraints below are the rules; that document is how the two processes actually run.
- `docs/mobile-app.md` — **required reading for anything that touches the iOS/Android app** (Capacitor shell, native sign-in, push tokens, universal links): the plan, what the 2026-10-04 spike proved, and the design rules that keep per-gym apps (stage 2) a configuration of the generic app (stage 1) rather than a fork. Planned, not built yet.

Use **Members** as the reference implementation for staff-level CRUD with soft-delete.
Use **Plans** (`api/src/api/membership-plans.ts` + `apps/admin/src/app/[locale]/plans/`) as the reference implementation for an admin-only CRUD API and its Inline row CRUD frontend (expandable rows, no modals — see `docs/feature-patterns.md`). For the Modal CRUD frontend shape, see Class Types.

Use `/plan` to generate a structured implementation plan before coding. Use the `db-reviewer` agent to check migration files. Use the `test-writer` agent to generate test files.

## Parallel agents (worktree workflow)

Multiple Claude Code agents may work simultaneously, each in its own worktree and feature branch.

### Ground rules

- **One agent per worktree.** Never modify files in another agent's worktree directory.
- **One feature branch per task.** Always branch from `main`; never branch from another feature branch.
- **No destructive Git commands** (`git reset --hard`, `git clean -fd`, `git checkout -- .`, `git restore .`, `git branch -D`) unless the user explicitly requests them. Never discard changes to make a merge succeed.

### Required sync before feature completion

Before a feature is considered complete, the agent must integrate the latest `origin/main` into its branch:

```bash
git fetch origin
git merge origin/main   # always merge, never rebase
```

If conflicts occur:
- Resolve them carefully — preserve valid changes from **both** sides.
- Never blindly choose "ours" or "theirs".
- Pay particular attention to `docs/roadmap.md` (see below).
- Run tests after resolving conflicts.
- Confirm the working tree is clean before marking the feature done.

Use `/finish-feature` to run through the full sync + test + status checklist automatically.

### Special handling of docs/roadmap.md

`roadmap.md` is a shared file modified by multiple parallel agents.

- Keep changes minimal and focused on the current task.
- Do not reformat or reorder unrelated sections.
- Do not remove another agent's entries.
- When resolving merge conflicts in `roadmap.md`, keep changes from both sides — merge the sections manually rather than picking one side.
- Always sync with `origin/main` before the final commit if `roadmap.md` was modified.

## Hard constraints

- No microservices, no event sourcing, no AI/LLM integrations.
- One database: MySQL 8 (HeatWave when deployed). No additional stores without a concrete reason.
- Every domain table must have `gym_id`. Every query must filter by it. A **shared platform catalogue** — `nutrition_library_items`, `exercises`, `themes`, and since #947 `personal_goals` and `nutrition_goals` — is the one other shape: `gym_id` is nullable with the FK still `ON DELETE CASCADE`, `NULL` means a System row owned by the platform and administered from Cordel, non-NULL means that gym's own, and a gym-facing read takes `(gym_id IS NULL OR gym_id = ?)` while every write still checks the row's own `gym_id`. The global lookup tables (`benefit_types`, `charge_types`, `action_types`, `muscles`, `result_types`) have no `gym_id` at all.
- A `weekday` column means **0=Sunday … 6=Saturday** (`gym_operating_hours`, `activity_type_schedule_rules`, `trainer_availability`, `training_plans`). A column storing luxon's ISO numbering (1=Monday … 7=Sunday) must be named `iso_weekday` instead, so the two bases can never be joined by accident — see `member_recurring_slots` (migration 169).
- A new `member_notifications.type` goes in **two** places: the `NotificationType` union in `api/src/infra/notifications.ts` **and** the `chk_member_notifications_type` CHECK (current definition: migration 170). Adding only the first makes every insert of that type fail invisibly — `sendNotification()` is fire-and-forget and only logs.
- A new `recordAudit({ entityType })` value also needs an `AUDIT_ENTITY_REGISTRY` entry in `api/src/infra/audit-registry.ts`. Without one the rows write but carry no `entity_name`, and the type never reaches the Audit Log's entity-type filter (`GET /audit-logs/meta`).
- A Member holds **zero or one Membership Plan**, never two (#956, migration 213). This reverses #634 §6/§14's "several plans in parallel, but only one of each type" (migration 172): the UNIQUE index on `user_memberships` is `user_memberships_one_active (active_member_key)` again, and migration 213's one-time sweep is what made that creatable (per owning Member, the `active` row beats the `paused` one, then the latest `starts_at`, then the latest `id`; the rest were cancelled and dated like a replacement, with a `status_changed` ledger row each — `npm run memberships:multi-active` is the read-only report that identifies them, and it is also the only thing that reports the overlap the sweep deliberately leaves). `api/src/domain/oneActivePlan.ts` is the one place the rule is decided and `api/src/api/one-active-plan.ts` the one place it is enforced in SQL, and every path that creates a `user_memberships` row calls them **inside its own insert transaction** — `POST /user-memberships`, `POST /user-memberships/:id/assign-new-plan`, `POST /membership-plans/:id/assign`. Three of their answers are the rule rather than the implementation. **`paused` counts as the one plan** and so does a future-dated row (`LIVE_ASSIGNMENT_STATUSES`): the first because pausing would otherwise be a way around the rule, the second because `pending` is a derived `lifecycle_status` and the row is stored `active` — the index cannot express either (its generated column is NULL unless the row is `active`), so the database guarantees at most one `active` row per **owning** Member and the application guarantees the rest. **"Already has a plan" is read through `user_membership_members`**, never `user_memberships.member_id` alone, so a covered member of a family plan somebody else owns already has one (#956 Q4) — that is the overlap `active_member_key` is blind to, which is why it is checked under the `FOR UPDATE` lock and why migration 213 does not sweep it. And **replacing is immediate and explicit**: an unconfirmed caller gets `409 { error: 'active_plan_exists', message, current_plan, conflicts }` carrying both plan names and the current plan's dates (so the confirmation dialog needs no second read of what it is about to cancel — that dialog is one place too: `apps/admin/src/lib/activePlanConflict.ts` recognises the 409 **by shape**, the status *and* the code *and* a usable `current_plan`, so the router's other 409s still read as an error line, and `apps/admin/src/components/ReplacePlanDialog.tsx` draws it over the app's existing `ConfirmDialog`, raised by all four admin entry points with one set of `common.replace_plan_*` keys because the rule is one rule; the first attempt never sends `confirm`, which is also why a click handler is never passed by reference — the `MouseEvent` would land in the `confirmReplacement` argument and confirm it — and Cancel clears the conflict and nothing else, no request, no close, no reload. Do not add a second replacement dialog, a per-page wording of it, or a client-side "does this Member have a plan" check), and `confirm: true` makes the superseded row `cancelled` with `closed_at` stamped now and `ends_at` set to the new plan's `starts_at`, through `supersedeLiveAssignments()` and nowhere else — the two plans meet at one date, they never overlap as live rows, the old row is never deleted and its snapshot, promotions, billing events and `next_billing_date` are left exactly as they are, because they are the record of what it billed. A `starts_at` earlier than the plan being replaced is a 400, since the superseded row's `ends_at` would land before its own `starts_at`. `POST /user-memberships/:id/assign-new-plan` needs no `confirm` (replacement is its whole contract) but does for a *second* live assignment the request never named; the Plans page's Assign is all-or-nothing across the selected Members, because a partial run would leave a gym with cancellations it did not get to weigh. **Covering** a Member is the fourth way they come to hold a Plan, so `POST /user-memberships/:id/members` enforces the rule too — and it is the one path that offers **no** `confirm`: a replacement ends the old plan on the new one's `starts_at`, and coverage added to a plan that started months ago has no such date, so the staff action stays the explicit one (close their plan, then add them) and the 409 says so. Do not add a second status list, a second supersede, a scheduled transition (it would need a nightly sweep to flip the status on the day), a stored "current plan" column, or an assignment path that checks the rule outside its own insert transaction. Note what this did *not* change: the Member-level Billing Simulation stays consolidated (#629 Q4) and simply has one assignment to consolidate, and `POST /me/payment-requests` lost #634's `409 multiple_active_memberships` with the state that produced it — `user_membership_id` is still accepted and still narrows the read.
- Any new code path that inserts a `user_memberships` row must call `snapshotAssignedPlan()` (`api/src/api/assigned-plan-snapshot.ts`) inside the same transaction. An Assigned Plan owns the commercial configuration it was assigned with (#635 §11–§17) — an assignment created without one reads back as `snapshot_captured: false` and silently falls back to the live catalogue, so a Plan or Product edited later would move what it bills.
- Any new code path that *edits* an existing assignment's snapshot must call `materialiseAssignedPlanSnapshot()` first, in the same transaction (#635 stage 6). The live fallback is all-or-nothing: the moment one section of an uncaptured assignment is written, the assignment counts as captured and every section the edit did not mention reads back as empty. An edit also stays on that assignment — never write through to the Membership Plan, another assignment or the Product — and a `cancelled`/`expired` assignment is not editable at all.
- Billing reads the **Assigned Plan snapshot**, never the live catalogue, for an assignment that already exists (#635 §13–§17). A query that projects, charges or advances an assignment's billing takes its cadence from `ASSIGNMENT_CADENCE` in `api/src/api/assigned-plan-snapshot.ts` (`COALESCE(um.recurring_billing_*, bp.recurring_billing_*)`) and therefore **LEFT** JOINs `billing_policies` — an INNER JOIN drops every assignment whose Plan lost its policy. Since #635 stage 13 (migration 189) `billing_policies` holds that pair and `auto_renew` and nothing else: Initial Billing, Initial Service and Recurring Service are gone, **Billing & Duration is the Plan's only billing section** (the surviving pair is its *Billing frequency* — Free/Paid/Bonus say how long a contract runs, never how often it charges), and no second cadence, service-period concept or per-plan billing column may be reintroduced. Since #820 a Plan's *Billing frequency* is also a **choice of two** — Month (`1 month`) or 4 Weeks (`4 week`) — named once in `api/src/domain/planBillingFrequency.ts` and enforced by `PUT /membership-plans/:id/billing-policy`, never by the dropdown alone: the stored shape is still that `(interval, unit)` pair, so a new pair is added in **two** places (the declaration and, mirrored, `PLAN_BILLING_FREQUENCY_OPTIONS` in `apps/admin/src/app/[locale]/plans/planProfile.ts`) and never as a symbolic column. A cadence outside the two is refused on write but still read, billed and displayed wherever it is already stored — `planBillingFrequencyOf()` answers `null` for it, and a surface that coerced that `null` to Month would tell a gym it bills monthly while the run charges every two months. Prices and benefits come from `user_memberships.membership_fee_price`, the `user_membership_{session,oneoff,periodical}` rows, the `user_membership_promotion_*_snapshot` rows and `user_membership_services`' own price columns; the live catalogue is only the fallback for an assignment that captured no snapshot. The same holds for a path that merely *displays* an assignment's benefits or cadence, on a staff screen or a member-facing one (`GET /me/membership`, #635 stage 10): it reads the assignment's rows through `loadPlanBenefitsForSimulation()` / `ASSIGNMENT_CADENCE`, so what the Member is shown cannot drift from what the nightly run charges them. The Plan-keyed `membership_plan_benefits` (migration 006) is gone — migration 184 — and nothing replaces it.
- **The entity is called a Product** (#949). *Sellable Item* was its name until this rename and is retired as a term: no user-facing copy, no identifier, no route, no column and no prose in these docs says it again. All three stages have shipped — stage 1 the copy a gym owner reads, stage 2 the code identifiers (`Product*`, `api/src/domain/product*.ts`, `components/ProductBenefits.tsx`), the file names, the locale keys (the `products` namespace, `col_product`, `applies_to_product`, `impact_products`) and the admin route, and stage 3 the wire and the schema (migration 214): the API root is **`/products`** with no alias, the table is **`products`**, its FK column **`product_id`** in the thirteen tables that key to it, the three promotion snapshots' **`product_name`**, the join table **`product_professional_services`**, the eight **`products_*`** CHECKs (plus `chk_products_enrollment_status`), every index and FK constraint renamed with them, and `charge_types.is_gym_charge` → **`is_product`**. The response fields are `products` (on an enriched Plan and on a tax rate's delete impact), `product_id`, `product_name`, `product_status`, `product_deleted_at` and `product_retired`; the stored `promotions.applies_to` value and the Billing Simulation line `kind` are **`'product'`**; the feature flag is **`financials.products`** and the audit entity type **`product`**, whose `audit_logs.entity_type` rows were backfilled because that column is the key `AUDIT_ENTITY_REGISTRY` and the Audit Log's filter are built from — the audited values themselves (`previous_values`/`new_values`) were not touched, because they are the record of what changed. Three things keep an older spelling on purpose and are **not** drift: the two legacy admin routes `financials/sellable-items` and `financials/gym-charges`, each a `permanentRedirect` to `financials/products` so a link written before either rename still lands; and the old migrations, which keep their own file names and SQL, because they are the history of a schema that really did carry those names (a migration is never edited, and `require()`ing one by another name would simply fail). Two gates hold the line, both in the API suite because CI runs `npm test` in `api/` only: `api/src/test/product-terminology.unit.test.ts` fails the build if a locale **value or key** in either app says otherwise, and `api/src/test/product-identifiers.unit.test.ts` fails it if any retired **shape** — `SellableItem` / `sellableItem` / `SELLABLE_ITEM`, anything spelling `sellable` at all, `gym_charge`/`gym_charges`, `gymCharge`/`GymCharge`, or the English prose — comes back anywhere under `api/src` or either app's `src`. It bans shapes rather than a list of names, which is why it still needs no allowlist: its only carve-outs are the two gates' own fixtures and, by rule rather than by file, the migration **file name** inside a line that `require()`s one. A **Product Type** is `products.type` and nothing else: the global `charge_types` lookup (no `gym_id`, per the constraint above) is a different concept that merely shares a word and keeps the name **Charge Type** — which is also why `is_product` lives on it and says which Charge Types seed a per-gym Product. New copy says Product / Products, *Producto* / *Productos* and *Producte* / *Productes*.
- A **Product's Billing Frequency** is a separate question from a Plan's cadence, and since #945 it is a choice of **four**: Once, 4 Weeks, Month, Year, named once in `api/src/domain/productFrequency.ts` and mirrored for the form in `apps/admin/src/app/[locale]/financials/products/productFrequency.ts`. `week` (#821) and `per_session` (#945) are **retired, not deleted**: `products_billing_frequency_check` (migration 123, renamed with its table in 214) still permits all six values and there is no backfill either time, because an item a gym configured weekly is a real price whose period is neither a month nor 28 days, and because what a gym meant by *Per Session* — a package billed once, or the usage-based model the product never had — is not knowable from the row, so #945 §3's "flag the value for correction rather than guessing" applies rather than the coercion it also invites. (`per_session` billing identically to `once` — `cadenceForProduct()` gives neither a schedule — is not a licence to rewrite it.) So "what may be stored" and "what may be configured" are two different answers, and `productFrequencyWriteError(next, current)` is the one place that decides the second — `POST /products` refuses a retired value outright, `PUT /products/:id` accepts one only when it is what the row already holds, so editing another field of a legacy item neither 400s nor silently rewrites its frequency, and nothing may be moved *onto* it (nor from one retired value to the other). `isRecurringFrequency()` (`domain/productClassification.ts`) still counts `week` as recurring and `per_session` as not, so a legacy item keeps classifying into the same benefit section and keeps billing, and correcting a `per_session` item to Once moves it between no sections. The editor renders the retired value as a **disabled** option only while the form holds it — never as a selectable one, and never coerced to another frequency — with the notice beside it **naming** that value (`frequency_legacy_notice` interpolates the label, resolved before `t()` is called, since there is more than one retired value), and `POST /:id/duplicate` copies it verbatim, because Duplicate is a copy, not the dropdown. Every other surface only ever *displays* a stored frequency, so the offered list has exactly one consumer and a legacy row still reads *Per Session* where it is stored; `week` meanwhile stays **offered** by a Session Benefit's own Frequency (#918), which is a different set answering a different question. A new frequency therefore goes in **three** places (the declaration, its mirror, and the CHECK beside them); do not add a second accepted-set list in a route or a page.
- A **Product's Mandatory flag** (#832, migration 200) is `products.mandatory`, and it is one column for both kinds of row that table holds: the per-gym System items seeded from `charge_types` (`is_system = 1` — the ticket's "Base Products", the Insurance Fee among them) and the gym's own (`is_system = 0`, "Custom"). Do not add a second flag, a platform-level product catalogue or a per-kind editor for it. It is **editable on a System item**, so `PUT /products/:id` writes it outside the `IF(? = 0, …)` `is_system` guard that still freezes a System row's name/type/units, and it is written as `mandatory = IF(?, ?, mandatory)` keyed on whether the request supplied the field — a `COALESCE` on the value itself would make unchecking the box unpersistable, which is the one way a boolean column of this shape goes wrong. A body value that is neither a boolean nor 0/1 is a 400, never coerced (the string `"false"` is truthy). There is no CHECK on it (the router coerces to `? 1 : 0`, and `ADD CONSTRAINT` rebuilds `products` under `ALGORITHM=COPY`). Exactly **one** thing reads it, since #893: a mandatory item is part of every **Membership Plan** benefit section, and `api/src/domain/mandatoryPlanBenefits.ts` is the only place that decides what that means. Its candidate set is the gym's **active, non-deleted** mandatory items — an inactive or deleted one is ignored, because forcing it in would fail every Plan save on a catalogue change nobody asked for — and which section each belongs to is `classifyProduct()` (#550) and never a second mapping. `mergeMandatoryBenefits()` is what a read reports (`GET /membership-plans/:id/{session,oneoff,periodical}-benefits` and `enrichPlan`'s three embedded sections), adding a missing mandatory item as `implicit: true` at quantity 1; `withMandatoryBenefits()` is what the replace-all `PUT` writes, so a client that drops one has it **preserved rather than 400d** — that is what makes an existing Plan pick up a newly mandatory item the first time any of its sections is saved. A submitted mandatory item passes through untouched, quantity included: Mandatory says the item must exist, never what its quantity is, and it is not a reason to change one. The enforcement is the server's — the shared `ProductBenefits.tsx` takes an explicit `enforceMandatory` opt-in (the Plans page only, never Promotions) and merely renders the row without a `✕` and without a picker that could swap the item away, so a client bypassing it changes nothing. Everything else about the flag is still unread and still out of scope: automatic inclusion in a **Billing** Plan, refusing its removal from one, Billing Plan pricing and any Insurance Fee special case, so a path that acts on the flag beyond the above is deciding that behaviour and needs a ticket. In particular #893 changes no billing: a mandatory item reaches an assignment's Assigned Plan snapshot the ordinary way, as a stored Plan benefit row, and nothing back-fills the Plans that were never saved again.
- A **Product of Type `Sessions` prices the whole package**, not one session: `products.amount` is the total for the `units` sessions it contains, so `Units: 5` beside `Price: €50.00` means €50.00 for the five and never €250.00 (#942). Nothing multiplies a price by a unit count, and no per-session price is stored, computed or displayed anywhere. What the ticket added is the sentence that says so, and `apps/admin/src/app/[locale]/financials/products/productPriceNotes.ts` is the one place that decides it — `sessionPackageNote()` answers the *Total price for N sessions* wording (ICU-pluralised off the item's own `units`, with a package wording for a session item whose nullable `units` is unset) and `null` for every other type, which is what keeps fee-based items untouched; `taxNoteKey()` answers which `(tax …)` suffix a displayed figure takes, and `null` for an item with no `applied_tax_rate` rather than claiming a tax that is not configured. Every surface showing such a price asks that module rather than testing `type === 'sessions'` beside a price for itself, and the two form hints ask `sessionPackageNoteForForm()` with the draft's live Type and Units so the sentence tracks what is being typed rather than the saved row. Do not add a per-session price column, a per-session figure derived from `amount / units`, or a second place that decides this wording.
- The **nightly billing run** (`POST /billing/run`) prices the cycle `next_billing_date` names, never "today": `priceMembershipFeeOn()` (`api/src/api/membership-fee-pricing.ts`) asks the Billing Simulation's own `resolveMembershipFee()` what that date costs and whether it is waived, so what is charged cannot drift from what the staff screens and the Member's My Membership page show (#635 stages 11–12). A waived cycle calls no payment provider and writes no `payment_requests` row — it records a `waived_billing` billing event and advances `next_billing_date`, leaving `last_billed_at` untouched. A new `billing_events.event_type` goes in **two** places: the writer and the `billing_events_event_type_check` CHECK (current definition: migration 185) — adding only the first makes the INSERT fail and takes the run's transaction with it.
- A **`next_billing_date` written onto an assignment is never today or earlier** (#790). The payment webhook stamps the first one as the first `starts_at`-anchored cycle boundary *strictly after* UTC today, and any transition back to `active` (Reactivate, a `PUT` status flip) walks a past one forward the same way along its own schedule — both through `api/src/domain/nextBillingDateStamp.ts`, which reads the cadence via `ASSIGNMENT_CADENCE` (LEFT JOIN) and every date, today included, as a `YYYY-MM-DD` string from SQL, over the one pure rule `firstBillingDateAfter()` (`api/src/domain/billingDate.ts`, stepping with the run's own `advanceBillingDate()`). A back-dated `starts_at` stays allowed: the cycles that elapsed before the first payment, and the ones missed while paused, are **written off** — no catch-up charge, no `adjustment` row — because the first payment is priced on *today* (`currentCycleDate()`), so stamping `starts_at + cadence` charged one elapsed cycle per night and then the paid cycle a second time. A new writer that puts an assignment (back) on the run's schedule calls one of those two helpers rather than computing a date itself; the run's own `advanceBillingDate(next_billing_date)` step and the staff Retry/Manual payment's one-cycle advance are unchanged.
- A rejected recurring charge **escalates, it does not repeat** (#785, migration 194). The nightly run counts consecutive rejections of the cycle `next_billing_date` names in `user_memberships.failed_attempts` (+ `last_failed_at`) and the second one pauses the assignment (`recordStatusChange`, `active → paused`, `source = 'system'`) — which is the whole mechanism, since a `paused` row is outside the run's `WHERE status = 'active'`. The count advances per run **day** (`DATE(last_failed_at) = UTC_DATE()`, compared in SQL so no DATETIME crosses a timezone conversion): a rejection on a date the assignment was already rejected on is recorded but does not escalate, because #781's second daily attempt becomes the day's real run whenever the first crashed. The retry is therefore the **next run day**, never a second attempt in the same loop: a card declined seconds ago declines again, and `next_billing_date` not moving is what schedules it. Only a provider **rejection** counts: `provider_error` (the provider threw or never answered — the charge's outcome is unknown, so a night the provider is unreachable would otherwise pause a gym's whole book) and `no_payment_method` (nothing was attempted) leave the counter exactly as it was, in both directions. Anything that settles or skips the cycle clears it — the run's own success and waived branches, the payment webhook's `completed` branch (a member paying their checkout link settles the same cycle), both staff actions through `clearDunningState()` (`api/src/domain/billingEventPayments.ts`), and any transition back to `active`, because reactivating means "bill this again" and a resumed assignment gets the documented two attempts rather than one. `domain/billingDunning.ts` is the one place that decides all of this (`countsTowardPause`, `registerRejection`); a new failure branch in the run asks it rather than incrementing the column itself, and a new code path that settles a cycle clears the pair. The decision is taken from the row **under the run's `FOR UPDATE` lock**, never from the row the due query read before the provider round trip: a staff payment landing in that window clears the pair, and deciding from the stale count would write it back and pause a member who has just paid. The columns are **not** part of the Assigned Plan snapshot (`has_billing_snapshot`) for migration 192's reason, there is no CHECK on them (`ADD CONSTRAINT` rebuilds `user_memberships` under `ALGORITHM=COPY`), the escalation is not a new status, and reactivation stays explicit — clearing the count never flips `paused → active`.
- A **system-wide nightly run** (`POST /billing/run`, `POST /recurring-bookings/run`) claims its slot through `claimRun()` and closes it through `finishRun()` (`api/src/infra/run-log.ts`), from the success path **and** the `catch` — never by stamping a `last_run_at`. The rule is **one *completed* run per UTC date** (#780, migration 193): both logs are histories now, one row per run, and a run is refused only when a run for today's UTC date already reached `completed`. Do not reintroduce an "N hours since the last start" window — a cron GitHub fires late then skips a day, and a stamp written before the first row is touched locks the day when the run crashes. Overlap is the `in_progress` half of the guard (a row younger than `STALE_RUN_MINUTES`, `api/src/domain/runGuard.ts`, answers `429`); a stale one is taken over. "Today's run already completed" answers **`200 { skipped_reason: 'already_completed_today', run_date, …zeroed counters }`**, never `429` — the second daily attempt is a safety net, not an error, and the counters are what `.github/workflows/*-run.yml` parses (#778). The field is `skipped_reason`, never `skipped`, which is already a numeric counter of the recurring booking run. - **An Admin event's execution status is derived on read, never stored** (#977). What happened to the *event* — `scheduled`, `not_used`, `completed`, `cancelled` — is one axis, and `api/src/domain/eventExecutionStatus.ts` is the one place that decides it: a `scheduled` row that has ended with no `booked` bookings is **`not_used`**, one that has ended *with* bookings stays `scheduled` until a person confirms it (§4/§13 — a booked past session is never completed automatically), and the two values a person chooses carry through from the `status` column that already held them. There is **no `execution_status` column and no sweep**: `not_used` is a function of the clock and the booking count, so a stored copy would need a nightly writer, and a night it missed would report yesterday's empty slots as still *Scheduled* — which is also why no confirmation task is created for an empty slot (§3, the whole point for a gym whose calendar is mostly open slots for private classes). An explicit decision **outranks the clock in both directions**, which is what keeps `Completed · 0 attendees` (§5 — the teacher held the session with nobody there) a different fact from a slot that passed unbooked, and a `draft` manual entry answers **`null`** rather than a fifth value, because it was never put on the calendar and so neither ran nor went unused. `withEventExecutionStatus()` wraps **every** read of both routers — list, single row and the rows the mutations return — so the field is reported and never re-derived: the badge's `full` (a scheduled session at capacity, still the UI's own derivation) is gated on it, and a surface that re-asked "has it ended with nobody in it" would be the second place deciding what an unused slot is. Both explicit transitions record **previous → new** status through `recordAudit` (§14), which is also where "who confirmed it and when" lives — there is no `completed_by`/`completed_at` column beside it, and `POST /class-sessions/:id/complete` keeps its pre-existing guards (pending attendance, no trainer) rather than growing an "ended" one, since the *action* is what §4 gates and the UI is where it is offered. Do not add a stored execution status, a second place that decides `not_used`, a nightly transition writer, a fifth value, or a member-facing surface that reports any of it.

- **A cancellation is undone, never replaced** (#979). `POST /class-sessions/:id/reactivate` is the only way back from `cancelled`, and it writes `status = 'scheduled'` — clearing the `cancellation_reason` it undoes, since the audit row is where that reason lives from then on — and nothing else: the lifecycle is `Scheduled → Cancelled → Scheduled`, `Completed` stays reserved for an event that actually took place (§3), and anything not `cancelled` is a `400 { code: 'not_cancelled' }`, which is also what the loser of two concurrent calls gets because the `UPDATE` carries `status = 'cancelled'` in its own WHERE. **Nothing is restored, because nothing was removed**: `POST /:id/cancel` writes the event's status and has never touched `calendar_event_bookings`, so the enrolled members, the waitlist and its `waitlist_position` ordering are still exactly as they were (§4/§5) and reactivation inserts nothing at all — which is what makes a duplicate booking, a duplicate waitlist entry or a second event impossible by construction (§11), and why a booking the member cancelled themselves stays cancelled. Do not add a restore step, a re-booking path or a `cancelled_bookings` snapshot table; the route's booking read is there to *report* what came back (the alert and the audit row) and a path that re-books from it is deciding something else. Two things it does guard, and they are the rule rather than the implementation. The cancellation freed the trainer/space slot — every conflict check in this router skips `cancelled` rows — so re-occupying it goes through `assertSlotAvailable()`, the one `FOR UPDATE` shared-slot rule `POST /` and `PUT /:id` also use (#979 extracted it rather than writing a third copy), answering the same four `409` codes; a new writer that puts a session back on a slot calls that helper rather than checking for itself. And the members who held a booking are alerted with **`event_reactivated`**, never `booking_confirmed` — the member booked nothing (§6/§11) — while a **waitlisted** member is not alerted at all, because they were never told the class was cancelled either and have no booking to have restored; the member-facing copy is a locale key plus, where a type needs a second line, an entry in the Alerts page's declared `DETAIL_TYPES` (next-intl prints a missing key verbatim, so a `t()` fallback is not one). A **past** cancelled event is reactivatable on purpose, since "cancelled by mistake" is usually noticed after the class should have run, and #977's rule then classifies it — `not_used` when nobody is on it — so this route decides no execution status of its own. In the admin a cancelled session's Actions block offers **exactly one** action (completing, moving or re-cancelling it all act on a slot nobody holds), confirmed in the panel's own inline confirm card rather than a second overlay style, and the panel reloads instead of closing so §8's status, capacity, enrolled list and waiting list read as restored immediately. A **manual** calendar entry has no reactivate route: its status is edited in `EventDetailsPanel`'s own select, which is also how it is cancelled, so the explicit action pairs with the explicit cancel only sessions have — do not add a second reactivation path, a bulk one, or a reactivation that re-notifies, re-books or reprices anything.

The split is deliberate: the **declaration** is pure (orderings and payloads are asserted directly), the **hook** owns the form values, the muscle roles, the selected result types, the validation, the error line and the `saving` flag, and the **component** is only the JSX. The editor names **no endpoint and makes no permission decision** — `onSave` and the media controls' `basePath` come from the page, which is what keeps `/exercises` (a gym's module permissions) and `/platform/exercises` (`requireSuperadmin`) out of the shared UI: do not merge the two routers, and do not put an ownership branch (`gym_id`, `cloned_from_id`, `isSuperadmin`) in the editor. A shared media control takes its route root and its storage gating as props (`ExerciseImageField`/`ExerciseVideoField`'s `basePath`, defaulting to `/exercises`, and `requiresGymStorage`, false for a Base Exercise, whose objects live under `PLATFORM_STORAGE_ROOT` and are gated by no gym's bucket). Where the two screens behaved differently, unification takes the **stricter** side — removing media asks for confirmation on both now, not neither. And a platform screen that needs a gym-facing catalogue gets its own read rather than borrowing one: `GET /platform/exercises/lookups` serves the muscle and result-type catalogues because `/muscles` and `/result-types` sit behind `tenantContext` + `requireModuleAccess('TRAINING')` + `requireFeatureEnabled('training.exercises')`, and a Base Exercises page must not break when the superadmin's *selected* gym has exercises switched off (register such a route **before** `/:id`, or Express reads its name as an id). Since #965 the **read-only half** is shared the same way and for the same reason: the expanded card is `ExerciseReadOnlyView.tsx`, the editor's counterpart over the same `exerciseForm.ts` declaration and the same `exerciseFieldChrome.ts` (so a field added to the form appears in both halves and neither can be restyled alone), the media is one `ExerciseMediaPreview` (the thumbnail, never the master; no `<video>` until the player is asked for; `playing`/`onPlay` the page's so one clip plays at a time), and `⋮ → Details` is one `ExerciseDetailModal` carrying **only** the technical metadata — the internal id, Created/Modified At & By and `ViewAuditLogButton` — because the configuration it used to restate is what the card already shows. It needs a column to read, so migration 208 gives `exercises` the `created_by_name`/`created_by_type` + `modified_by_name`/`modified_by_type` snapshot pairs (#799's rule: a Base Exercise's actor is a superadmin with no `gym_memberships` row); the **platform** router is the only writer and stamps them wherever it moves `modified_at`, the media routes included, while the gym-facing `SELECT` **masks** them on a `gym_id IS NULL` row — `GET /exercises/:id` serves base rows, and a shared catalogue's rows are not the reading gym's to attribute. Those aliases shadow the columns `e.*` now expands to, so they stay after `e.*` and that `SELECT` stays top-level (a derived table would raise ER_DUP_FIELDNAME). Do not add a second read-only view, a second media preview, a second Details modal, or an actor column beside the pair. See "When two pages edit the same entity" in `docs/feature-patterns.md`.
- Every Details view offers **View Audit Log** via the shared `apps/admin/src/components/ViewAuditLogButton.tsx` — never a hand-rolled deep link. Filter by the canonical entity type + id, never by display name. See "Details view → View Audit Log" in `docs/feature-patterns.md`.
- A gym-facing read of a **platform catalogue** (the `gym_id IS NULL` rows of a shared table) goes on the gym's own router behind `tenantContext` — never on `/platform/*`, which is `requireSuperadmin` and would lock out the gym admin who needs it (`GET /exercises/base`, #718). When a gym copies such a row into its own catalogue, the copy records provenance in **`cloned_from_id`**, and that column is the only source of truth for "where did this come from": `POST /exercises/import` reads it to decide what the gym already has, and the Exercises list derives its **System sourced** / **Custom** badge from it. Do not add a source/origin column or duplicate the library row's identity anywhere else. That copy is also the gym's **import state**, and importing is what makes the row visible to the gym (#804): `GET /exercises` filters `e.gym_id = ?` and never `OR e.gym_id IS NULL`, because existing in the platform library is not the same as having been imported — a base row a gym never imported has no business in that gym's Exercises page, under any filter, search or ordering, and adding one to the library must not make it appear in every gym at once. The filter belongs in the list query, not on one control, and there is no `imported` flag to add: the copy is the state. The library is read through `GET /exercises/base` (the Import modal), which keeps offering a non-imported row, and `GET /exercises/:id` still answers for a base row; the write paths already assume this rule, since `workout-templates.ts` and `training-plans.ts` validate an `exercise_id` with `gym_id = ?`.
- A **CodeQL alert** is cleared by fixing the code, by a human dismissing it in Security → Code scanning, or by an owner-authorized merge that records the assessment — **never by a suppression comment**. Neither `// codeql[rule]` nor `// lgtm[rule]` does anything in this repository (both were tried on the same alert, #767), so a suppression comment only misleads the next reader: `api/src/test/codeql-suppressions.unit.test.ts` fails the build if one is added. Put the reasoning in prose at the sink instead, and see "Code scanning (CodeQL)" in `docs/architecture.md` for the known `js/xss-through-dom` false positive on detached media elements, which every browser upload helper of that shape will raise again.
- What the API tells a client about a **failure that reached the global error handler** is decided in exactly one place: `api/src/domain/httpErrorResponse.ts` (#966). An error carrying an explicit HTTP `status` — the `throw Object.assign(new Error(m), { status: 400 })` shape `centerContext.ts` uses, body-parser's own 400/413 — is a *deliberate* answer and keeps its message; anything else is an unexpected failure, so the client gets `500 { error: 'Internal server error' }` and the real error is logged server-side and nowhere else. The handler used to answer `err?.message` verbatim, which is how `Unknown column 'b.result_type' in 'field list'` reached a gym owner's toast. A route that needs a specific message for a specific failure gives the error a status or answers in the route — never by relying on the handler to forward a driver's words — and `handleDupEntry()`'s 409 and the storage routes' own `stage`/`path`/`details` body (#828) are unaffected, because neither reaches the handler. The same ticket's defect is the rule beside it: an **exercise instance's result type is the exercise's, never its block's** — migration 074 (#154) dropped `workout_template_blocks.result_type` and `workout_blocks.result_type` and put `result_type_id` + `target_value`/`min_value`/`max_value`/`unit` on `workout_template_exercises`/`workout_exercises` — so a JSON tree projects it from the exercise with a **LEFT** JOIN onto `result_types` (an INNER JOIN drops every exercise configured with none), exactly as `workout-templates.ts` `GET /:id` does. #1009 is the ticket that decided the remaining question: a **block has no result type to snapshot**, so `workout_block_logs.result_type` is **dropped** (migration 209) rather than re-vocabularied — nothing read it (every reader is a blanket `SELECT *`/`SELECT wbl.*` with no consumer: no admin caller for `GET /members/:memberId/workout-block-logs`, none for `GET /me/workout-block-logs`, no report), so keeping it would have meant inventing what a block's result type means when its exercises disagree and backfilling the rows holding `Rounds`/`Score`, which have no member of the `result_types` slug vocabulary, with that invention. What survives is `result_value`: **one optional, untyped free-text value** the member typed for the block ("21:04", "7 rounds + 3"), so no path may give it a type column, a derived type, a coerced legacy value or a per-block "takes no result" flag — an empty input is `null`. Typed, per-set results are the exercise instance's, in `exercise_logs` + `exercise_log_sets`. Three queries read one of 074's dropped columns before this was gated, found one ticket at a time — the two trees plus the Members App's My Training page, where `block.result_type` was `undefined` and `undefined.toLowerCase()` threw while rendering any block, so the page was down ahead of the 500 that was reported. `api/src/test/migration-074-dropped-columns.unit.test.ts` is now the gate: no production source under `api/src` or `apps/member/src` may name `result_type`, `exercise_type`, `distance_value` or `distance_unit`, because after migration 209 **no table has a column with any of those names** — and `duration_seconds` is deliberately outside that set, since 074 dropped it from `workout_template_exercises` only and it is still a real column of `workout_blocks`, `workout_template_blocks` and `exercise_logs`. Note that CI runs `npm test` in `api/` **only** (the admin job type-checks and builds), which is why that gate scans the Members App from the API suite rather than living in `apps/member/src/test`.
- A **receipt** ("factura simplificada") is issued for money *actually received*, and there is exactly one implementation of that rule: `isReceiptableEvent()` (`api/src/domain/billingEventStatus.ts`, #787). The event type must record a payment (`payment_recorded`, `recurring_payment`, `failed_billing`) **and** `deriveBillingEventStatus()` must say `paid` — which is what makes a `failed_billing` settled afterwards by Retry or Manual payment receipt-able without a special case, since #640's actions never append a second ledger row. A `waived_billing`, an `adjustment` and anything failed, expired or pending are refused. Do not add a second eligibility check, and do not put one on the `GET` routes: a `receipt_number` can only exist if the predicate already allowed it. The number itself comes from `issueReceiptNumber()` (`api/src/domain/receiptNumbers.ts`) and nowhere else — it reads the event `FOR UPDATE` before spending anything, so one payment can never burn two numbers out of the gapless per-gym, per-year `receipt_sequences`. The nightly run allocates one for every charge it settles, **after** the charge transaction has committed and in one of its own, with the failure logged and swallowed: that transaction records money the provider has already taken, so a new statement inside it can roll the charge record back while the charge stands (the `insertId` defect #635 stage 3 fixed). A receipt that fails to auto-issue stays issuable through `POST /payments/:id/receipt`, so it is never worth that risk, and `receipts_issued` is a reported counter, not a run-log column and never a reason to fail a run.
- A **`pending` payment request whose checkout page was opened is not stale** (#789). `payment_requests` carries two deadlines and they are not interchangeable: `page_token_expires` (creation + 10 min) bounds how long the *link* may be opened, and `GET /payment-page/token/:token` — the only writer that clears `page_token` on a row still `pending` — is what records that it was. `POST /billing/cleanup` therefore expires a request whose `page_token IS NOT NULL` with its token, and one whose `page_token IS NULL` only after `abandonedRequestHours()` (`api/src/domain/paymentRequestExpiry.ts`, `PAYMENT_REQUEST_ABANDONED_HOURS`, default 24, floored at 1 so a typo cannot reintroduce the defect). Do not reintroduce a single deadline, and do not add a second query or a shorter window that expires an opened request: the member is in the Card Input and a 3DS redirect while it stands, and an `expired` row is skipped by the webhook's own guard — which is how a member came to be charged with no completed request, no stored card and no `next_billing_date`. The other half of that rule lives in the webhook: **only a `completed` payload may reopen a terminal row**, and only an `expired` one, because the provider is the source of truth about money. A `failed`/`expired` payload never revives a row, and an already-`completed` row is always skipped — that skip is the handler's idempotency under Monei's retries, so nothing may widen it further. `expired` stays the cleanup response's total, because `.github/workflows/billing-run.yml` parses that field (#778).
- **Replacing a member's stored card charges nothing** (#788, migration 195). It is a card *verification*: `createCardVerificationRequest()` (`api/src/payments/provider.ts`) deliberately takes **no amount**, and the Monei adapter sends `amount: 0` + `transactionType: 'VERIF'` + `generatePaymentToken: true` — do not give that method an amount, a void path or a second provider call, and do not raise a real payment to obtain a token (the Start payment button did, which is the defect the ticket removed). The `payment_requests` row it writes exists only to carry the hosted page's `page_token` and the webhook's `provider_order`: `source = 'card_update'`, `amount = 0.00`, `charge_type_id` **NULL** — never a charge type (a `card_verification` entry in `charge_types` would put a non-charge in the cash-payment picker and in charge-type reporting). It is therefore **not a financial row**: anything that reads `payment_requests` as money excludes that source, as `GET /members`' `payment_status`, `GET /payment-requests` and `GET /me/payment-requests` do, and the webhook's card-update branch writes **no** `billing_event`, stamps no `next_billing_date` and clears none of #785's dunning counters — replacing a card is not paying, and the rejected cycle is still owed. A verification that is rejected, or completes without a token, must leave the card already on file untouched. `domain/storedCards.ts` owns the constant and the pure rules (including `cardRemovalBlock()`: removal is refused while any assignment is `active`/`paused` with a `next_billing_date`, because the nightly run skips a card-less assignment *silently*) and `api/card-updates.ts` the provider call, the insert and the reads — a new surface (staff or member) calls those rather than restating either.
- An amount crosses the **PaymentProvider boundary in minor units** (cents for EUR): every caller of `createPaymentRequest()` and `executeRecurring()` converts through `toMinorUnits()` (`api/src/payments/money.ts`), while everything on our side — `user_memberships.membership_fee_price`, `billing_events.amount`, `payment_requests.amount`, what `resolveMembershipFee()` and `priceMembershipFeeOn()` return — stays a decimal number of euros. Do not add a caller that passes a euro amount to the provider or a provider that expects euros: the nightly run and the staff Retry did exactly that for as long as the provider was stubbed in tests, and a real renewal of a 29.99 € fee would have charged twenty-nine cents. A test of a provider call asserts the `amount` the stub received.
- All config via environment variables. No hardcoded values. Payment provider credentials in particular stay in the environment — the `payment_providers` catalogue (#636) names *which* adapter a gym uses (`provider_key`), never how to authenticate as it.
- Every new code path that inserts into `gyms` must set `payment_provider_id` (NOT NULL since migration 175). Take the catalogue's default (`is_default = 1 AND deleted_at IS NULL`) unless the caller names one — `api/src/api/gyms.ts`, `api/src/test/helpers.ts` and `api/src/infra/seed.ts` are the three existing paths.
- Translated **UI labels** live in `apps/*/locales/base/{en,es,ca}.json`. Translated **data** lives in a `(entity_id, locale)` junction table with the entity's own column as the base value and fallback — never one row per language, and never a `name_es`/`name_ca` column. Resolve it server-side from the request locale (`api/src/infra/locale.ts`) and return it in a separate field (`display_name`), leaving the base column for edit forms to submit back. Since #967 there is exactly **one** implementation of those rules: `api/src/domain/nameTranslations.ts`, configured per entity by a thin wrapper (`domain/nutritionLibrary.ts` for a Nutrition Library food, `domain/exerciseTranslations.ts` for an exercise) — a new translated column adds a wrapper and a junction table, never a second `COALESCE`, a second validator or a second search clause. Three of its rules are load-bearing. The stored map (`translations`) is projected on **every** read of the entity, list reads included, because `⋮ → Edit` seeds its form from the row the page already holds (#800) and a form seeded without it submits an empty replace-all set and clears them on the first save. A write that **omits** the field leaves the stored rows alone while an explicit `{}` clears them — the distinction every replace-all section `PUT` draws, and the only thing standing between a pre-#967 client and a gym's translations. And a `?q=` matches the base name **or any** stored translation rather than only the locale on screen (a gym searching `Press de Banca` means that exercise whatever language its screen is in), with a client-side picker filtering on the same three things (`apps/admin/src/lib/exerciseNames.ts`). A **read-only consumer** surface is the one place the localized value takes the field's own name (`item_name`, `exercise_name`), since it has no form to overwrite anything. A copy copies them (Duplicate, Clone, `POST /exercises/import`); a **re-import** does not, because it exists to restore System media and must never overwrite a translation the gym corrected. In the UI the language list is the API's (`GET /exercises/locales`, `GET /platform/exercises/lookups`, `GET /platform/nutrition-library/locales`) and never a list in a component, and `apps/admin/src/lib/localeLabels.ts` is the one place a locale gets a *label*, resolved before `t()` is called. See "Translated Catalog Content" in `docs/feature-patterns.md`.
- A **Member's default language** is `members.preferred_locale` (#1039, migration 220) and it is the one stored locale in the product: nothing else persists a language, and no second list of languages exists. Which locales *exist* stays `SUPPORTED_LOCALES` (`api/src/infra/locale.ts`, env-configured, parsed at boot), which is why the column carries **no CHECK** — a deployment adding `fr` would store a locale the application accepts and the database refuses — and why `parseMemberPreferredLocaleInput()` (`api/src/domain/memberPreferredLocale.ts`) is the only place a request's value is judged: it reuses `normalizeLocale()`, so what is stored is the allowlist's own string and `es-ES` folds onto `es`. `NULL` means **no preference** and is what every member written before the migration means — the per-request resolution (`x-locale`, then `Accept-Language`, then the base locale) applies unchanged, so there is no backfill, no seeded default and no stored copy of today's default. Its three answers are every partial write's: a field the request does not *mention* keeps the stored value, an explicit `null`/`''` **clears** it, and anything else is a 400 rather than a coercion — which is why `PATCH /me/profile` writes `preferred_locale = IF(?, ?, preferred_locale)` keyed on whether the field was supplied (a `COALESCE` on the value makes clearing unpersistable, the `products.mandatory` rule), and why both of its reads narrow the column through `toMemberPreferredLocale()` rather than reporting a locale the deployment no longer configures. In the Members App the preference is **applied in exactly one place**: `apps/member/src/components/MemberLocalePreference.tsx`, mounted once by the locale layout, over the pure `preferredLocalePath()` in `apps/member/src/lib/memberLocale.ts` — which is also the app's one language declaration (`MEMBER_LOCALES`, which `middleware.ts` hands to next-intl rather than keeping a list of its own). A page never switches the locale for itself, because the locale of a page *is* its first URL segment: next-intl resolves the messages from it, `<html lang>` and the Clerk localization follow it, and `apiClient` sends it as `x-locale`, so a second mechanism would make those four disagree. `preferredLocalePath()` answers *stay put* for a member with no preference, for a locale this app has no route segment or messages for, and for a member already on theirs — the case that would otherwise loop — and the component is skipped while a superadmin impersonates, since the preference is the member's and the staff user chose their own locale in the URL. Do not add a second stored locale, a per-gym or per-device language preference, a language list in a component, or a page that redirects on the preference itself.
- The **Member entity is called a Member on screen, in every language** (#1026): `Member`/`Members` in English, **`Miembro`/`Miembros`** in Spanish, **`Membre`/`Membres`** in Catalan. `Socio`/`Socios` and `Soci`/`Socis` are retired as user-facing terms — new copy never reaches for them, and `api/src/test/member-terminology.unit.test.ts` fails the build if either appears in a locale **value** of either app or in the privacy policy's own prose (in the API suite, because CI runs `npm test` in `api/` only). It is a copy rule and nothing else: the locale **keys** are English identifiers, and `members`, `Member`, `MEMBERS`, the `member` role, `/members`, `member-centers` and every other technical identifier are the domain's own names and stay as they are — renaming one to match a label is the thing the ticket forbids. Two things are deliberately not drift. The compound name of another entity keeps that entity's wording rather than the Member's: the **Membership Fee** is `cuota de membresía` / `quota de membresia` and the **Membership Plan** is `plan de membresía` / `pla de membresia`, which is what these files already said everywhere else, so removing the retired word renamed no second entity. And `api/src/lib/receipt-pdf.ts`'s `'Socio'` is the placeholder printed where a person's *name* goes on a Spanish fiscal receipt, not a label of this domain, so it is out of the gate and out of the rule. Do not reintroduce the retired words, translate the entity a fourth way, or add a second place that decides its name.
- **Training Plan Templates** and **Assigned Training Plans** are two different things, and the UI says which (#970): the reusable, gym-wide definitions are *Training Plan Templates* (`/{locale}/training-plan-templates`, and Cordel's *Base Training Plan Templates*, whose nav label names the templates its page is headed after), while the plans a member holds are *Assigned Training Plans* — the sidebar item, the `/{locale}/training-plans` heading, the Member card's section and their empty states. It is a wording rule and nothing else: the locale **keys** (`nav.training_plans`, `training_plans.title`, `members.section_training_plans`, `member_training_plans.title`), the routes, the `training.training_plans` feature key and every API field stay as they are, so do not rename an identifier to match a label; singular entity strings (`+ New Training Plan`, *From a Training Plan Template*) name one plan rather than the section and keep their wording; and the Members App's own page stays *My Training Plan*, which already says whose plan it is.
- Backend-first: define the API contract before building UI.
- Do not duplicate business logic in the frontend.

## API tests

Run tests with `npm test` inside `api/`. All test files live under `api/src/test/`. Reuse the helpers in `helpers.ts` — `createTestGym`, `createTestMembership`, `request`, etc.

### Unit tests vs integration tests

Write **unit tests** when the code under test has no DB or HTTP dependency — pure functions, middleware logic, crypto/validation helpers. No `createTestGym`, no `cleanupTestGyms`, no `db.end()`. Mock external dependencies with `vi.mock` or `vi.spyOn`.

Write **integration tests** for routers and anything that must exercise the full Express + MySQL stack. All rules below apply to integration tests only.

Good candidates for unit tests:
- Signature verification and payload parsing (e.g. `payments-provider.test.ts`)
- `requireModuleAccess` / `requireModuleWrite` permission matrix
- `tenantContext` and `centerContext` middleware
- Pure helper functions and input validation

### Rules for every new integration test file

- One file per domain (e.g. `bookings.test.ts`, `members.test.ts`).
- Always call `cleanupTestGyms()` in `afterAll` and `db.end()` last.
- Always create a fresh gym + membership in `beforeAll` — never share state across `describe` blocks.
- Insert DB rows directly via `db.query` for setup; use the HTTP API (`request`) for the action under test.
- Do **not** add a `slug` column to `centers` — it does not exist in the schema.

### What to cover for every new router

1. **Tenant isolation** — a resource from gym A returns 404/403 when accessed with gym B's `x-gym-id`.
2. **Auth** — unauthenticated request returns 401; wrong role returns 403.
3. **Happy path** — the main success case returns the expected status and shape.
4. **Key invariants** — e.g. capacity/waitlist for bookings, 409/keep/expire for training plans, soft-delete hidden from list + restore for members.

### cleanupTestGyms dependency order

When adding a new domain that has FKs pointing to `members` or `gyms`, extend `cleanupTestGyms` in `helpers.ts` to delete those rows first. Current order: `bookings → user_membership_services → members → class_sessions → activity_types → products → gyms`. A table whose FK to a catalog table (e.g. `products`) has no `ON DELETE CASCADE` must be deleted before that catalog table, not only before `members`.

## Finishing a task

Before opening the PR, run these checks in order:

1. **Migration review** — if any migration file was added or changed, run the `db-reviewer` agent on it. Fix all BLOCKERs before continuing.

2. **Test files** — for every new router, run the `test-writer` agent to generate `api/src/test/<router>.test.ts` (integration test). For any new pure functions or middleware, also write a unit test file (no DB helpers, use `vi.mock`/`vi.spyOn`). Run `npm test` inside `api/` to confirm all pass.

3. **Doc updates** — check whether the changes warrant updating any `.md` files:
   - `docs/roadmap.md` — mark the ticket done and update the Status section if the feature is complete.
   - `docs/architecture.md` — update if new tables, routers, middleware, or patterns were introduced.
   - `docs/feature-patterns.md` — update if a new pattern or template emerged that future tickets should follow.
   - `docs/go-to-production.md` — add a checklist item whenever the ticket defers something "until production" (there is no production environment yet); tick items the ticket completes.
   - `CLAUDE.md` — update if a new hard constraint, convention, or cleanup rule was established.

   Only update a file if the ticket genuinely changes what it documents. Navigation-only or i18n-only changes rarely need doc updates; new API surface, DB schema, or architectural patterns almost always do.

4. **Sync with origin/main** — run `/finish-feature` (or manually: `git fetch origin && git merge origin/main`). Resolve any conflicts carefully (see the Parallel agents section above). Re-run tests if any conflicts touched API code. The working tree must be clean before opening the PR.

5. **Open the PR** — commit doc changes together with the feature and run `gh pr create --base main` on a branch named `feat/<slug>-<issue-number>`. Include the issue number in the PR title and body (`Closes #N`).
