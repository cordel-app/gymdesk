# Gymdesk

Multi-tenant Gym Management SaaS. Express backend + Next.js frontend + MySQL 8 (Oracle HeatWave) + Clerk auth.

## Before implementing any feature

For any issue that involves new API surface, DB schema changes, or significant UI work, write a plan first and get approval before coding. A plan should cover: migrations, API endpoints, frontend sections, tests, and doc updates. Keep it concise — bullet points per layer, not prose.

Read these files first — they contain the full context needed to implement correctly:

- `docs/architecture.md` — starts with a TL;DR; full codebase structure, auth, roles, DB conventions below it
- `docs/feature-patterns.md` — step-by-step checklist and code templates for new features
- `docs/roadmap.md` — ticket order, current status, and phase decisions
- `docs/decisions.md` — settled architectural choices (MySQL, Clerk, no ORM, etc.) — don't re-litigate these
- `docs/payments.md` — **required reading for anything that touches money**: the first-payment (CIT) and recurring-charge (MIT) processes end to end, the data model with its CHECK sets, the provider boundary, and the manual test runbook. The constraints below are the rules; that document is how the two processes actually run.

Use **Members** as the reference implementation for staff-level CRUD with soft-delete.
Use **Plans** (`api/src/api/membership-plans.ts` + `apps/admin/src/app/[locale]/plans/`) as the reference implementation for an admin-only CRUD API and its Inline row CRUD frontend (expandable rows, no modals — see `docs/feature-patterns.md`). For the Modal CRUD frontend shape, see Class Types.

Use `/plan` to generate a structured implementation plan before coding. Use the `db-reviewer` agent to check migration files. Use the `test-writer` agent to generate test files.

## Parallel agents (worktree workflow)

Multiple Claude Code agents may work simultaneously, each in its own worktree and feature branch.

### Ground rules

- **One agent per worktree.** Never modify files in another agent's worktree directory.
- **One feature branch per task.** Always branch from `main`; never branch from another feature branch.
- **No destructive Git commands** (`git reset --hard`, `git clean -fd`, `git checkout -- .`, `git restore .`, `git branch -D`) unless the user explicitly requests them. Never discard changes to make a merge succeed.

### Required sync before feature completion

Before a feature is considered complete, the agent must integrate the latest `origin/main` into its branch:

```bash
git fetch origin
git merge origin/main   # always merge, never rebase
```

If conflicts occur:
- Resolve them carefully — preserve valid changes from **both** sides.
- Never blindly choose "ours" or "theirs".
- Pay particular attention to `docs/roadmap.md` (see below).
- Run tests after resolving conflicts.
- Confirm the working tree is clean before marking the feature done.

Use `/finish-feature` to run through the full sync + test + status checklist automatically.

### Special handling of docs/roadmap.md

`roadmap.md` is a shared file modified by multiple parallel agents.

- Keep changes minimal and focused on the current task.
- Do not reformat or reorder unrelated sections.
- Do not remove another agent's entries.
- When resolving merge conflicts in `roadmap.md`, keep changes from both sides — merge the sections manually rather than picking one side.
- Always sync with `origin/main` before the final commit if `roadmap.md` was modified.

## Hard constraints

- No microservices, no event sourcing, no AI/LLM integrations.
- One database: MySQL 8 (HeatWave when deployed). No additional stores without a concrete reason.
- Every domain table must have `gym_id`. Every query must filter by it.
- A `weekday` column means **0=Sunday … 6=Saturday** (`gym_operating_hours`, `activity_type_schedule_rules`, `trainer_availability`, `training_plans`). A column storing luxon's ISO numbering (1=Monday … 7=Sunday) must be named `iso_weekday` instead, so the two bases can never be joined by accident — see `member_recurring_slots` (migration 169).
- A new `member_notifications.type` goes in **two** places: the `NotificationType` union in `api/src/infra/notifications.ts` **and** the `chk_member_notifications_type` CHECK (current definition: migration 170). Adding only the first makes every insert of that type fail invisibly — `sendNotification()` is fire-and-forget and only logs.
- A new `recordAudit({ entityType })` value also needs an `AUDIT_ENTITY_REGISTRY` entry in `api/src/infra/audit-registry.ts`. Without one the rows write but carry no `entity_name`, and the type never reaches the Audit Log's entity-type filter (`GET /audit-logs/meta`).
- Any new code path that inserts a `user_memberships` row must call `snapshotAssignedPlan()` (`api/src/api/assigned-plan-snapshot.ts`) inside the same transaction. An Assigned Plan owns the commercial configuration it was assigned with (#635 §11–§17) — an assignment created without one reads back as `snapshot_captured: false` and silently falls back to the live catalogue, so a Plan or Sellable Item edited later would move what it bills.
- Any new code path that *edits* an existing assignment's snapshot must call `materialiseAssignedPlanSnapshot()` first, in the same transaction (#635 stage 6). The live fallback is all-or-nothing: the moment one section of an uncaptured assignment is written, the assignment counts as captured and every section the edit did not mention reads back as empty. An edit also stays on that assignment — never write through to the Membership Plan, another assignment or the Sellable Item — and a `cancelled`/`expired` assignment is not editable at all.
- Billing reads the **Assigned Plan snapshot**, never the live catalogue, for an assignment that already exists (#635 §13–§17). A query that projects, charges or advances an assignment's billing takes its cadence from `ASSIGNMENT_CADENCE` in `api/src/api/assigned-plan-snapshot.ts` (`COALESCE(um.recurring_billing_*, bp.recurring_billing_*)`) and therefore **LEFT** JOINs `billing_policies` — an INNER JOIN drops every assignment whose Plan lost its policy. Since #635 stage 13 (migration 189) `billing_policies` holds that pair and `auto_renew` and nothing else: Initial Billing, Initial Service and Recurring Service are gone, **Billing & Duration is the Plan's only billing section** (the surviving pair is its *Billing frequency* — Free/Paid/Bonus say how long a contract runs, never how often it charges), and no second cadence, service-period concept or per-plan billing column may be reintroduced. Since #820 a Plan's *Billing frequency* is also a **choice of two** — Month (`1 month`) or 4 Weeks (`4 week`) — named once in `api/src/domain/planBillingFrequency.ts` and enforced by `PUT /membership-plans/:id/billing-policy`, never by the dropdown alone: the stored shape is still that `(interval, unit)` pair, so a new pair is added in **two** places (the declaration and, mirrored, `PLAN_BILLING_FREQUENCY_OPTIONS` in `apps/admin/src/app/[locale]/plans/planProfile.ts`) and never as a symbolic column. A cadence outside the two is refused on write but still read, billed and displayed wherever it is already stored — `planBillingFrequencyOf()` answers `null` for it, and a surface that coerced that `null` to Month would tell a gym it bills monthly while the run charges every two months. Prices and benefits come from `user_memberships.membership_fee_price`, the `user_membership_{session,oneoff,periodical}` rows, the `user_membership_promotion_*_snapshot` rows and `user_membership_services`' own price columns; the live catalogue is only the fallback for an assignment that captured no snapshot. The same holds for a path that merely *displays* an assignment's benefits or cadence, on a staff screen or a member-facing one (`GET /me/membership`, #635 stage 10): it reads the assignment's rows through `loadPlanBenefitsForSimulation()` / `ASSIGNMENT_CADENCE`, so what the Member is shown cannot drift from what the nightly run charges them. The Plan-keyed `membership_plan_benefits` (migration 006) is gone — migration 184 — and nothing replaces it.
- A **Sellable Item's Billing Frequency** is a separate question from a Plan's cadence, and since #821 it is a choice of **five**: Once, Per Session, 4 Weeks, Month, Year, named once in `api/src/domain/sellableItemFrequency.ts` and mirrored for the form in `apps/admin/src/app/[locale]/financials/sellable-items/sellableItemFrequency.ts`. `week` is **retired, not deleted**: `gym_charges_billing_frequency_check` (migration 123) still permits all six values and there is no backfill, because an item a gym configured weekly is a real price whose period is neither a month nor 28 days. So "what may be stored" and "what may be configured" are two different answers, and `sellableItemFrequencyWriteError(next, current)` is the one place that decides the second — `POST /sellable-items` refuses `week` outright, `PUT /sellable-items/:id` accepts it only when it is what the row already holds, so editing another field of a legacy item neither 400s nor silently rewrites its frequency, and nothing may be moved *onto* it. `isRecurringFrequency()` (`domain/sellableItemClassification.ts`) still counts `week` as recurring, so a legacy item keeps classifying as a `periodical` benefit and keeps billing. The editor renders the retired value as a **disabled** option only while the form holds it — never as a selectable one, and never coerced to another frequency — and `POST /:id/duplicate` copies it verbatim, because Duplicate is a copy, not the dropdown. A new frequency therefore goes in **three** places (the declaration, its mirror, and the CHECK beside them); do not add a second accepted-set list in a route or a page.
- A **Sellable Item's Mandatory flag** (#832, migration 200) is `gym_charges.mandatory`, and it is one column for both kinds of row that table holds: the per-gym System items seeded from `charge_types` (`is_system = 1` — the ticket's "Base Sellable Items", the Insurance Fee among them) and the gym's own (`is_system = 0`, "Custom"). Do not add a second flag, a platform-level sellable-item catalogue or a per-kind editor for it. It is **editable on a System item**, so `PUT /sellable-items/:id` writes it outside the `IF(? = 0, …)` `is_system` guard that still freezes a System row's name/type/units, and it is written as `mandatory = IF(?, ?, mandatory)` keyed on whether the request supplied the field — a `COALESCE` on the value itself would make unchecking the box unpersistable, which is the one way a boolean column of this shape goes wrong. A body value that is neither a boolean nor 0/1 is a 400, never coerced (the string `"false"` is truthy). There is no CHECK on it (the router coerces to `? 1 : 0`, and `ADD CONSTRAINT` rebuilds `gym_charges` under `ALGORITHM=COPY`). Exactly **one** thing reads it, since #893: a mandatory item is part of every **Membership Plan** benefit section, and `api/src/domain/mandatoryPlanBenefits.ts` is the only place that decides what that means. Its candidate set is the gym's **active, non-deleted** mandatory items — an inactive or deleted one is ignored, because forcing it in would fail every Plan save on a catalogue change nobody asked for — and which section each belongs to is `classifySellableItem()` (#550) and never a second mapping. `mergeMandatoryBenefits()` is what a read reports (`GET /membership-plans/:id/{session,oneoff,periodical}-benefits` and `enrichPlan`'s three embedded sections), adding a missing mandatory item as `implicit: true` at quantity 1; `withMandatoryBenefits()` is what the replace-all `PUT` writes, so a client that drops one has it **preserved rather than 400d** — that is what makes an existing Plan pick up a newly mandatory item the first time any of its sections is saved. A submitted mandatory item passes through untouched, quantity included: Mandatory says the item must exist, never what its quantity is, and it is not a reason to change one. The enforcement is the server's — the shared `SellableItemBenefits.tsx` takes an explicit `enforceMandatory` opt-in (the Plans page only, never Promotions) and merely renders the row without a `✕` and without a picker that could swap the item away, so a client bypassing it changes nothing. Everything else about the flag is still unread and still out of scope: automatic inclusion in a **Billing** Plan, refusing its removal from one, Billing Plan pricing and any Insurance Fee special case, so a path that acts on the flag beyond the above is deciding that behaviour and needs a ticket. In particular #893 changes no billing: a mandatory item reaches an assignment's Assigned Plan snapshot the ordinary way, as a stored Plan benefit row, and nothing back-fills the Plans that were never saved again.
- A **Sellable Item of Type `Sessions` prices the whole package**, not one session: `gym_charges.amount` is the total for the `units` sessions it contains, so `Units: 5` beside `Price: €50.00` means €50.00 for the five and never €250.00 (#942). Nothing multiplies a price by a unit count, and no per-session price is stored, computed or displayed anywhere. What the ticket added is the sentence that says so, and `apps/admin/src/app/[locale]/financials/sellable-items/sellableItemPriceNotes.ts` is the one place that decides it — `sessionPackageNote()` answers the *Total price for N sessions* wording (ICU-pluralised off the item's own `units`, with a package wording for a session item whose nullable `units` is unset) and `null` for every other type, which is what keeps fee-based items untouched; `taxNoteKey()` answers which `(tax …)` suffix a displayed figure takes, and `null` for an item with no `applied_tax_rate` rather than claiming a tax that is not configured. Every surface showing such a price asks that module rather than testing `type === 'sessions'` beside a price for itself, and the two form hints ask `sessionPackageNoteForForm()` with the draft's live Type and Units so the sentence tracks what is being typed rather than the saved row. Do not add a per-session price column, a per-session figure derived from `amount / units`, or a second place that decides this wording.
- The **nightly billing run** (`POST /billing/run`) prices the cycle `next_billing_date` names, never "today": `priceMembershipFeeOn()` (`api/src/api/membership-fee-pricing.ts`) asks the Billing Simulation's own `resolveMembershipFee()` what that date costs and whether it is waived, so what is charged cannot drift from what the staff screens and the Member's My Membership page show (#635 stages 11–12). A waived cycle calls no payment provider and writes no `payment_requests` row — it records a `waived_billing` billing event and advances `next_billing_date`, leaving `last_billed_at` untouched. A new `billing_events.event_type` goes in **two** places: the writer and the `billing_events_event_type_check` CHECK (current definition: migration 185) — adding only the first makes the INSERT fail and takes the run's transaction with it.
- A **`next_billing_date` written onto an assignment is never today or earlier** (#790). The payment webhook stamps the first one as the first `starts_at`-anchored cycle boundary *strictly after* UTC today, and any transition back to `active` (Reactivate, a `PUT` status flip) walks a past one forward the same way along its own schedule — both through `api/src/domain/nextBillingDateStamp.ts`, which reads the cadence via `ASSIGNMENT_CADENCE` (LEFT JOIN) and every date, today included, as a `YYYY-MM-DD` string from SQL, over the one pure rule `firstBillingDateAfter()` (`api/src/domain/billingDate.ts`, stepping with the run's own `advanceBillingDate()`). A back-dated `starts_at` stays allowed: the cycles that elapsed before the first payment, and the ones missed while paused, are **written off** — no catch-up charge, no `adjustment` row — because the first payment is priced on *today* (`currentCycleDate()`), so stamping `starts_at + cadence` charged one elapsed cycle per night and then the paid cycle a second time. A new writer that puts an assignment (back) on the run's schedule calls one of those two helpers rather than computing a date itself; the run's own `advanceBillingDate(next_billing_date)` step and the staff Retry/Manual payment's one-cycle advance are unchanged.
- A rejected recurring charge **escalates, it does not repeat** (#785, migration 194). The nightly run counts consecutive rejections of the cycle `next_billing_date` names in `user_memberships.failed_attempts` (+ `last_failed_at`) and the second one pauses the assignment (`recordStatusChange`, `active → paused`, `source = 'system'`) — which is the whole mechanism, since a `paused` row is outside the run's `WHERE status = 'active'`. The count advances per run **day** (`DATE(last_failed_at) = UTC_DATE()`, compared in SQL so no DATETIME crosses a timezone conversion): a rejection on a date the assignment was already rejected on is recorded but does not escalate, because #781's second daily attempt becomes the day's real run whenever the first crashed. The retry is therefore the **next run day**, never a second attempt in the same loop: a card declined seconds ago declines again, and `next_billing_date` not moving is what schedules it. Only a provider **rejection** counts: `provider_error` (the provider threw or never answered — the charge's outcome is unknown, so a night the provider is unreachable would otherwise pause a gym's whole book) and `no_payment_method` (nothing was attempted) leave the counter exactly as it was, in both directions. Anything that settles or skips the cycle clears it — the run's own success and waived branches, the payment webhook's `completed` branch (a member paying their checkout link settles the same cycle), both staff actions through `clearDunningState()` (`api/src/domain/billingEventPayments.ts`), and any transition back to `active`, because reactivating means "bill this again" and a resumed assignment gets the documented two attempts rather than one. `domain/billingDunning.ts` is the one place that decides all of this (`countsTowardPause`, `registerRejection`); a new failure branch in the run asks it rather than incrementing the column itself, and a new code path that settles a cycle clears the pair. The decision is taken from the row **under the run's `FOR UPDATE` lock**, never from the row the due query read before the provider round trip: a staff payment landing in that window clears the pair, and deciding from the stale count would write it back and pause a member who has just paid. The columns are **not** part of the Assigned Plan snapshot (`has_billing_snapshot`) for migration 192's reason, there is no CHECK on them (`ADD CONSTRAINT` rebuilds `user_memberships` under `ALGORITHM=COPY`), the escalation is not a new status, and reactivation stays explicit — clearing the count never flips `paused → active`.
- A **system-wide nightly run** (`POST /billing/run`, `POST /recurring-bookings/run`) claims its slot through `claimRun()` and closes it through `finishRun()` (`api/src/infra/run-log.ts`), from the success path **and** the `catch` — never by stamping a `last_run_at`. The rule is **one *completed* run per UTC date** (#780, migration 193): both logs are histories now, one row per run, and a run is refused only when a run for today's UTC date already reached `completed`. Do not reintroduce an "N hours since the last start" window — a cron GitHub fires late then skips a day, and a stamp written before the first row is touched locks the day when the run crashes. Overlap is the `in_progress` half of the guard (a row younger than `STALE_RUN_MINUTES`, `api/src/domain/runGuard.ts`, answers `429`); a stale one is taken over. "Today's run already completed" answers **`200 { skipped_reason: 'already_completed_today', run_date, …zeroed counters }`**, never `429` — the second daily attempt is a safety net, not an error, and the counters are what `.github/workflows/*-run.yml` parses (#778). The field is `skipped_reason`, never `skipped`, which is already a numeric counter of the recurring booking run. A new run status goes in **two** places: `RunLogStatus` in `domain/runGuard.ts` and the `chk_<table>_status` CHECK (current definition: migration 193).
- There is exactly **one** implementation of "what does the Membership Fee cost on this date": `resolveMembershipFee()` (`api/src/domain/billingSimulation.ts`), and every path calls it — the Billing Simulation, `GET /me/membership` (its `membership_fee` and `upcoming_payments`), the Promotion apply/revoke adjustment (`currentMembershipFeeInTx()` in `membership-promotions.ts`) and, through `priceMembershipFeeOn()`, the nightly run and every staff surface (#635 stage 12). A second copy of the arithmetic is what stage 12 existed to remove: the Member was shown one price and charged another for the same cycle, in both directions. An applied Promotion's **Membership Fee Benefit lives inside the Promotion's own Free/Paid/Bonus timeline and ends with it** (the thread's stage 12 answer (a)) — a Promotion configured with no months discounts nothing at all, and a benefit whose own `duration_months` outlasts the Promotion is capped at it (`effectiveBenefitDurationMonths`, #625). A **stored** agreed price is therefore never the answer for any cycle, and since #635 stage 15 (migration 191) there is none: `user_memberships.final_price`, the `billing.date_aware_membership_fee` flag that gated the corrected pricing and the `payments.membership_fee_drift` report that quantified it are all gone, date-aware pricing is unconditional, and **no stored, promotion-discounted price column may be reintroduced** — price the cycle. The shared entry point is `api/src/api/membership-fee-pricing.ts`: `priceMembershipFeeOn(row, date)` for a given cycle, `currentMembershipFee()` / `currentMembershipFees()` for "what does this member pay now" (the cycle `currentCycleDate()` names — never one already past), and `FEE_ASSIGNMENT_COLUMNS` for the columns any of them needs. Any surface that shows or charges an assignment's fee — the Assigned Plans list and card, the Payments dashboard's projected rows, a staff- or member-raised payment request, My Membership — goes through it and reports the result as a computed `membership_fee`, never as a column. The number every path discounts *from* is `regularMembershipFee()` (`api/src/api/user-memberships.ts`) — the assignment's frozen `membership_fee_price`, then its Plan's price window, then a non-zero `base_price`; `base_price` alone is a constant 0 since migration 058. `membership_fee_price` is also where a **negotiated** fee lives (there is no second column for it), so a path that writes one is editing the snapshot and must materialise it first; `discount_reason` marks it as negotiated (which is what keeps `POST /membership-plans/:id/pricing/apply-to-assigned-plans` off it), and a past `discount_expires_at` is the one case that reads the Plan's price window instead (`regularMembershipFee`'s `ignoreFrozenFee`).
- A **Membership Plan's catalogue price** is quoted gross-and-net, and the rate that split is taken at is decided in exactly one place: `selectPlanTaxRates()` (`api/src/domain/planTaxRate.ts`, #817). `membership_plans.tax_rate_id` is nullable and the Pricing editor offers that as **Default**, which means the gym's system rate (`tax_rates.is_system = 1`, non-deleted — the row `seedSystemPtPackage()` already picks), so the helper answers two different questions: `own` is what a screen *displays* as the Plan's Tax rate (`null` ⇒ "Default", unchanged since #413) and `effective` is `own ?? system`, which is what `computePriceFields()` splits at and what `applied_tax_rate` reports. Resolving that fallback in the frontend is the defect the ticket removed — a Plan on Default had no rate, so `enrichPlan` returned a null split and the Current price rendered `—` for a Plan that has a price. Any surface showing a Plan's price reports the server's `amount_incl_tax`/`amount_excl_tax` and does no arithmetic of its own (`formatPlanCurrentPrice()` in `plans/planProfile.ts`), a soft-deleted rate is still shown as a Plan's own but is never chosen as the gym default, and no second "effective tax rate" resolution — in a query, a router or a page — may be added beside it.

- A code path that prices an assignment's **Membership Fee** on a given date applies the assignment's own Billing & Duration through `classifyPlanDurationPeriod()` (`api/src/domain/planDuration.ts`): the Free Period, the Pre-paid Duration and the Bonus Duration charge no fee, counted from the assignment's `starts_at` — never snapped to the first of its month, which is a Promotion preview's anchor, not a real contract's (#635 §7, stage 8). **An applied Promotion outranks it**: where a Promotion governs the date (inside its own timeline, or applying its Membership Fee Benefit) it decides the fee alone, per the #635 thread's Q2 answer — stacking the two also lets the Plan's free month override a Promotion's paid one, which inverts that answer. The durations come from `user_memberships.free_periods`/`paid_periods`/`bonus_periods`/`pay_beforehand_periods` and fall back to the Plan's live columns only for an assignment that captured no snapshot at all; a per-column `COALESCE` is wrong here, because the columns are nullable and a Free Period added to the Plan later would reach assignments that already exist (§13). Each of those four numbers is a **count of the assignment's own Billing Frequency periods**, never of calendar months (#892, migration 201 — the rename is what the columns say now): `PlanDuration` carries the cadence it is counted in, so `toPlanDuration()` takes it as a required argument (resolved through `ASSIGNMENT_CADENCE`, `1 month` when there is none) and no pricing path can silently count a 4-weekly contract's Free Period in months. Changing a Plan's Billing frequency therefore changes the unit and never the stored numbers, and a **Promotion's** own `free_months`/`paid_months`/`bonus_months` stay calendar months — `promotionTimeline.ts` is untouched by that rule. Only the Membership Fee is waived — a Plan's Period Benefits are still charged in a free period. The **Pre-paid Duration** (`pay_beforehand_periods`, #635 stage 13, migration 189) is the Promotion's own column on a Plan: the first N periods of the Paid Duration, already paid up front, so they charge nothing and read as `prepaid_plan` — a pre-paid cycle, never a waived one — and it is bounded by the Paid Duration (0..`paid_periods`) wherever it is written, `toPlanDuration()` clamping what it reads.
- A **simulation** of what a Plan will bill is a projection over that classifier, never a second copy of it (#818). The Membership Plan card's **Example Timeline** — `api/src/domain/planExampleTimeline.ts`, embedded by `enrichPlan` as `example_timeline` and served by `GET /membership-plans/:id/example-timeline` — steps one row per billing period with `advanceBillingDate()` over the Plan's stored `billing_policies` pair (a pre-#820 cadence included, stepped exactly as stored) and takes each row's Status from `classifyPlanDurationPeriod()` at that row's own start date. Since #892 the classifier counts those durations in the very cadence these rows step by, so a row's status is the whole row's status: a 4-weekly Plan with Free Period = 2 shows exactly **two** free rows. (It showed three until #892, because the third 4-week period still started inside two free calendar months; the ticket reverses that in the nightly run as well as in the preview, so the table still cannot advertise a charge the run does not make.) It replaces #485's Billing Events Forecast, which read price × cadence and never looked at Billing & Duration — `domain/billingForecast.ts` is gone; do not reintroduce a Plan projection that ignores the durations, a second place that decides which period is Free/Pre-paid/Pay/Bonus, or any tax arithmetic in the page (the row carries the server's VAT-inclusive `amount` plus a `waived` flag, and a Plan with no price reads `—`, never €0.00). Nothing is persisted and nothing is charged. The table itself is the shared `apps/admin/src/components/ExampleTimeline.tsx`, rendered by both the Plan and the Promotion card and holding no entity knowledge — a second simulation design for one of them is what the ticket forbade; each page keeps its own status labels (the Plan's read *(benefit)*, never *(promotion)*) and its own Billing cell. Since #915 the Plan card carries a **second** projection beside it, and the two answer different questions on purpose: the Example Timeline is one row per billing *period* and is about the Membership Fee alone, while the **Billing Event Simulation** is one group per billing *date*, listing every line that falls on it — the fee plus each Sellable Item the Plan carries. Neither replaces the other and neither may grow into the other. `api/src/domain/planBillingEventSimulation.ts` is that second projection, and it is a **thin adapter over the engine, never a second one**: it expresses the Plan as the hypothetical assignment a member enrolling today would hold and hands it to `computeBillingSimulation()`, then does exactly two things of its own — supply the horizon floor and re-group the engine's cadence sections by date. A path that computes a date, an amount or a period status itself instead of reading the engine's is the thing the ticket forbade. The hypothetical assignment carries no Promotions, no Additional Periodic Services and no Personal Membership Fee Benefit (none is a property of a Plan, and inventing one advertises a price no member is promised) and it is open-ended, because a Paid Duration says how long the contract runs and never when billing stops. The horizon is `minimumCycles` on `BillingSimulationInput` — at least `stream.start + N x cadence` for *every* recurring stream, `SIMULATED_CYCLES = 2` — so the length is derived from the frequencies present and never from a month count, and it only ever *raises* the horizon, leaving #629 §6's first-regular-charge rule intact. Do not convert two frequencies to a common cadence to make them share a group (each item is its own stream; a shared *date* is what a shared group means), do not drop a `waive`d line because it costs 0 (it is a billing event, shown at €0 beside its regular price), and do not put tax arithmetic in the projection or the page: the whole thing runs in **VAT-inclusive euros**, grossed up once by `enrichPlan` through `computePriceFields()` with the stored amount as the fallback for an item that has no rate. That conversion is exact only because a Plan may configure `no_benefit`/`waive`/`percentage_discount` and nothing else (#896 §16), so a Plan-side action that takes an *amount* would have to be priced net — which is another reason §16 is the CHECK's to enforce and not the dropdown's. Since #922 that projection is **shared**: its result shape, its `SIMULATED_CYCLES` horizon floor and its group-by-date re-grouping live in `api/src/domain/billingEventSimulation.ts`, and each entity owns only the adapter that expresses itself as a hypothetical assignment — `planBillingEventSimulation.ts` and `promotionBillingEventSimulation.ts`, rendered by one frontend component (`apps/admin/src/components/BillingEventSimulation.tsx` over the JSX-free `apps/admin/src/lib/billingEventSimulation.ts`), with the labels resolved in each page's own namespace. A **Promotion's** Billing Event Simulation (`GET /promotions/:id/billing-event-simulation`) is therefore the same projection over a different context: the Sellable Items it grants, each at the price its grant's own pair gives the units or periods that grant covers and at the regular price after them, open-ended because a Promotion reaching its End Date never revokes a standing application (#900), and anchored on its own `starts_at` when that is still in the future. It carries **no Membership Fee line** — a Promotion has no fee of its own, the fee belongs to whichever Plan it is applied alongside, and inventing one advertises a price no member is promised; what a Promotion does to a fee is the Example Timeline beside it. A third surface that wants this projection adds an adapter and a caller, never a second engine, a second grouping or a second component.
- The **Personal Membership Fee Benefit** (#772, migration 192) is the one fee benefit bounded by nothing. - A Sellable Item configured **inside** a Promotion or a Membership Plan carries an `(action, value)` pair beside its quantity (#896, migration 203), and the pair belongs to that relationship alone — never to `gym_charges`, which is what lets the same item be waived by one Plan and discounted by a Promotion. The vocabulary is the existing `PromotionBenefitAction`, and `applyPeriodBenefit()` stays the one place a pair becomes an amount: `applyLineBenefit()` (`api/src/domain/sellableItemBenefitActions.ts`) only decides *what* amount to hand it — the **line** (`unit × quantity`), never the unit, per the ticket thread. The two option sets live in that module, are mirrored by the `chk_<table>_action` CHECK beside each of the twelve tables, and since stage 4 are mirrored again for the browser in `apps/admin/src/lib/sellableItemBenefitActions.ts`, so a new action goes in **three** places: a Promotion may configure all five (`no_benefit`, `waive`, `percentage_discount`, `fixed_discount`, `fixed_price`), a Membership Plan only the first three (§16 — a Plan cannot configure *Fixed discount* or *Fixed Price*, and the CHECK is what enforces that rather than the dropdown). `benefitConfigError()` is the one validation, mirrored in SQL by `chk_<table>_value`: an action that takes no value must carry none, a percentage is 0..100, an amount is non-negative. The default is `no_benefit` — a writer that does not name the column charges the normal price and can never invent a discount — and the six assignment-side snapshot tables carry the pair for the Assigned Plan rule, because a configuration that reached only the catalogue is one no existing assignment could have been agreed with: a path that **copies** a benefit row (`snapshotPromotionGrants()`, `snapshotAssignedPlan()`, `writeAssignedPlanBenefitSection()`, both `duplicate` routes) copies the pair with it, since billing reads the snapshot and never the live row. On the way in, `parseSellableItemBenefitInput()` is the only place a request's pair is judged, and its third answer is the load-bearing one: a line the request did not *mention* keeps the pair it is stored with rather than resetting to the default, because the six section `PUT`s are replace-all and a client that sends only `gym_charge_id` + `quantity` would otherwise wipe migration 203's `waive` backfill and start charging for what a Promotion gives away — clearing a treatment is `action: 'no_benefit'`, explicitly. A read reports the pair through `shapeSellableItemBenefitRow()` (`value` a number, not mysql2's `DECIMAL` string; an action the context may not configure read back as the default). Since #896 stage 3 the pair is also what **prices** a Sellable Item line, in the Billing Simulation's two charge builders (`domain/billingSimulation.ts`) and nowhere else: the item's own treatment applies to the whole line and each covering Promotion grant's is folded on top for the periods or units that grant covers, so the pre-ticket "a Plan benefit is charged, a Promotion grant is free" is now just the `no_benefit`/`waive` case of one rule and a grant reports the action it actually applies (`waive`) rather than the retired `included`. Two properties are the rule: an item's **own** treatment never sets `promotional` — it never ends, so it *is* this contract's regular charge, and flagging it would run every discounted item to the projection's safety cap (#629 §6), exactly as #772 reasons about the Personal Membership Fee Benefit — and a grant configured `no_benefit` covers its periods without changing the price or the horizon. A one-off or session line allocates its units grant by grant in order, capped at the quantity billed, and prices whatever is left over with the item's own treatment. A loader that feeds the engine reads the pair through `toSellableItemBenefit()` **in its own context**, and the field is required on `SimulationGrant` / `SimulationPlanBenefit` for the reason `personalFeeBenefit` is required: a path that forgot it would silently charge for what a Promotion gives away. Since stage 4 the pair is **configured** in exactly one editor, the shared `SellableItemBenefits.tsx`, which takes the context as a prop: `benefitContext="promotion"` offers all five options, `benefitContext="plan"` the three, and **omitting it renders no column at all** — which is what keeps the Assigned Plan snapshot sections as they were, since their `PUT` takes quantity alone. The value input is rendered only for an action that takes one and is named after that action, and a typed number is deliberately *kept* while the action changes, so `toBenefitItems()` is what submits only the value the selected action takes — and a draft line carrying no action at all still sends a quantity-only payload, for the "keeps what it is stored with" reason above. The **labels** are per context and are locale keys, never anything this module knows: the Promotions UI says *Promotion* / *No promotion* and must not contain the word "Benefit" anywhere (§3 — `sellable-item-benefit-actions-ui.test.ts` fails if a `promotions` label says it), while the Membership Plans UI says *Benefit* / *No benefit* for the very same stored `no_benefit`. Do not add a second action list, a second editor for the pair, a per-benefit frequency, or a pricing field on the Sellable Item itself. Since #916 that pair is also what a Membership Plan's Benefit sections **display**: each row reports an `original_price_incl_tax` / `final_price_incl_tax` pair (plus the two `*_line_*` totals) from `api/src/domain/planBenefitPrices.ts`, which is `applyLineBenefit()` at quantity 1 and at the row's quantity and decides nothing else — the gross-up is `grossBenefitUnitPrice()` over `computePriceFields()`, shared with #915's loader, so the sections and the Billing Event Simulation beside them cannot quote one line two ways and no page does tax arithmetic (#817). An item carrying no price reports `null` and reads as `—`, never €0.00. The **Next proxy** on the other side of that call forwards the response as `await res.arrayBuffer()`, never `res.text()` (#830, both apps): a UTF-8 decode turns every byte that is not valid UTF-8 into U+FFFD while the status and `Content-Type` stay correct, so nothing errors and the bytes are simply undecodable — which is how a Base Theme's blob-backed logo (`GET /themes/:id/logo`) rendered as a broken `logo preview`, and how `pdfFetch()`'s receipts were corrupted. Do not branch on the content type; `ArrayBuffer` is byte-exact for JSON too.

An expanded card shows the entity's own fields read-only and holds no `<input>`, `<select>`, `<textarea>`, checkbox, toggle, `<button>`, `onChange`, Save, Cancel or Edit affordance of any kind — the context menu is the single entry point into the form, and that item is gated like any other write action. The field set both halves render is declared **once**, in a module beside the page (`apps/admin/src/app/[locale]/members/memberProfile.ts`, `…/staff/staffProfile.ts`, `…/centers/centerProfile.ts`): the keys and their order, their read-only labels, their formatting and the persisted-row → form-values mapping the Edit action seeds with, with the row type `extends`ing it. Since #882 the **layout** is shared the same way: the read-only view is the Edit form with the inputs replaced by values, so one component (`…/members/MemberProfileLayout.tsx`) owns the grid, the field order, the labels, the full-width Notes and the position of a trailing relation, and neither half restates a grid template, a `gridColumn: '1 / -1'` or a label style — each half supplies only a cell's contents through `renderField`, which is what keeps the layout presentational and unable to make a read-only field editable. The two halves never render at once either: the section that reads takes an `editing` prop keyed on the same `editingId === row.id` that opens the form, because both showing the same fields is the entity rendered twice on one page. A label or help sentence that is the *form's* stays the form's — `editLabelKey` keeps Name's required marker and `helpKey` explains how to fill a field in, so neither appears beside a value nobody can change. The read-only view renders **the same list row the form is seeded from**, never a second representation and never a second read of the entity — a second field list or a second read is how the two drift apart. Do not restate a read's business rule in the frontend either: it belongs on the route both callers use. A Member's centers carry the sole-active-center fallback (`soleActiveCenterId()` — an empty `member_centers` list is the gym's single active center, never "no centers"), and it lives on `GET /members/:memberId/centers`, which 404s a member outside the caller's gym before applying it; a Staff member, by contrast, is allowed **zero** centers (#440), so an empty list there says so in words and assumes no default. When the same entity is administered from **two pages** the shared declaration moves up rather than sideways — `apps/admin/src/components/nutritionLibrary/` holds the Nutrition Library's row shape, mapping, section order, formatters, chip style, read-only view and Details modal, and both libraries (a gym's and Cordel's Base one) import it instead of restating the columns (#799). Two rules come with that: **`⋮ → Details` carries the audit information** — the Created/Modified/Deleted By pairs and the View Audit Log link belong in that modal, not on the expanded card and never in the Edit form — and the modal renders the **list row** rather than a detail endpoint of its own, so a column it shows is a column the list returns. A "whole catalogue, assigned ones highlighted" section reuses the Edit form's selected colours through one exported style helper and renders **spans**, never disabled checkboxes. Showing an actor needs a column to read: snapshot `*_by_name` + `*_by_type` at write time (migrations 126, 178, 196), because a superadmin acting directly has no `gym_memberships` row to join to — and a shared catalogue's rows are not the reading gym's to attribute, so a gym-facing projection masks the platform actor's name (`itemDetailColumnsSql`'s `maskPlatformActors`). **The form the context menu opens is inline, in the row — never a modal** (#800): a page converted from a modal keeps `CrudModal` for its Details view only, and the inline form has to render the error line, the Save/Cancel pair and the disabled-while-saving state the modal used to give it, keep itself open on an API error with the user's input intact, and label its own controls. What it submits does not change with it: the `PUT` payload is built in the same shared module as the row → form mapping, so a column the modal carried through without rendering a control (a Center's `code`) stays in the payload as an `editable: false` field rather than silently disappearing from it. The **order** of that menu is presentation and a ticket may fix it per page — Professional Services does (#802: Duplicate first, the Deactivate·Activate slot second, Details always last), so do not "align" it back to another page's order. Red comes from `ContextMenu`'s own `danger: true` flag, never a colour in the page, and marks only what is destructive (`Deactivate` and `Delete`, never `Activate`); reordering never moves a handler, a `disabled: !canWrite` gate or a `title: readOnlyTitle`. **Creation is inline too** (#805): `+ Add <entity>` opens an inline card at the top of the list, not a modal, and it renders the *same* form body as the inline editor rather than a second copy — the section order, the row → form mapping and the payloads are declared once beside the form (`apps/admin/src/components/exercises/exerciseForm.ts`), and a column only one half may submit (Exercises' `video_url`, #717 Q6) is a parameter of that declaration plus its own payload builder, never a divergent form. A label for a fixed seeded catalogue (migration 073's nine `result_types`) is a `<thing>_<slug>` key in `apps/*/locales/base/*.json` resolved through a helper that falls back to the row's own `name`: next-intl prints a missing key verbatim, so `t(\`result_type_${slug}\`) ?? name` shows `exercises.result_type_repetitions` on screen and the `??` never fires. A card whose sections are separate sub-resources with **their own** section-level editors (#627) is still read-only when expanded: Edit mode is a mode of the one expanded body, not a second body — `isEditing` gates every section's `Edit` button and every section-level form, so both halves show the same sections and none of them can go missing from one of them (Membership Plans' PRICING was invisible to anyone editing until #816). A section-level `Edit` button belongs to that mode and nowhere else (#897 — a Promotion's four Benefit sections were editable straight from the read-only card): the header is handed its `onEdit` only inside Edit mode and `null` outside it, so the button is **absent** rather than disabled, and the card-level flag is what every section asks. That button is one component for every card that has one — `apps/admin/src/components/SectionEditButton.tsx` (#901), rendered by both the Membership Plan and the Promotion card — and it takes its colours from the Theme's existing **Buttons** group, `primaryButton`/`primaryButtonText` (`--gd-primary-btn`/`--gd-primary-btn-text`): a page must not restate its look (Plans styled it as a brand-coloured text link and Promotions as a hardcoded lilac `btnSmall('#6c63ff')`, which is the divergence the ticket removed), and the same action must not get a Theme setting of its own — the literals are `var()` fallbacks for the frames before `applyTokens()` has run, never a second source of truth — and since #912 they are spelled in exactly one module, `apps/admin/src/components/ui.tsx`, as `primaryActionColors` with `primaryBtnStyle()`/`primaryBtnSmall()` over `btnStyle()`/`btnSmall()`'s geometry, which `sectionEditButtonStyle` and the Theme editor's own primary actions (`+ Assign Centers…`, `Save changes`, `+ Add`) all derive from. A new primary action calls one of those two rather than re-spelling the pair, and dropping `btnStyle()`/`btnSmall()`'s argument is **not** the same thing: their default is `--brand`, which `applyTokens()` maps to `sidebarSelectedItemBackground` — the sidebar's colour, not an action's. Secondary, file-picker and destructive buttons keep their own colours, and a text link is not a button (its token is `--gd-link`). The label stays the page's (`plans.edit_pricing` beside `plans.edit` beside the Promotion's `edit`), as do `disabled` and `title`, because the shared button decides no permission — a discriminator naming which section is open carries no `'main'` member, because the main configuration is a form for as long as the mode lasts. Cancelling one section closes that section alone and stays in the mode, with its own error line; only the card's own Cancel or its main save leaves it. An action that changes *other* rows belongs to Edit mode too, however read-only its surroundings look (Plans' "Apply new price to assigned plans" repriced every Assigned Plan from the read-only card), `⋮ → Edit` expands the row it opens so Cancel reveals the read-only view rather than collapsing it, and leaving Edit mode closes every section editor with it. The section **order** is part of the shared declaration (`PLAN_SECTION_ORDER` in `apps/admin/src/app/[locale]/plans/planProfile.ts`), never of the JSX, and so is a block that renders *inside* a section rather than beside it — Price History is PRICING's, as `PLAN_PRICING_SUBSECTIONS` (#881), and is deliberately absent from `PLAN_SECTION_ORDER`, since a key in both lists would render the history twice. A read-only section **two different cards present the same way** is likewise one component: the compact `Label: Value` Billing & Duration summary the Plan card and the Promotion card share (`apps/admin/src/components/BillingDurationSummary.tsx`, #879) owns the look and nothing else — which items exist, how each value is formatted and what an unset value reads as stay with each page, so a Promotion keeps omitting a zero month count while a Plan spells out *Not configured*. Do not restate that style literal in a page, and do not give a summary a control or a field's explanatory sentence — both belong to the editor behind `⋮ → Edit`. See "Read-Only Expanded Row, Editing Behind the Context Menu" and "⋮ menu order and the destructive style" in `docs/feature-patterns.md`.
- **An entity administered from two pages has one editor** (#806). Exercises are edited from a gym's `[locale]/exercises` and the platform's `[locale]/cordel/exercises`, and both render `apps/admin/src/components/exercises/ExerciseEditor.tsx` over `useExerciseEditorState()` and `exerciseForm.ts` — there is no second Exercise form anywhere, so a field, a label, a section order or a validation rule is changed in one place. The split is deliberate: the **declaration** is pure (orderings and payloads are asserted directly), the **hook** owns the form values, the muscle roles, the selected result types, the validation, the error line and the `saving` flag, and the **component** is only the JSX. The editor names **no endpoint and makes no permission decision** — `onSave` and the media controls' `basePath` come from the page, which is what keeps `/exercises` (a gym's module permissions) and `/platform/exercises` (`requireSuperadmin`) out of the shared UI: do not merge the two routers, and do not put an ownership branch (`gym_id`, `cloned_from_id`, `isSuperadmin`) in the editor. A shared media control takes its route root and its storage gating as props (`ExerciseImageField`/`ExerciseVideoField`'s `basePath`, defaulting to `/exercises`, and `requiresGymStorage`, false for a Base Exercise, whose objects live under `PLATFORM_STORAGE_ROOT` and are gated by no gym's bucket). Where the two screens behaved differently, unification takes the **stricter** side — removing media asks for confirmation on both now, not neither. And a platform screen that needs a gym-facing catalogue gets its own read rather than borrowing one: `GET /platform/exercises/lookups` serves the muscle and result-type catalogues because `/muscles` and `/result-types` sit behind `tenantContext` + `requireModuleAccess('TRAINING')` + `requireFeatureEnabled('training.exercises')`, and a Base Exercises page must not break when the superadmin's *selected* gym has exercises switched off (register such a route **before** `/:id`, or Express reads its name as an id). See "When two pages edit the same entity" in `docs/feature-patterns.md`.
- Every Details view offers **View Audit Log** via the shared `apps/admin/src/components/ViewAuditLogButton.tsx` — never a hand-rolled deep link. Filter by the canonical entity type + id, never by display name. See "Details view → View Audit Log" in `docs/feature-patterns.md`.
- A gym-facing read of a **platform catalogue** (the `gym_id IS NULL` rows of a shared table) goes on the gym's own router behind `tenantContext` — never on `/platform/*`, which is `requireSuperadmin` and would lock out the gym admin who needs it (`GET /exercises/base`, #718). When a gym copies such a row into its own catalogue, the copy records provenance in **`cloned_from_id`**, and that column is the only source of truth for "where did this come from": `POST /exercises/import` reads it to decide what the gym already has, and the Exercises list derives its **System sourced** / **Custom** badge from it. Do not add a source/origin column or duplicate the library row's identity anywhere else. That copy is also the gym's **import state**, and importing is what makes the row visible to the gym (#804): `GET /exercises` filters `e.gym_id = ?` and never `OR e.gym_id IS NULL`, because existing in the platform library is not the same as having been imported — a base row a gym never imported has no business in that gym's Exercises page, under any filter, search or ordering, and adding one to the library must not make it appear in every gym at once. The filter belongs in the list query, not on one control, and there is no `imported` flag to add: the copy is the state. The library is read through `GET /exercises/base` (the Import modal), which keeps offering a non-imported row, and `GET /exercises/:id` still answers for a base row; the write paths already assume this rule, since `workout-templates.ts` and `training-plans.ts` validate an `exercise_id` with `gym_id = ?`.
- A **CodeQL alert** is cleared by fixing the code, by a human dismissing it in Security → Code scanning, or by an owner-authorized merge that records the assessment — **never by a suppression comment**. Neither `// codeql[rule]` nor `// lgtm[rule]` does anything in this repository (both were tried on the same alert, #767), so a suppression comment only misleads the next reader: `api/src/test/codeql-suppressions.unit.test.ts` fails the build if one is added. Put the reasoning in prose at the sink instead, and see "Code scanning (CodeQL)" in `docs/architecture.md` for the known `js/xss-through-dom` false positive on detached media elements, which every browser upload helper of that shape will raise again.
- A **receipt** ("factura simplificada") is issued for money *actually received*, and there is exactly one implementation of that rule: `isReceiptableEvent()` (`api/src/domain/billingEventStatus.ts`, #787). The event type must record a payment (`payment_recorded`, `recurring_payment`, `failed_billing`) **and** `deriveBillingEventStatus()` must say `paid` — which is what makes a `failed_billing` settled afterwards by Retry or Manual payment receipt-able without a special case, since #640's actions never append a second ledger row. A `waived_billing`, an `adjustment` and anything failed, expired or pending are refused. Do not add a second eligibility check, and do not put one on the `GET` routes: a `receipt_number` can only exist if the predicate already allowed it. The number itself comes from `issueReceiptNumber()` (`api/src/domain/receiptNumbers.ts`) and nowhere else — it reads the event `FOR UPDATE` before spending anything, so one payment can never burn two numbers out of the gapless per-gym, per-year `receipt_sequences`. The nightly run allocates one for every charge it settles, **after** the charge transaction has committed and in one of its own, with the failure logged and swallowed: that transaction records money the provider has already taken, so a new statement inside it can roll the charge record back while the charge stands (the `insertId` defect #635 stage 3 fixed). A receipt that fails to auto-issue stays issuable through `POST /payments/:id/receipt`, so it is never worth that risk, and `receipts_issued` is a reported counter, not a run-log column and never a reason to fail a run.
- A **`pending` payment request whose checkout page was opened is not stale** (#789). `payment_requests` carries two deadlines and they are not interchangeable: `page_token_expires` (creation + 10 min) bounds how long the *link* may be opened, and `GET /payment-page/token/:token` — the only writer that clears `page_token` on a row still `pending` — is what records that it was. `POST /billing/cleanup` therefore expires a request whose `page_token IS NOT NULL` with its token, and one whose `page_token IS NULL` only after `abandonedRequestHours()` (`api/src/domain/paymentRequestExpiry.ts`, `PAYMENT_REQUEST_ABANDONED_HOURS`, default 24, floored at 1 so a typo cannot reintroduce the defect). Do not reintroduce a single deadline, and do not add a second query or a shorter window that expires an opened request: the member is in the Card Input and a 3DS redirect while it stands, and an `expired` row is skipped by the webhook's own guard — which is how a member came to be charged with no completed request, no stored card and no `next_billing_date`. The other half of that rule lives in the webhook: **only a `completed` payload may reopen a terminal row**, and only an `expired` one, because the provider is the source of truth about money. A `failed`/`expired` payload never revives a row, and an already-`completed` row is always skipped — that skip is the handler's idempotency under Monei's retries, so nothing may widen it further. `expired` stays the cleanup response's total, because `.github/workflows/billing-run.yml` parses that field (#778).
- **Replacing a member's stored card charges nothing** (#788, migration 195). It is a card *verification*: `createCardVerificationRequest()` (`api/src/payments/provider.ts`) deliberately takes **no amount**, and the Monei adapter sends `amount: 0` + `transactionType: 'VERIF'` + `generatePaymentToken: true` — do not give that method an amount, a void path or a second provider call, and do not raise a real payment to obtain a token (the Start payment button did, which is the defect the ticket removed). The `payment_requests` row it writes exists only to carry the hosted page's `page_token` and the webhook's `provider_order`: `source = 'card_update'`, `amount = 0.00`, `charge_type_id` **NULL** — never a charge type (a `card_verification` entry in `charge_types` would put a non-charge in the cash-payment picker and in charge-type reporting). It is therefore **not a financial row**: anything that reads `payment_requests` as money excludes that source, as `GET /members`' `payment_status`, `GET /payment-requests` and `GET /me/payment-requests` do, and the webhook's card-update branch writes **no** `billing_event`, stamps no `next_billing_date` and clears none of #785's dunning counters — replacing a card is not paying, and the rejected cycle is still owed. A verification that is rejected, or completes without a token, must leave the card already on file untouched. `domain/storedCards.ts` owns the constant and the pure rules (including `cardRemovalBlock()`: removal is refused while any assignment is `active`/`paused` with a `next_billing_date`, because the nightly run skips a card-less assignment *silently*) and `api/card-updates.ts` the provider call, the insert and the reads — a new surface (staff or member) calls those rather than restating either.
- An amount crosses the **PaymentProvider boundary in minor units** (cents for EUR): every caller of `createPaymentRequest()` and `executeRecurring()` converts through `toMinorUnits()` (`api/src/payments/money.ts`), while everything on our side — `user_memberships.membership_fee_price`, `billing_events.amount`, `payment_requests.amount`, what `resolveMembershipFee()` and `priceMembershipFeeOn()` return — stays a decimal number of euros. Do not add a caller that passes a euro amount to the provider or a provider that expects euros: the nightly run and the staff Retry did exactly that for as long as the provider was stubbed in tests, and a real renewal of a 29.99 € fee would have charged twenty-nine cents. A test of a provider call asserts the `amount` the stub received.
- All config via environment variables. No hardcoded values. Payment provider credentials in particular stay in the environment — the `payment_providers` catalogue (#636) names *which* adapter a gym uses (`provider_key`), never how to authenticate as it.
- Every new code path that inserts into `gyms` must set `payment_provider_id` (NOT NULL since migration 175). Take the catalogue's default (`is_default = 1 AND deleted_at IS NULL`) unless the caller names one — `api/src/api/gyms.ts`, `api/src/test/helpers.ts` and `api/src/infra/seed.ts` are the three existing paths.
- Translated **UI labels** live in `apps/*/locales/base/{en,es,ca}.json`. Translated **data** lives in a `(entity_id, locale)` junction table with the entity's own column as the base value and fallback — never one row per language, and never a `name_es`/`name_ca` column. Resolve it server-side from the request locale (`api/src/infra/locale.ts`) and return it in a separate field (`display_name`), leaving the base column for edit forms to submit back. See "Translated Catalog Content" in `docs/feature-patterns.md`.
- Backend-first: define the API contract before building UI.
- Do not duplicate business logic in the frontend.

## API tests

Run tests with `npm test` inside `api/`. All test files live under `api/src/test/`. Reuse the helpers in `helpers.ts` — `createTestGym`, `createTestMembership`, `request`, etc.

### Unit tests vs integration tests

Write **unit tests** when the code under test has no DB or HTTP dependency — pure functions, middleware logic, crypto/validation helpers. No `createTestGym`, no `cleanupTestGyms`, no `db.end()`. Mock external dependencies with `vi.mock` or `vi.spyOn`.

Write **integration tests** for routers and anything that must exercise the full Express + MySQL stack. All rules below apply to integration tests only.

Good candidates for unit tests:
- Signature verification and payload parsing (e.g. `payments-provider.test.ts`)
- `requireModuleAccess` / `requireModuleWrite` permission matrix
- `tenantContext` and `centerContext` middleware
- Pure helper functions and input validation

### Rules for every new integration test file

- One file per domain (e.g. `bookings.test.ts`, `members.test.ts`).
- Always call `cleanupTestGyms()` in `afterAll` and `db.end()` last.
- Always create a fresh gym + membership in `beforeAll` — never share state across `describe` blocks.
- Insert DB rows directly via `db.query` for setup; use the HTTP API (`request`) for the action under test.
- Do **not** add a `slug` column to `centers` — it does not exist in the schema.

### What to cover for every new router

1. **Tenant isolation** — a resource from gym A returns 404/403 when accessed with gym B's `x-gym-id`.
2. **Auth** — unauthenticated request returns 401; wrong role returns 403.
3. **Happy path** — the main success case returns the expected status and shape.
4. **Key invariants** — e.g. capacity/waitlist for bookings, 409/keep/expire for training plans, soft-delete hidden from list + restore for members.

### cleanupTestGyms dependency order

When adding a new domain that has FKs pointing to `members` or `gyms`, extend `cleanupTestGyms` in `helpers.ts` to delete those rows first. Current order: `bookings → user_membership_services → members → class_sessions → activity_types → gym_charges → gyms`. A table whose FK to a catalog table (e.g. `gym_charges`) has no `ON DELETE CASCADE` must be deleted before that catalog table, not only before `members`.

## Finishing a task

Before opening the PR, run these checks in order:

1. **Migration review** — if any migration file was added or changed, run the `db-reviewer` agent on it. Fix all BLOCKERs before continuing.

2. **Test files** — for every new router, run the `test-writer` agent to generate `api/src/test/<router>.test.ts` (integration test). For any new pure functions or middleware, also write a unit test file (no DB helpers, use `vi.mock`/`vi.spyOn`). Run `npm test` inside `api/` to confirm all pass.

3. **Doc updates** — check whether the changes warrant updating any `.md` files:
   - `docs/roadmap.md` — mark the ticket done and update the Status section if the feature is complete.
   - `docs/architecture.md` — update if new tables, routers, middleware, or patterns were introduced.
   - `docs/feature-patterns.md` — update if a new pattern or template emerged that future tickets should follow.
   - `docs/go-to-production.md` — add a checklist item whenever the ticket defers something "until production" (there is no production environment yet); tick items the ticket completes.
   - `CLAUDE.md` — update if a new hard constraint, convention, or cleanup rule was established.

   Only update a file if the ticket genuinely changes what it documents. Navigation-only or i18n-only changes rarely need doc updates; new API surface, DB schema, or architectural patterns almost always do.

4. **Sync with origin/main** — run `/finish-feature` (or manually: `git fetch origin && git merge origin/main`). Resolve any conflicts carefully (see the Parallel agents section above). Re-run tests if any conflicts touched API code. The working tree must be clean before opening the PR.

5. **Open the PR** — commit doc changes together with the feature and run `gh pr create --base main` on a branch named `feat/<slug>-<issue-number>`. Include the issue number in the PR title and body (`Closes #N`).
